# RAG 파이프라인

두 단계로 나눠서 기억한다. **인덱싱은 미리, 검색·생성은 질문할 때마다.**

인덱싱(indexing)은 문서를 검색할 수 있는 형태로 미리 가공해 저장해 두는 일이다.
책 뒤의 "찾아보기"를 미리 만들어 두는 것과 같다. 질문이 올 때마다 100페이지를 처음부터 읽을 수는 없으니까.

---

## 1. 인덱싱 (문서가 추가·변경될 때)

```
원본 문서 (PDF · Word · 위키 · DB · 이메일)
   │
   ├─ ① 수집 (Ingestion)     : 커넥터로 가져오기. 권한 메타데이터도 함께
   ├─ ② 파싱 (Parsing)       : 텍스트 추출. 표·이미지·머리말 처리
   ├─ ③ 청킹 (Chunking)      : 검색 단위로 자르기
   ├─ ④ 임베딩 (Embedding)   : 각 청크 → 숫자 벡터
   └─ ⑤ 저장                 : Vector DB 에 (벡터 + 원문 + 메타데이터)
```

메타데이터(metadata)는 본문이 아니라 본문에 "관한" 정보다. 문서 제목, 작성 부서, 개정일, 누가 볼 수 있는지 같은 것들이다.
커넥터(connector)는 SharePoint·Confluence·사내 DB 같은 원본 시스템에서 문서를 꺼내 오는 연동 코드를 말한다.

각 단계에서 실제로 뭐가 터지는지:

| 단계 | 현실의 문제 |
| --- | --- |
| ① 수집 | 고객사 시스템이 API 를 안 준다. 권한 정보가 문서와 따로 논다. 증분 감지가 안 된다 |
| ② 파싱 | **스캔 PDF 는 텍스트가 없다**(OCR 필요). 표가 뭉개진다. 머리말/바닥글이 모든 청크에 섞인다 |
| ③ 청킹 | 조항 중간이 잘린다. 표의 헤더와 값이 분리된다 |
| ④ 임베딩 | 비용·속도. 한국어 성능이 모델마다 크게 다르다 |
| ⑤ 저장 | 문서 삭제 시 인덱스에서 안 지워져 **없는 문서를 근거로 답한다** |

표의 용어 두 개만 짚는다. 증분 감지는 "지난번 인덱싱 이후 바뀐 문서만" 골라내는 기능이다.
이게 안 되면 문서 하나가 바뀌어도 전체를 다시 처리해야 한다(`02-chunking-embedding.md` 8절).
OCR(Optical Character Recognition)은 이미지 속 글자를 읽어 텍스트로 바꾸는 기술이다. 스캔 PDF 는 사실상 사진이라 OCR 을 거쳐야 글자가 생긴다.

> **엔터프라이즈 RAG 프로젝트의 시간 대부분은 ①과 ②에서 소모된다.**
> "AI 를 붙이는 일"인 줄 알았는데 실제로는 남의 시스템에서 데이터를 꺼내오는 일이다.
> 랭코드 대표가 말한 "비표준 시스템 연동"이 바로 이 지점이다.

### 무엇을 인덱싱하지 않을지도 정한다

"있는 문서는 전부 임베딩한다"는 흔한 안티패턴이다. 아래 같은 것들은 검색 결과 자리만 차지하고 답에 도움이 안 된다.

- 모든 페이지에 반복되는 머리말·바닥글, 메뉴, 저작권 문구
- 같은 문서의 사본, 초안, 폐지된 구버전
- 질문 대상이 아닌 문서(시스템 로그, 자동 생성 알림 메일)

인덱스에 들어간 청크는 전부 top-k 자리를 두고 경쟁한다. 쓸모없는 청크 1만 개가 들어가면 정답 청크가 밀려날 기회도 1만 번 생긴다.

## 2. 검색·생성 (질문할 때마다)

```
사용자 질문
   │
   ├─ ① 쿼리 전처리     : 대화 맥락 반영해 독립 질문으로 재작성
   ├─ ② 권한 필터 결정   : 이 사용자가 볼 수 있는 문서 범위
   ├─ ③ 검색            : 벡터 검색 + 키워드 검색 (하이브리드) → top-N
   ├─ ④ 리랭킹          : 정교한 모델로 재정렬 → top-k
   ├─ ⑤ 컨텍스트 조립    : 토큰 예산 안에서 청크 배치
   ├─ ⑥ 생성            : LLM 에 "이 근거로만 답하라"
   └─ ⑦ 후처리          : 출처 매핑, 근거 검증, 스트리밍 전송
```

top-N 과 top-k 는 둘 다 "상위 몇 개"라는 뜻인데, 여기서는 단계를 구분하려고 글자를 다르게 썼다.
③에서 후보를 넓게 50개(N=50) 가져오고 ④에서 그중 정말 쓸 5개(k=5)만 남긴다고 보면 된다.
리랭킹은 `03-retrieval-quality.md` 2절에서 자세히 다룬다.

### ① 쿼리 전처리 — 자주 빠뜨리는 단계

```
사용자: "연차가 며칠이야?"
사용자: "그럼 반차는?"        ← 이 문장만 임베딩하면 아무것도 못 찾는다
```

대화형 UI 에서는 후속 질문이 독립적으로 의미를 갖지 못한다. "그럼 반차는?"에는 "규정", "사용 방법" 같은 검색할 거리가 하나도 없다.
그래서 직전 대화를 LLM 에 주고 "독립적으로 검색 가능한 질문으로 바꿔줘"를 한 번 돌린다.

```
→ "회사의 반차 사용 규정은 무엇인가"
```

이걸 **query rewriting / condensing** 이라고 한다. 챗 RAG 에서 체감 효과가 가장 큰 개선 중 하나다.

### ② 권한 필터는 검색 **전에**

ACL(Access Control List)은 "이 문서를 누가 볼 수 있는가"를 적어 둔 목록이다.
예를 들어 인사평가 문서의 ACL 이 `["hr-team", "executives"]` 면 그 두 그룹에 속한 사람만 볼 수 있다.
테넌트(tenant)는 시스템을 함께 쓰는 고객사 하나를 말한다. 아래 SQL 의 `tenant_id` 가 "어느 고객사 데이터인가"다.

```sql
-- ✅ 검색 전 필터 (pre-filtering)
SELECT ... FROM chunks
WHERE tenant_id = :tid AND acl_group = ANY(:user_groups)
ORDER BY embedding <=> :q LIMIT 20;

-- ❌ 검색 후 필터 — top-20 을 가져와 걸러내면 0개가 남을 수 있다
```

후처리 필터링은 "권한 있는 문서가 있는데도 빈 답"을 만든다.
전체에서 가장 비슷한 20개가 하필 전부 임원 전용 문서였다면, 사원에게는 21위 이하에 볼 수 있는 문서가 있어도 0개가 돌아간다.
자세한 건 `04-enterprise-rag.md`.

### ⑤ 컨텍스트 조립 — 순서가 성능에 영향을 준다

컨텍스트(context)는 LLM 에 한 번에 넣는 프롬프트 전체, 그중에서도 검색해 온 근거 청크 묶음을 말한다.
컨텍스트 윈도우는 모델이 한 번에 읽을 수 있는 최대 토큰 수다. 토큰 예산은 그 안에서 근거 청크에 배정한 몫이다.
예를 들어 근거용 예산이 4,000 토큰이고 청크가 평균 500 토큰이면 많아야 8개가 들어간다.

**"Lost in the middle"** 현상: LLM 은 프롬프트의 처음과 끝을 잘 보고 가운데를 흘리는 경향이 있다.
2023년 같은 제목의 논문이 이를 측정했다. 정답이 든 문서를 20개 문서 묶음의 맨 앞이나 맨 뒤에 두면 잘 맞혔다. 가운데에 두면 정답률이 눈에 띄게 떨어졌다.
그래서 가장 관련 높은 청크를 맨 앞이나 맨 뒤에 배치하는 전략을 쓴다.

```
나쁜 배치: [3위] [5위] [1위] [4위] [2위]   ← 1등이 가운데에 묻힘
좋은 배치: [1위] [3위] [5위] [4위] [2위]   ← 1·2등이 양 끝
```

또 하나, **많이 넣을수록 좋은 게 아니다.** 예산이 남는다고 관련도 낮은 청크까지 채우면 모델이 엉뚱한 문장을 근거로 삼을 기회만 늘어난다.
점수가 임계값(`00-foundations.md` 4절) 밑인 청크는 예산이 남아도 넣지 않는다.

각 청크에는 출처 표시를 붙여서 넣어야 나중에 인용을 매핑할 수 있다.

```
[1] (사내규정_2026.pdf, 3장 2절)
연차휴가는 1년간 80% 이상 출근한 근로자에게 15일을 부여한다...

[2] (인사팀_FAQ.md)
Q. 입사 1년 미만인데 연차를 쓸 수 있나요?...
```

### ⑥ 생성 프롬프트의 뼈대

```
당신은 사내 규정 안내 어시스턴트입니다.

규칙:
- 아래 <문서> 안의 내용만 근거로 답하십시오.
- 문서에 없는 내용은 추측하지 말고 "제공된 문서에서 확인할 수 없습니다"라고 답하십시오.
- 답변의 각 주장 끝에 [1], [2] 형식으로 근거 번호를 표시하십시오.
- 문서들이 서로 모순되면 그 사실을 알리고 각각을 제시하십시오.

<문서>
[1] (출처) ...
[2] (출처) ...
</문서>

질문: {question}
```

첫 번째 규칙처럼 "찾아 준 문서 안에서만 답하라"고 묶는 것을 그라운딩(grounding)이라고 한다.
그라운딩이 없으면 모델은 학습 때 본 일반 지식으로 빈칸을 메운다. "보통 회사는 연차가 15일이니까" 하고 우리 회사 규정과 다른 답을 지어내는 식이다.
이렇게 근거 없이 그럴듯한 내용을 만들어 내는 현상을 환각(hallucination)이라고 부른다.

**"모른다고 답해도 된다"를 명시적으로 허용하는 것**이 환각을 줄이는 가장 저렴한 장치다.
모델은 기본적으로 뭐라도 답하려는 성향이 있다.

### ⑦ 후처리 — 답을 내보내기 전에

모델이 붙인 `[1]`, `[2]` 를 ⑤에서 붙인 출처 목록과 맞춰 실제 문서 링크로 바꾼다(출처 매핑).
근거 검증은 답변의 각 문장이 정말 그 근거 청크에 있는 내용인지 확인하는 단계다.
이 성질을 충실성(faithfulness)이라고 부른다. 측정 방법은 `03-retrieval-quality.md` 4절의 LLM-as-judge 에서 다룬다.

## 3. 핵심 용어 — 각각 한 줄로

> 임베딩·코사인 유사도가 한 줄로는 감이 안 오면 `00-foundations.md` 를 먼저 읽는다.

| 용어 | 한 줄 | 실무 포인트 |
| --- | --- | --- |
| **임베딩** | 텍스트를 의미가 담긴 고차원 벡터로 | 의미가 비슷하면 벡터 공간에서 가깝다 |
| **Vector DB** | 벡터를 저장하고 가장 가까운 것을 빠르게 찾는 DB | pgvector, Qdrant, Azure AI Search |
| **코사인 유사도** | 두 벡터가 이루는 각도 | 크기가 아니라 **방향**을 본다 |
| **ANN** | 근사 최근접 탐색 (HNSW, IVFFlat) | 전수 비교는 O(n) → 정확도를 조금 포기하고 속도를 얻음 |
| **청킹** | 문서를 검색 단위로 자르기 | **품질의 8할.** 오버랩을 둔다 |
| **top-k** | 상위 몇 개를 가져올지 | 키우면 놓칠 확률↓ 노이즈↑ 비용↑ |
| **리랭킹** | 넓게 가져온 뒤 정교한 모델로 재정렬 | "빠른 검색 → 정확한 재정렬" |
| **하이브리드 검색** | BM25(키워드) + 벡터 | **고유명사·제품코드·사번**은 키워드가 강하다 |
| **메타데이터 필터** | 부서·권한·기간으로 범위를 먼저 좁힘 | 엔터프라이즈의 핵심 |
| **컨텍스트 윈도우** | 프롬프트 최대 토큰 | 무한정 못 넣는다 = 설계 문제 |
| **그라운딩** | 찾은 문서 안에서만 답하도록 제약 | 출처 표시와 한 쌍 |

### ANN 이 왜 필요한가

문서 100만 개 × 1536차원 벡터. 질문 하나마다 100만 번의 코사인 유사도 계산은 너무 느리다.
위 표의 O(n) 은 "청크 수(n)에 비례해 시간이 늘어난다"는 뜻이다. 청크가 10배 늘면 검색도 10배 느려진다.
ANN(Approximate Nearest Neighbor, 근사 최근접 탐색)은 전부 비교하는 대신 "가까울 만한 후보"만 골라 비교한다.
pgvector 가 제공하는 ANN 인덱스는 두 가지다.

**HNSW** (Hierarchical Navigable Small World) 는 벡터들을 그래프로 미리 연결해 두고, 가까운 쪽으로 따라가며 탐색한다.
지하철 노선도에 비유할 수 있다. 맨 위층에는 급행역 몇 개만 있어 먼 거리를 빠르게 건너뛴다. 아래층으로 내려갈수록 역이 촘촘해져 목적지 근처를 정밀하게 찾는다.
정확도 99% 를 유지하면서 수십\~수백 배 빠르다.

대가: **인덱스 구축 비용과 메모리**. 그리고 근사이므로 **아주 드물게 진짜 최근접을 놓친다.**

**IVFFlat** 은 벡터들을 미리 몇 개의 묶음(클러스터)으로 나눠 두고 질문과 가까운 묶음 몇 개만 뒤진다.
도서관이 책을 분야별 서가로 나눠 두고 "IT 서가와 경영 서가만 찾아보는" 방식과 같다.
묶음 수는 `lists`, 질의 때 뒤질 묶음 수는 `ivfflat.probes` 로 정한다.
HNSW 보다 인덱스를 빨리 만들고 메모리도 덜 쓰지만 같은 속도에서 정확도(recall)는 대체로 낮다.
또 묶음을 기존 데이터로 나누기 때문에 데이터가 어느 정도 쌓인 뒤에 인덱스를 만들어야 한다.

| | HNSW | IVFFlat |
| --- | --- | --- |
| 구조 | 층이 있는 그래프 | 클러스터 묶음 |
| 질의 시 조절값 | `hnsw.ef_search` | `ivfflat.probes` |
| 장점 | 속도 대비 정확도가 좋다 | 구축이 빠르고 메모리가 적다 |
| 단점 | 구축이 느리고 메모리를 많이 쓴다 | 데이터가 쌓인 뒤 만들어야 한다 |

여기서 recall 은 "진짜 가장 가까운 것들 중 몇 %를 찾아냈나"다. 근사 탐색이 정답 10개 중 9개를 찾으면 recall 0.9 다.
특별한 이유가 없으면 HNSW 로 시작하는 경우가 많다. 파라미터는 `02-chunking-embedding.md` 7절.

> ❓ 입사 후 확인: CXP Agent 는 pgvector 의 HNSW 를 쓰나, 다른 Vector DB(Azure AI Search 등)를 쓰나?

## 4. 왜 키워드 검색이 아니라 벡터인가 (그리고 왜 둘 다인가)

키워드 검색은 질문과 문서에 같은 단어가 있는지를 본다. 대표 알고리즘이 BM25 다(`03-retrieval-quality.md` 1절에서 계산까지 다룬다).
벡터 검색은 앞에서 본 대로 의미의 방향이 비슷한지를 본다.

| 질문 | 키워드 검색 | 벡터 검색 |
| --- | --- | --- |
| "연차 며칠 쓸 수 있어?" (문서엔 "휴가 부여 일수") | ❌ 글자가 안 겹침 | ✅ 의미가 가까움 |
| "SKU-4821 재고" | ✅ 정확히 매칭 | ❌ 코드는 의미가 없어 벡터가 무의미 |
| "김철수 과장 연락처" | ✅ | △ 이름은 벡터로 구분이 약함 |
| "작년에 매출이 왜 떨어졌지?" | ❌ | ✅ |

**그래서 하이브리드가 기본값이다.** 둘 다 돌리고 점수를 합친다 (→ `03-retrieval-quality.md` 의 RRF).

한국어 특유의 문제: 교착어라 형태소 분석 없이는 키워드 검색이 잘 안 된다.
교착어는 "휴가 + 를", "휴가 + 는"처럼 단어 뒤에 조사·어미가 붙어 형태가 바뀌는 언어다.
"휴가를", "휴가는", "휴가가" 가 전부 다른 토큰이 된다. PostgreSQL 기본 `to_tsvector` 는 한국어를 모른다.
→ 한국어 형태소 분석기(mecab-ko 등)를 붙이거나, Elasticsearch 의 nori 플러그인을 쓴다.
형태소 분석기는 "휴가를"을 "휴가 / 를"로 쪼개 주는 도구다. 그러면 "휴가"끼리 매칭된다.

> ❓ 입사 후 확인: 한국어 키워드 검색을 어떻게 처리하고 있나?

## 5. RAG 가 실패하는 6가지 — 원인별 대응

| 실패 | 증상 | 어디를 고치나 |
| --- | --- | --- |
| **검색 실패** | 정답 문서가 top-k 에 안 들어옴 | 청킹, 임베딩 모델, 하이브리드, 쿼리 재작성 |
| **청킹 경계 손상** | 조항이 반쪽, 표 헤더 분실 | 구조 기반 분할, 오버랩, 컨텍스트 주입 |
| **노이즈** | k 를 키웠더니 오히려 답이 나빠짐 | 리랭킹으로 k 를 줄인다 |
| **문서 모순** | 구버전·신버전 규정이 같이 검색됨 | 유효기간·버전 메타데이터, 최신성 가중치 |
| **권한 누락** | 볼 수 없는 문서가 근거로 쓰임 | **사고다.** 검색 전 필터 강제 |
| **측정 안 함** | 조용히 나빠지는 걸 모름 | 평가셋 + CI |

**진단 순서가 중요하다.**

```
답이 이상하다
   ↓
① 어떤 청크가 top-k 로 들어갔는지 로그를 본다   ← 반드시 여기부터
   ↓
정답 청크가 없다 → 검색 문제 (청킹/임베딩/쿼리)
정답 청크가 있다 → 생성 문제 (프롬프트/모델/컨텍스트 순서)
```

**이 두 갈래를 분리하지 못하면 영원히 프롬프트만 만지게 된다.**
그래서 "어떤 청크가 들어갔는가"를 로그와 관리 화면에서 볼 수 있어야 한다.
이건 프론트엔드가 만들 수 있는 것이고, 팀 전체의 디버깅 속도를 바꾼다.

## 6. 프론트엔드가 실제로 만드는 것

| 화면 | 왜 중요한가 |
| --- | --- |
| **출처(citation) 표시** | 신뢰의 대부분이 여기서 만들어진다. 문서명 + 페이지 + 원문 하이라이트로 점프 |
| **"모른다"의 표현** | 억지 답변 대신 *무엇이 부족한지* — "관련 문서를 찾지 못했습니다. 검색어를 바꿔보세요" |
| **스트리밍 렌더링** | 토큰 단위 갱신 시 리렌더 최적화 (→ `05-realtime-ui/`) |
| **피드백 수집** | 👍/👎 + "왜 틀렸는지" → 평가셋의 원료가 된다 |
| **검색 과정 노출** | "문서 12개 검색 중 → 3개 선택" 를 보여주면 대기 시간이 견딜 만해진다 |
| **디버그 뷰 (내부용)** | top-k 청크와 점수를 볼 수 있는 관리자 화면. **팀의 생산성 도구** |
| **권한 표시** | "이 답변은 당신이 접근 가능한 12개 문서를 기준으로 합니다" |

마지막 두 개는 아무도 요구하지 않지만 있으면 팀 전체가 쓰게 된다.
"요구사항이 불명확해도 스스로 구조를 잡는" 일의 구체적 형태다.

2. 권한 필터를 검색 뒤에 걸면 어떤 상황에서 빈 답이 나오나? 숫자로 예를 들어 보라.
