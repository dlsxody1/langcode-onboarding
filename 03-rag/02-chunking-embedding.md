# 청킹과 임베딩

**RAG 품질의 8할이 여기서 결정된다.** 모델을 바꿔서 해결되는 문제가 아니다.

---

## 1. 청킹 — 왜 자르나

세 가지 제약이 겹쳐서 자를 수밖에 없다.

1. **임베딩 모델의 입력 길이 제한** (보통 512~8192 토큰)
2. **긴 텍스트 하나를 벡터 하나로 만들면 의미가 뭉개진다** — 100페이지 문서의 평균 벡터는 아무것도 가리키지 않는다
3. **컨텍스트 윈도우 예산** — 검색 결과를 프롬프트에 넣어야 하는데 무한정 못 넣는다

---

## 2. 전략별 비교

### ① 고정 길이 + 오버랩 — 기본값

```python
chunk_size = 500        # 토큰 또는 문자
overlap    = 50         # 앞 청크의 끝을 다음 청크에 겹쳐 넣는다
```

**오버랩이 있는 이유:** 경계에서 문맥이 끊기는 걸 완화한다.
"연차는 15일이다. 단, 입사 1년 미만은" / "6개월 이상 근무 시 1일씩 부여한다" 로 잘리면
두 번째 청크만 검색됐을 때 무슨 얘긴지 알 수 없다.

- ✅ 단순, 어떤 문서에나 적용
- ❌ 문장·조항 중간에서 자른다

### ② 재귀적 문자 분할 (Recursive) — 실무 표준

구분자 목록을 우선순위대로 시도한다.

```
["\n\n", "\n", ". ", " ", ""]
  문단     줄     문장   단어  글자
```

문단으로 잘라서 크기가 맞으면 거기서 끝, 너무 크면 줄 단위로, 그래도 크면 문장 단위로...
**LangChain 의 `RecursiveCharacterTextSplitter` 가 이것이고, 대부분의 출발점이다.**

### ③ 구조 기반 — 문서에 구조가 있을 때 가장 좋다

| 문서 유형 | 자연스러운 단위 |
| --- | --- |
| 사내 규정·계약서 | **조항** (제1조, 제2조) |
| Markdown 위키 | 헤딩 (`##`, `###`) |
| API 문서 | 엔드포인트 |
| FAQ | Q&A 쌍 |
| 회의록 | 안건 |
| 코드 | 함수·클래스 |

**규정 문서를 조항 단위로 자르면 검색 품질이 눈에 띄게 올라간다.**
"제15조 연차휴가"가 통째로 한 청크면, 질문이 무엇이든 그 조항 전체가 근거로 들어간다.

랭코드 고객사 문서(정책·규정·계약)는 대부분 구조가 뚜렷하다. **여기에 투자할 가치가 크다.**

### ④ 의미 기반 (Semantic chunking)

인접 문장들의 임베딩 유사도를 계산해서, **주제가 바뀌는 지점**에서 자른다.
- ✅ 경계가 자연스럽다
- ❌ 인덱싱 비용이 크고, 생각보다 이득이 작을 때가 많다. **먼저 ②③ 부터 시도해라**

### ⑤ 부모-자식 (Small-to-Big) — 매우 유용한 패턴

```
검색은 작은 청크로 (정확도 ↑)
프롬프트에는 그 청크가 속한 큰 단락을 넣는다 (문맥 ↑)
```

작은 청크는 의미가 집중돼 있어 검색이 잘 되고, 큰 단락은 LLM 이 답을 만들기에 충분한 맥락을 준다.
**두 마리 토끼를 잡는 흔한 실무 패턴이다.** 구현은 청크에 `parent_id` 를 두면 끝.

## 3. 청크 크기는 어떻게 정하나

**정답은 없고, 측정해서 정한다.** 다만 출발점은 있다.

| 문서 성격 | 권장 출발점 |
| --- | --- |
| 조항형 (규정·계약) | 조항 단위 (가변) |
| 서술형 (보고서·기사) | 300~800 토큰 + 10~15% 오버랩 |
| FAQ·짧은 문서 | 문서 하나가 청크 하나 |
| 코드 | 함수 단위 |
| 대화 로그 | 턴 몇 개 묶음 |

**트레이드오프:**

```
청크가 작다  →  검색 정확 ↑, 문맥 부족 ↑, 청크 수 ↑ (비용 ↑)
청크가 크다  →  문맥 충분 ↑, 노이즈 ↑, 검색 희석 ↑
```

"검색 희석"은 **긴 청크의 벡터가 여러 주제의 평균이 되어 무엇과도 애매하게 비슷해지는 것**이다.

> 실제로는 평가셋(→`03-retrieval-quality.md`)을 만들어 놓고 300/500/800 을 각각 돌려
> Recall@5 를 비교한다. 이게 유일하게 신뢰할 수 있는 방법이다.

## 3-2. 실측 — 청크 크기만 바꿨을 때 무슨 일이 일어나는가

`labs/lab2-mini-rag` 로 실제로 측정한 결과다. **문서·질문·임베딩·검색 코드는 전부 동일하고
청킹 설정만 바꿨다.** (한국어 문서 3개 약 6.4KB, 평가 질문 25개, TF-IDF 임베딩)

| 청킹 설정 | 청크 수 | Recall@1 | Recall@3 | MRR |
| --- | ---: | ---: | ---: | ---: |
| fixed 800자 / overlap 80 | 5 | 0.600 | **1.000** | **0.780** |
| fixed 400자 / overlap 40 | 9 | 0.560 | 0.920 | 0.753 |
| **heading (구조 기반)** | 21 | **0.600** | 0.800 | 0.736 |
| fixed 150자 / overlap 50 | 30 | — | 0.760 | 0.667 |
| fixed 150자 / overlap 0 | 21 | 0.440 | 0.720 | 0.613 |

### 읽는 법 ① — 작은 청크는 일관되게 나쁘다

150자 청크는 **모든 지표에서, 모든 검색 방식에서** 최하위다. Recall@1 이 0.600 → 0.440 으로 떨어진다.
이유는 실제 청크를 보면 바로 보인다.

```
── 보안정책.md#f2  (150자)
# 3. 생성형 AI 사용 - 사내에서 승인된 AI 도구 외의 외부 AI 서비스에 회사 데이터를 입력하는 것을
금지한다. - 승인 도구 목록은 정보보호팀이 분기별로 갱신한다. - 고객사 데이터를 AI 도구에 입력할
때는 고객사와의 계약에 데이터 처리 조항이 있는지 먼저 ...

── 보안정책.md#f3  (149자)
확인하여야 한다. - 소스코드는 승인된 AI 코딩 도구에 한하여 입력할 수 있다.  ## 4. 단말 보안
- 업무용 노트북은 디스크 전체 암호화를 적용하여야 한다. ...
```

**"소스코드는 승인된 AI 코딩 도구에 한하여 입력할 수 있다"** 가 `#f3` 의 첫머리에 있는데,
그 앞 문장은 `#f2` 에 있고 `#f3` 은 "확인하여야 한다."라는 **문장 꼬리로 시작한다.**
게다가 `#f3` 은 AI 정책과 단말 보안이라는 **서로 무관한 두 주제가 섞여 있다.**
이 청크의 벡터는 어느 쪽과도 애매하게 비슷한 값이 된다 — 이게 "검색 희석"의 실물이다.

같은 내용이 구조 기반으로는 이렇게 잘린다.

```
── 보안정책.md#h2  (235자)  정보보안 정책 > 3. 생성형 AI 사용
[보안정책.md > 정보보안 정책 (v4.2, 2026-03 개정) > 3. 생성형 AI 사용]
- 사내에서 승인된 AI 도구 외의 외부 AI 서비스에 회사 데이터를 입력하는 것을 금지한다.
- 승인 도구 목록은 정보보호팀이 분기별로 갱신한다.
- 고객사 데이터를 AI 도구에 입력할 때는 ... 먼저 확인하여야 한다.
- 소스코드는 승인된 AI 코딩 도구에 한하여 입력할 수 있다.
```

주제 하나가 통째로 들어 있고, **맨 앞에 출처 경로가 붙어 있다**(맥락 주입 → 다음 절).

### 읽는 법 ② — 오버랩을 키운다고 좋아지지 않는다

150자 설정에서 오버랩만 0 → 50 → 80 으로 올려봤다.

| overlap | 청크 수 | Recall@5 (hybrid) |
| ---: | ---: | ---: |
| 0 | 21 | 0.880 |
| 50 | 30 | 0.840 |
| 80 | 43 | 0.800 |

**올릴수록 나빠졌다.** 오버랩을 키우면 거의 같은 내용의 청크가 여러 개 생기고,
**top-k 자리를 그 중복들이 차지해서** 정말 필요한 다른 청크가 밀려난다.
(청크 수가 21 → 43 으로 두 배가 된 것을 보라)

오버랩은 "경계에서 잘리는 것"을 완화하는 장치이지 많을수록 좋은 값이 아니다. 10~15% 가 관례적 출발점.

### 읽는 법 ③ — 이 표를 그대로 믿으면 안 된다 ⚠️

**`fixed 800/80` 이 1등인 건 청킹 전략이 좋아서가 아니다.** 청크가 **5개뿐**인데 `k=3` 으로 뽑으면
전체의 60% 를 통째로 프롬프트에 넣는 것이다. 검색이랄 게 없다.

실제 제품은 청크가 수만~수십만 개다. 거기서는 800자 청크가 이기지 않는다.
**이 실험의 코퍼스가 6KB 라서 생긴 인공물이다.**

그래서 위 표를 `Recall@5` 가 아니라 **`Recall@1` 과 `MRR`** 로 봐야 한다.
가장 엄격한 `Recall@1` 에서는 구조 기반(21청크)이 800자(5청크)와 **동점**이다.
청크가 4배 많은데도 같은 정확도라는 뜻이고, 이건 실제 규모에서는 구조 기반이 이긴다는 신호다.

> **이게 이 절에서 가장 중요한 교훈이다.**
> 평가 숫자는 항상 코퍼스 규모·k 값·정답 레이블에 의존한다.
> "0.96 이 나왔다"가 아니라 **"어떤 조건에서 0.96 인가"** 를 같이 봐야 한다.
> 이 함정에 대해서는 `03-retrieval-quality.md` 4절에서 더 다룬다.

## 4. 청크에 맥락을 주입하기 — 효과 큰 기법

잘린 청크는 자기가 어디서 왔는지 모른다.

```
원문 청크: "이 경우 초과분은 다음 해로 이월되지 않는다."
```

이것만 검색되면 무슨 얘긴지 알 수 없다. **각 청크 앞에 출처 맥락을 붙여서 임베딩한다.**

```
[사내규정_2026.pdf > 제3장 휴가 > 제15조 연차휴가]
이 경우 초과분은 다음 해로 이월되지 않는다.
```

더 나아가 **Contextual Retrieval** (Anthropic 이 2024 에 제안): LLM 으로 각 청크마다
"이 청크가 전체 문서에서 어떤 맥락인지" 한두 문장을 생성해 앞에 붙인다.
검색 실패율이 크게 떨어진다고 보고됐다. **인덱싱 비용이 올라가지만 프롬프트 캐싱으로 상당히 상쇄된다.**

## 5. 파싱 — 청킹 전에 이미 망가지는 것들

| 문제 | 증상 | 대응 |
| --- | --- | --- |
| **스캔 PDF** | 텍스트가 아예 안 나옴 | OCR (Azure Document Intelligence, Tesseract) |
| **표** | 셀이 뒤죽박죽, 헤더 분실 | 표는 따로 추출해 Markdown 표로 변환. 헤더를 모든 행 청크에 반복 |
| **머리말/바닥글** | 모든 청크에 "주식회사 OO 대외비" 가 섞임 | 반복 패턴 제거 |
| **다단 레이아웃** | 좌우 칼럼이 섞여 읽힘 | 레이아웃 인식 파서 |
| **이미지 속 정보** | 조직도·다이어그램이 통째로 날아감 | 비전 모델로 캡션 생성 |
| **각주·미주** | 본문 중간에 끼어듦 | 분리 |

**표가 특히 중요하다.** 엔터프라이즈 문서의 핵심 정보는 표에 있는 경우가 많다
(요금표, 권한 매트릭스, 일정표). 표를 제대로 못 다루면 그 질문들은 전부 실패한다.

표 처리의 실무 패턴:
- 표 전체를 하나의 청크로 (작은 표)
- 행 단위 청크 + **각 행에 헤더를 반복해서 붙임** (큰 표)
- 표에 대한 요약 문장을 LLM 으로 생성해 함께 인덱싱

> Azure Document Intelligence 는 표·레이아웃 추출이 강하고 .NET SDK 가 있다.
> 랭코드가 MS 파트너이므로 이걸 쓸 가능성이 높다.

## 5-2. 실측 — TF-IDF 는 의미를 모른다는 것의 실물

같은 실습에서, 질문 하나만 **모든 설정에서 계속 실패**한다.

```
질문: "새로 들어온 사람도 집에서 일할 수 있나요?"
정답: 사내규정 제42조 — "신규 입사자는 입사 후 3개월간 재택근무를 신청할 수 없다"
```

TF-IDF 벡터 검색이 실제로 가져온 것:

```
1. [0.1140] 인사팀FAQ.md / Q. 입사한 지 6개월인데 휴가를 쓸 수 있나요?
2. [0.0999] 인사팀FAQ.md / Q. 올해 휴가를 다 못 썼는데 돈으로 받을 수 있나요?
3. [0.0460] 사내규정.md  / 제41조 (근무시간)
```

**정답 청크는 top-10 안에도 없다.** 세 개 모두 휴가 이야기이고 재택근무와 무관하다.

왜 이렇게 되는지는 단어를 나열해 보면 즉시 보인다.

| 질문의 표현 | 문서의 표현 | 겹치는 글자 |
| --- | --- | --- |
| 새로 들어온 사람 | 신규 입사자 | **없음** |
| 집에서 일하다 | 재택근무 | **없음** |

TF-IDF 는 **글자가 겹쳐야** 가깝다고 판단한다. 겹치는 게 "사람/있나요" 같은 흔한 말뿐이니,
우연히 "입사"라는 글자가 들어간 휴가 FAQ 가 1등이 된 것이다.

점수를 보라 — 1등이 **0.1140** 이다. 잘 맞은 검색(보통 0.3 이상)에 비해 현저히 낮다.
**"최고점이 낮다"는 것 자체가 '못 찾았다'는 신호다.** 이걸 임계값으로 잡아
"관련 문서를 찾지 못했습니다"를 띄우는 것이 `04-enterprise-rag.md` 에서 말하는 **"모른다"의 UX** 다.

진짜 임베딩 모델은 학습 과정에서 "신규 입사자 ≈ 새로 들어온 사람", "재택근무 ≈ 집에서 일하다"를
벡터 공간상 가까운 위치로 배치한다. **그게 "의미 검색"이라는 말의 전부다.**

> **엔터프라이즈 맥락에서 이게 왜 중요한가:**
> 규정 문서는 "신규 입사자", "소정근로시간", "부여한다" 같은 **격식체 법률 문어**로 쓰여 있고,
> 사용자는 "새로 온 사람", "하루 몇 시간 일해요?" 같은 **구어**로 묻는다.
> 이 둘 사이의 간극이 한국어 엔터프라이즈 RAG 에서 가장 큰 검색 실패 요인이다.
> → 대응: 좋은 다국어 임베딩 모델 + 하이브리드 검색 + (문서 쪽에) FAQ 형태의 구어 문서를 함께 인덱싱

| 항목 | 의미 |
| --- | --- |
| **차원 수** | 768 / 1024 / 1536 / 3072. 클수록 표현력↑ 저장·검색 비용↑ |
| **최대 입력 토큰** | 512 ~ 8192. 청크 크기의 상한 |
| **다국어 성능** | **한국어 성능은 모델마다 편차가 매우 크다** |
| **비용** | 백만 토큰당. 인덱싱은 1회, 질의는 매번 |
| **온프레미스 가능 여부** | 고객사가 데이터 반출을 금지하면 필수 |

### 선택지

| 모델 | 특징 |
| --- | --- |
| OpenAI `text-embedding-3-small/large` | 무난한 기본값. large 는 3072차원, 차원 축소 지원 |
| Azure OpenAI 의 동일 모델 | **데이터가 Azure 리전 밖으로 안 나간다** → 엔터프라이즈에서 결정적 |
| Cohere `embed-multilingual-v3` | 다국어 강함 |
| BGE-M3, multilingual-e5 | **오픈소스. 한국어 좋고 온프레미스 가능** |
| KURE, KoE5 등 한국어 특화 | 한국어 벤치마크 상위 |

> **엔터프라이즈에서 모델 선택은 성능보다 데이터 거버넌스가 먼저 결정한다.**
> "금융 고객사라 데이터를 외부로 못 보낸다" → 온프레미스 오픈소스 모델 확정. 성능은 그 다음 얘기.

### 절대 규칙

**인덱싱과 질의에 같은 모델을 써야 한다.** 당연해 보이지만 실수가 잦다.
모델을 바꾸면 **기존 벡터 전부를 다시 만들어야 한다** (재인덱싱). 벡터 공간이 완전히 다르기 때문.
100만 청크를 재임베딩하는 건 시간과 비용이 드는 일이므로, 모델 교체는 큰 결정이다.

> ❓ 입사 후 확인: 임베딩 모델은 뭘 쓰나? 고객사별로 다른가? 재인덱싱은 어떻게 하나?

## 7. Vector DB 에 실제로 저장하는 것

```sql
CREATE TABLE chunks (
  id           uuid PRIMARY KEY,
  tenant_id    uuid NOT NULL,              -- 멀티테넌시
  document_id  uuid NOT NULL,
  parent_id    uuid,                       -- small-to-big
  chunk_index  int  NOT NULL,              -- 문서 내 순서

  content      text NOT NULL,              -- 원문 (LLM 에 넣을 것)
  embedding    vector(1536) NOT NULL,      -- pgvector

  -- 검색 필터용 메타데이터
  acl_groups   text[],                     -- 접근 가능 그룹
  source_type  text,                       -- 'policy' | 'faq' | 'contract'
  department   text,
  valid_from   date,
  valid_to     date,                       -- 만료된 규정 제외용
  version      int,

  -- 출처 표시용
  source_uri   text,                       -- 원문으로 점프할 URL
  page_no      int,
  section      text,                       -- "제3장 > 제15조"

  content_hash text,                       -- 증분 인덱싱: 안 바뀐 청크는 건너뛴다
  indexed_at   timestamptz
);

CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON chunks (tenant_id, source_type);
CREATE INDEX ON chunks USING gin (acl_groups);
```

**벡터만 저장하는 게 아니다.** 메타데이터가 벡터만큼 중요하다.
- `acl_groups` 없으면 권한 필터를 못 한다
- `valid_to` 없으면 폐지된 규정으로 답한다
- `source_uri`, `page_no` 없으면 출처를 표시할 수 없다
- `content_hash` 없으면 문서 하나 바뀔 때마다 전체를 재임베딩한다

### HNSW 파라미터 (알아만 두기)

```sql
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
SET hnsw.ef_search = 40;   -- 질의 시: 크면 정확↑ 느림
```

기본값으로 시작하고, recall 이 부족할 때만 `ef_search` 를 올린다.

## 8. 증분 인덱싱 — 운영의 핵심

```
문서 변경 감지 (웹훅 / 폴링 / 변경 로그)
   ↓
문서를 다시 파싱·청킹
   ↓
청크별 content_hash 비교
   ├─ 같다 → 건너뜀 (임베딩 비용 0)
   ├─ 다르다 → 재임베딩 후 UPDATE
   └─ 사라졌다 → DELETE
```

**삭제 처리를 반드시 해라.** 원본에서 지워진 문서가 인덱스에 남아 있으면,
AI 가 **없는 문서를 근거로 답한다.** 사용자가 원문 링크를 눌렀는데 404 가 나오는 순간 신뢰가 끝난다.

문서 접근 권한이 바뀐 경우도 마찬가지다. 사람이 부서 이동을 하면 볼 수 있는 문서가 바뀐다.
→ **권한은 인덱스에 박아 넣는 것보다 질의 시점에 조회하는 게 안전할 때가 많다.**

## 9. 이 문서에서 남겨야 할 것

1. **청킹은 검색 품질의 상한선을 정한다.** 답이 두 청크로 잘려 있으면 어떤 모델도 못 찾는다 (3-2절)
2. **오버랩은 많을수록 좋지 않다.** 중복 청크가 top-k 를 잡아먹는다. 10~15% 가 출발점 (3-2절)
3. **구조가 있는 문서는 구조를 따라 잘라라.** 규정·계약서는 조항 단위가 정답에 가깝다
4. **청크에 출처 경로를 붙여서 임베딩해라.** 떼어놔도 어디서 왔는지 알 수 있게 (4절)
5. **표와 스캔 PDF 가 실무의 진짜 난관이다.** 파싱 단계에서 이미 망가지면 뒤는 손쓸 수 없다 (5절)
6. **어휘 기반 검색은 구어 질문을 못 받는다.** 규정은 문어체, 사용자는 구어체 (5-2절)
7. **임베딩 모델을 바꾸면 전체 재인덱싱이다.** 그래서 모델 교체는 가벼운 결정이 아니다 (6절)
8. **메타데이터가 벡터만큼 중요하다.** `acl_groups` 없으면 권한 필터를, `valid_to` 없으면 최신성을,
   `source_uri` 없으면 출처 표시를, `content_hash` 없으면 증분 인덱싱을 할 수 없다 (7절)
