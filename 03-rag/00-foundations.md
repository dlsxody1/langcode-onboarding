# 기초 — 벡터 · 임베딩 · 코사인 유사도

이후 문서는 "청크를 임베딩해서 코사인 유사도로 검색한다"를 **당연한 전제**로 깔고 간다.
이 문서는 그 한 문장을 끝까지 풀어 쓴다. 고등학교 수학(좌표, 피타고라스) 이상은 필요 없다.

---

## 1. 벡터 — 그냥 숫자 배열이다

```ts
const v = [0.9, 0.1, 0.0];   // 3차원 벡터
```

프론트엔드에서 매일 쓰는 `number[]` 와 똑같다. 다만 **"공간 위의 한 점(또는 화살표)"으로 본다**는 게 다르다.
`[0.9, 0.1, 0.0]` 은 원점에서 x 축으로 0.9, y 축으로 0.1 만큼 간 곳을 가리키는 화살표다.

벡터에는 두 가지 성질이 있다.

| 성질 | 뜻 | 계산 |
| --- | --- | --- |
| **크기 (길이, norm)** | 화살표가 얼마나 긴가 | `√(x² + y² + z²)` — 피타고라스 |
| **방향** | 화살표가 어디를 가리키나 | 크기로 나눠서 길이 1 로 만든 것 |

**RAG 에서 "의미"는 방향에 담긴다.** 이게 이 문서 전체의 결론이고, 아래는 전부 그 이유다.

---

## 2. 임베딩 — 텍스트를 "의미의 좌표"로 바꾸기

**임베딩 = 텍스트를 넣으면 고정 길이 벡터가 나오는 함수.**

```
embed("연차휴가는 15일을 부여한다")  →  [0.012, -0.034, 0.051, ... ]   (1536개)
embed("노트북 디스크를 암호화한다")  →  [-0.041, 0.007, 0.022, ... ]   (1536개)
```

글이 한 줄이든 한 페이지든 **항상 같은 길이**(모델이 정한 차원 수)의 배열이 나온다.

### 장난감 예시 — 축 3개짜리 세계

이해를 위해 축이 3개뿐이고, 각 축에 이름이 붙어 있다고 **가정**해 보자.

| | 휴가 축 | 근무 축 | 보안 축 |
| --- | ---: | ---: | ---: |
| A. "연차휴가는 15일을 부여한다" | 0.9 | 0.1 | 0.0 |
| B. "반차는 오전·오후 단위로 쓴다" | 0.8 | 0.3 | 0.0 |
| C. "노트북은 디스크 전체를 암호화한다" | 0.0 | 0.1 | 0.9 |
| **질문.** "휴가 며칠 쓸 수 있어?" | 0.85 | 0.15 | 0.05 |

A·B·질문은 모두 "휴가 축" 쪽을 가리키고, C 만 "보안 축" 쪽을 가리킨다.
**검색이란 질문 화살표와 방향이 가장 비슷한 문서 화살표를 찾는 일이다.**

### 진짜 임베딩은 축에 이름이 없다 ⚠️

위 표는 설명용 거짓말이다. 실제 1536차원 벡터에서 **"37번째 숫자 = 휴가 정도" 같은 해석은 불가능하다.**
의미는 특정 축 하나가 아니라 **1536개 숫자의 조합(=방향) 전체**에 흩어져 있다.
그래서 벡터를 눈으로 봐서는 아무것도 알 수 없고, **다른 벡터와 비교할 때만** 의미가 생긴다.

### 모델은 이 좌표를 어떻게 배웠나

임베딩 모델은 대량의 **(비슷한 문장 쌍, 무관한 문장 쌍)** 으로 학습된다.
"비슷한 쌍은 방향을 가깝게, 무관한 쌍은 멀게" 를 수억 번 반복하면
"신규 입사자" 와 "새로 들어온 사람" 이 공간에서 가까운 곳에 놓이게 된다(대조 학습, contrastive learning).

**그래서 임베딩 모델의 품질 = "무엇을 가깝다고 배웠는가"** 다.
한국어 구어·문어 쌍을 많이 본 모델은 한국어 규정 검색을 잘하고, 아니면 못한다.
`02-chunking-embedding.md` 6절에서 "한국어 성능은 모델마다 편차가 크다"고 하는 이유가 이것이다.

### 희소 벡터 vs 밀집 벡터

실습(`labs/lab2-mini-rag`)의 기본 임베딩은 진짜 모델이 아니라 **TF-IDF** 다. 둘은 생김새부터 다르다.

| | TF-IDF (희소, sparse) | 임베딩 모델 (밀집, dense) |
| --- | --- | --- |
| 차원 | 코퍼스의 단어 수만큼 (수만 개) | 고정 (768 / 1536 / 3072) |
| 값 | 대부분 0. 등장한 단어 자리만 값이 있다 | 거의 모든 칸에 값이 있다 |
| 축의 의미 | **있다** — 축 하나 = 단어(토큰) 하나 | 없다 |
| "가깝다"의 뜻 | **같은 글자가 겹친다** | **의미가 비슷하다** |
| 실습 코드 | `{"휴가": 0.31, "연차": 0.22}` 같은 dict | `[0.012, -0.034, ...]` |

TF-IDF 는 "축 = 단어"인 벡터다. 그래서 질문과 문서에 **같은 단어가 없으면 내적이 0** 이 된다.
`02-chunking-embedding.md` 5-2절의 "새로 들어온 사람도 집에서 일할 수 있나요?" 가 실패한 게 정확히 이것이다.

## 3. 코사인 유사도 — 두 화살표 사이의 각도

### 정의

```
                 A · B              (내적)
cos(θ) = ─────────────────
             |A| × |B|          (크기의 곱)
```

- **내적 `A · B`** : 같은 자리끼리 곱해서 전부 더한 것. `a₁b₁ + a₂b₂ + a₃b₃ + ...`
- **크기 `|A|`** : `√(a₁² + a₂² + ...)`
- 크기로 나누는 이유: **길이의 영향을 지우고 방향(각도)만 남기기 위해서**

결과값의 의미:

| 값 | 각도 | 뜻 |
| ---: | ---: | --- |
| 1 | 0° | 완전히 같은 방향 |
| 0 | 90° | 무관 (직각) |
| -1 | 180° | 정반대 |

### 손으로 한 번 계산해 보기

위 장난감 예시에서 **질문 q = [0.85, 0.15, 0.05]** 와 **A = [0.9, 0.1, 0.0]**:

```
① 내적     q·A = 0.85×0.9 + 0.15×0.1 + 0.05×0.0
                = 0.765    + 0.015    + 0
                = 0.780

② 크기     |q| = √(0.85² + 0.15² + 0.05²) = √0.7475 ≈ 0.8646
           |A| = √(0.9²  + 0.1²  + 0.0²)  = √0.82   ≈ 0.9055

③ 코사인   0.780 / (0.8646 × 0.9055) ≈ 0.996
```

나머지도 같은 방식으로 계산하면:

| 문서 | 코사인 유사도 | 순위 |
| --- | ---: | ---: |
| A. 연차휴가 15일 | **0.996** | 1 |
| B. 반차 단위 | 0.981 | 2 |
| C. 노트북 암호화 | 0.077 | 3 |

**이게 벡터 검색의 전부다.** 모든 청크와 코사인을 계산하고, 큰 순서로 k 개를 자른다(top-k).
(청크가 100만 개면 전부 계산하기엔 느려서 근사 탐색을 쓴다 → `01-pipeline.md` 의 ANN·HNSW)

### 왜 "거리"가 아니라 "각도"인가

두 점 사이의 직선 거리(유클리드 거리)를 쓰면 안 될까? 예를 보면 바로 보인다.

| 비교 | 코사인 | 유클리드 거리 |
| --- | ---: | ---: |
| `[1, 1]` vs `[3, 3]` (같은 방향, 길이만 3배) | **1.000** | 2.828 (멀다) |
| `[1, 1]` vs `[1, 0]` (방향이 45° 다름) | 0.707 | **1.000** (가깝다) |

거리로 보면 **방향이 다른 쪽이 더 가깝다**고 나온다. 의미 검색에서는 틀린 답이다.

TF-IDF 처럼 길이가 단어 수에 따라 변하는 벡터에서 이게 특히 문제가 된다.
"휴가" 를 한 번 쓴 짧은 문서와 열 번 쓴 긴 문서는 **주제(방향)는 같고 길이만 다르다.**
코사인은 둘을 같게 보고, 거리는 다르게 본다. **우리가 원하는 건 주제가 같은지다.**

### 정규화하면 내적 = 코사인

벡터를 미리 **길이 1 로 만들어 두면**(정규화, normalize) 분모가 `1 × 1 = 1` 이 되어
**코사인 유사도 = 그냥 내적** 이 된다. 실습 코드가 정확히 이렇게 한다.

```python
# labs/lab2-mini-rag/minirag.py — TfidfEmbedder
def embed(self, text):
    ...
    norm = math.sqrt(sum(v * v for v in vec.values())) or 1.0   # ② 크기
    return {k: v / norm for k, v in vec.items()}                # 길이 1 로

@staticmethod
def cosine(a, b):
    # 이미 정규화돼 있으므로 내적 = 코사인 유사도
    return sum(v * b.get(k, 0.0) for k, v in a.items())          # ① 내적만
```

**인덱싱할 때 한 번 나눠 두면, 질문마다 하는 계산은 곱셈·덧셈뿐이다.** 대부분의 Vector DB 가 이렇게 최적화한다.
참고로 OpenAI 임베딩은 **처음부터 길이 1 로 나온다.** 그래서 코사인·내적·유클리드 거리 중 무엇으로 정렬해도 순위가 같다.

### pgvector 에서 `<=>` 는 "거리"다

`01-pipeline.md` 의 SQL 에 이런 줄이 있다.

```sql
ORDER BY embedding <=> :q LIMIT 20;
```

| 연산자 | 뜻 | 정렬 |
| --- | --- | --- |
| `<=>` | **코사인 거리** = `1 - 코사인 유사도` | 작을수록 비슷 → `ASC` |
| `<#>` | 음의 내적 (`-(A·B)`) | 작을수록 비슷 → `ASC` |
| `<->` | 유클리드 거리 | 작을수록 비슷 → `ASC` |

"유사도"(클수록 비슷)와 "거리"(작을수록 비슷)를 헷갈리면 **정렬 방향이 뒤집혀 가장 무관한 문서가 1등**으로 나온다.
화면에 점수를 띄울 때도 지금 숫자가 유사도인지 거리인지 먼저 확인한다.
그리고 인덱스(`vector_cosine_ops`)와 연산자(`<=>`)는 **짝이 맞아야** 인덱스를 탄다.

## 4. 점수 읽는 법 — "0.8 이면 좋은 건가?"

**절대 기준은 없다.** 코사인 값의 분포는 임베딩 방식과 모델마다 완전히 다르다.

| 임베딩 | 점수가 생기는 모양 |
| --- | --- |
| TF-IDF (실습) | 글자가 안 겹치면 0. 잘 맞은 검색이 보통 0.3 이상. 실습에서 실패한 검색의 1등이 **0.114** 였다 |
| 밀집 임베딩 모델 | 음수는 드물고, **무관한 문장끼리도 꽤 높게** 나오는 경우가 많다. 범위가 좁게 몰린다 |

그래서 실무 규칙은 이렇다.

1. **순위는 믿고, 절대값은 믿지 않는다.** 같은 모델 안에서 "A 가 B 보다 비슷하다"는 믿을 만하다
2. **임계값은 측정해서 정한다.** 평가셋에서 "맞은 검색의 1등 점수"와 "틀린 검색의 1등 점수" 분포를 그려 보고 그 사이에 선을 긋는다
3. **모델을 바꾸면 임계값도 다시 잡는다.** 점수 분포 자체가 바뀌기 때문이다

이 임계값이 `04-enterprise-rag.md` 에서 말하는 **"관련 문서를 찾지 못했습니다" UX 의 기준선**이 된다.

## 5. 청킹이 왜 필요한지 — 벡터로 다시 보기

`02-chunking-embedding.md` 1절은 "긴 텍스트를 벡터 하나로 만들면 의미가 뭉개진다"고 말한다.
장난감 예시로 숫자를 직접 보자.

휴가 조항 A 와 보안 조항 C 가 **한 청크로 붙어 있다**고 하자.
청크의 벡터는 대략 두 내용의 평균 방향이 된다.

```
A       = [0.90, 0.10, 0.00]   (휴가)
C       = [0.00, 0.10, 0.90]   (보안)
A+C 청크 ≈ [0.45, 0.10, 0.45]   (둘의 평균)
```

| 질문 "휴가 며칠?" 과의 코사인 | 값 |
| --- | ---: |
| 휴가 조항만 따로 자른 청크 A | **0.996** |
| 휴가 + 보안이 섞인 청크 | 0.754 |

내용(A)은 그대로 들어 있는데 **점수가 0.996 → 0.754 로 떨어졌다.** 섞인 보안 내용이 방향을 끌어당겼기 때문이다.
청크 수가 수만 개면, 이 정도 차이로도 정답 청크는 top-k 밖으로 밀려난다.

**이게 "검색 희석"의 정체다.**
그리고 반대로 너무 잘게 자르면 청크 하나에 의미가 모자라 방향이 불분명해진다.
**한 청크 = 한 주제** 가 되도록 자르라는 말(구조 기반 청킹)은 결국 **"화살표가 한 방향만 가리키게 하라"** 는 뜻이다.

## 6. 정리 — 한 장으로

```
텍스트 ──embed()──▶ 벡터 (고정 길이 숫자 배열)
                     │
                     ├─ 의미는 "방향"에 있다. 축 하나하나는 해석 불가
                     ├─ 길이 1 로 정규화해 두면 코사인 = 내적
                     │
질문 ──embed()──▶ 벡터 ──▶ 모든 청크와 코사인 계산 ──▶ 큰 순서로 top-k
                                     (실제로는 HNSW 로 근사)
```

| 개념 | 한 줄 |
| --- | --- |
| 벡터 | 숫자 배열 = 공간 위의 화살표 |
| 임베딩 | 텍스트 → 의미가 비슷하면 방향이 비슷한 벡터 |
| 코사인 유사도 | 두 화살표 사이 각도의 cos. 1 같음 · 0 무관 |
| 정규화 | 길이를 1 로. 그러면 코사인 = 내적 |
| 코사인 거리 | `1 - 유사도`. pgvector `<=>`. 작을수록 비슷 |
| 희소 vs 밀집 | 글자가 겹쳐야 가까움 vs 의미가 비슷하면 가까움 |
| 검색 희석 | 여러 주제를 섞은 청크는 방향이 평균이 되어 어느 질문과도 애매해진다 |
