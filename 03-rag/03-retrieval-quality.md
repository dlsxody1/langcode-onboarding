# 검색 품질

**RAG 실패의 대부분은 검색 실패다.** 여기를 고치는 방법들.

순서는 이렇다. 1절은 검색을 두 가지로 돌려 합치는 하이브리드, 2절은 가져온 결과를 다시 줄 세우는 리랭킹, 3절은 질문 쪽을 손보는 기법이다.
4절은 이 모든 개선이 정말 효과가 있는지 재는 평가 방법이다. 5절은 무엇부터 할지 정리한 우선순위다.

---

## 1. 하이브리드 검색

하이브리드 검색(hybrid search)은 키워드 검색과 벡터 검색을 둘 다 돌리고 결과를 합치는 방식이다.

### 두 검색은 실패 유형이 다르다

| | BM25 (키워드) | 벡터 |
| --- | --- | --- |
| 원리 | 단어 빈도 · 희귀도 | 의미 벡터 거리 |
| 이기는 질문 | 고유명사, 제품코드, 사번, 정확한 용어 | 동의어, 풀어 쓴 질문, 개념적 질문 |
| 지는 질문 | 다른 단어로 표현된 같은 개념 | 의미 없는 식별자 (`SKU-4821`) |

**둘을 섞으면 각자의 실패를 서로 메운다.** 실무에서 하이브리드가 기본값인 이유.

`SKU-4821` 이 벡터 검색에 약한 이유는 이 코드에 "의미"랄 것이 없기 때문이다.
임베딩 모델 입장에서 `SKU-4821` 과 `SKU-4812` 는 거의 같은 방향의 벡터가 된다. 둘 다 "어떤 제품 코드"일 뿐이다.
반대로 BM25 는 `4821` 이라는 글자가 정확히 들어간 청크만 높게 친다.

### BM25 — 키워드 검색의 표준 점수

BM25 는 질문의 단어가 문서에 얼마나 들어 있는지로 점수를 매기는 알고리즘이다. `00-foundations.md` 의 TF-IDF 를 실무용으로 다듬은 것이라고 보면 된다.
질문의 단어마다 아래 세 가지를 따져 점수를 내고 전부 더한다.

| 요소 | 뜻 | 왜 필요한가 |
| --- | --- | --- |
| IDF (희귀도) | 그 단어가 전체 문서 중 몇 개에 나오나. 드물수록 크다 | "있나요"처럼 어디에나 있는 말은 구분에 쓸모가 없다 |
| TF (빈도) + 포화 | 이 문서에 몇 번 나오나. 단, 많이 나올수록 증가폭이 줄어든다 | 같은 단어를 10번 반복한 문서가 10배 관련 있지는 않다 |
| 길이 보정 | 긴 문서는 점수를 조금 깎는다 | 긴 문서는 단어가 우연히 들어갈 확률이 높다 |

TF 포화가 BM25 의 핵심 개선이다. 실습 코드의 기본값(`k1 = 1.5`)으로 길이 보정을 빼고 계산하면 이렇다.

| 이 문서에서 "연차"가 나온 횟수 | TF-IDF 식 단순 비례 | BM25 의 TF 부분 `tf × (k1+1) / (tf + k1)` |
| ---: | ---: | ---: |
| 1 | 1 | 1.00 |
| 2 | 2 | 1.43 |
| 10 | 10 | 2.17 |

단순 비례라면 10번 나온 문서가 10배 점수를 받는다. BM25 에서는 2배 남짓에 그친다. 아무리 반복해도 `k1 + 1 = 2.5` 를 넘지 못한다.
`k1` 은 포화 속도를, `b`(기본 0.75)는 길이 보정을 얼마나 세게 걸지 정한다. 대부분 기본값을 그대로 쓴다.

### RRF (Reciprocal Rank Fusion) — 점수 합치는 표준 방법

문제: BM25 점수(0\~30 아무 범위)와 코사인 유사도(0\~1)를 그냥 더할 수 없다.
BM25 점수 12.4 와 코사인 0.82 를 더하면 BM25 쪽이 결과를 거의 혼자 정한다. 정규화(둘 다 0\~1 로 늘리고 줄이기)를 해도 두 점수의 분포 모양이 달라 공정하지 않다.

RRF 는 **점수 대신 순위만 쓴다.** 각 검색기에서 받은 순위로 `1 / (k + 순위)` 를 계산해 더한다.

```python
def rrf(rankings: list[list[str]], k: int = 60) -> dict[str, float]:
    """rankings: 각 검색기의 결과 id 리스트 (순위 순)"""
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return dict(sorted(scores.items(), key=lambda x: -x[1]))
```

#### 손으로 계산해 보기

벡터 검색과 BM25 가 각각 3개씩 돌려줬다고 하자.

```
벡터 검색 순위:  1. A   2. B   3. C
BM25 순위:      1. C   2. A   3. D
```

| 청크 | 벡터 기여 | BM25 기여 | RRF 합계 | 최종 순위 |
| --- | ---: | ---: | ---: | ---: |
| A | 1/61 = 0.01639 | 1/62 = 0.01613 | **0.03252** | 1 |
| C | 1/63 = 0.01587 | 1/61 = 0.01639 | **0.03227** | 2 |
| B | 1/62 = 0.01613 | — | 0.01613 | 3 |
| D | — | 1/63 = 0.01587 | 0.01587 | 4 |

A 와 C 는 양쪽 모두에 나왔기 때문에 한쪽에만 나온 B·D 보다 확실히 위로 올라간다. 벡터에서 3등이던 C 가 최종 2등이 됐다.

- 점수 정규화가 필요 없다 (순위만 보므로)
- 둘 다에서 상위인 문서가 강하게 올라간다
- `k=60` 이 관례적 기본값 — 1위와 2위의 차이를 완만하게 만든다

`k` 의 효과도 숫자로 보면 분명하다. `k=0` 이면 1위가 1/1 = 1.0, 2위가 1/2 = 0.5 로 두 배 차이다. 한 검색기의 1등이 결과를 거의 혼자 정한다.
`k=60` 이면 1/61 과 1/62 로 차이가 2% 도 안 된다. 그래서 "한쪽에서 1등"보다 "양쪽에서 고르게 상위"가 이긴다.

> 가중치를 주고 싶으면 `w / (k + rank)` 로 검색기별 `w` 를 둔다.
> 사내 규정처럼 용어가 정형화된 도메인은 BM25 가중치를 높이는 게 나을 수 있다.

가중치를 질문 유형에 따라 바꾸는 방법도 있다. 질문이 `SKU-4821`, `v4.2`, 사번처럼 식별자 모양이면 BM25 쪽 가중치를 올리고,
"집에서 일하고 싶은데 어떻게 해요?"처럼 풀어 쓴 문장이면 벡터 쪽을 올린다. 모든 질문을 한 가지 전략으로 처리하지 않고 유형별로 갈라 보내는 것을 쿼리 라우팅(query routing)이라고 한다.
정규식 같은 간단한 규칙으로 시작해도 된다. 효과는 평가셋으로 확인한다(4절).

### 한국어 BM25 의 함정

한국어는 교착어라 **"휴가를 / 휴가는 / 휴가가"가 전부 다른 토큰**이 된다.
PostgreSQL 의 기본 `to_tsvector('simple', ...)` 는 이걸 처리 못 한다.

대응:
- 형태소 분석기 (mecab-ko, Kiwi) 로 토크나이징
- Elasticsearch/OpenSearch 의 **nori** 애널라이저
- 간이 대안: n-gram (bigram/trigram) 인덱싱 — 정확도는 떨어지지만 형태소 분석기 없이 동작

n-gram 은 글자를 n 개씩 겹쳐 자른 조각이다. "휴가를"의 bigram(2글자 조각)은 "휴가", "가를"이다.
"휴가는"도 "휴가"를 만들어 내므로 조사가 달라도 "휴가" 조각으로 서로 매칭된다. 실습 코드의 토크나이저가 이 방식이다.

> ❓ 입사 후 확인: 키워드 검색을 어떻게 구현하고 있나? PG full-text? Elasticsearch? Azure AI Search?
> (Azure AI Search 는 하이브리드 + 한국어 애널라이저 + 시맨틱 랭커를 다 제공한다. MS 파트너라면 유력)

## 2. 리랭킹

리랭킹(reranking)은 1차 검색으로 넓게 가져온 후보를 더 정교한 모델로 다시 채점해 순서를 바꾸는 단계다.

### 왜 필요한가

벡터 검색의 유사도는 **"대체로 관련 있음"** 까지만 판단한다.
질문과 청크를 각각 따로 벡터로 만들어 비교하기 때문에, 둘 사이의 미세한 관계를 못 본다.

이렇게 질문과 문서를 따로따로 인코딩(벡터로 변환)하는 구조를 bi-encoder 라고 한다. 지금까지 본 임베딩 검색이 전부 이 구조다.
따로 만들기 때문에 문서 벡터를 미리 계산해 저장해 둘 수 있어서 빠르다. 대신 질문을 보지 않은 채로 문서를 요약한 셈이라 세부 관계를 놓친다.

예를 들어 "입사 1년 미만 연차"라는 질문에 bi-encoder 는 "연차" 이야기를 하는 청크를 전부 비슷하게 높이 친다.
"1년 미만"이라는 조건에 딱 맞는 "1개월 개근 시 1일 부여" 조항과 일반적인 "15일 부여" 조항을 잘 구분하지 못한다.

**Cross-encoder 리랭커**는 (질문, 청크) 쌍을 **함께** 모델에 넣어 관련도를 점수화한다.
질문의 "1년 미만"과 청크의 "1개월 개근"을 한 번에 읽고 비교하므로 훨씬 정확하다.
하지만 쌍마다 모델을 새로 돌려야 하고 미리 계산해 둘 수도 없어서 훨씬 느리다. 그래서 전체에 못 쓰고 **2단계**로 쓴다.

```
bi-encoder    : embed(질문) ─┐
                             ├─ 코사인 → 점수     (문서 벡터는 미리 계산해 둠)
                embed(청크) ─┘

cross-encoder : model(질문 + 청크) → 점수         (쌍마다 매번 계산)
```

```
① 1차 검색 (빠름)   : 하이브리드로 top-50 을 넓게 가져온다
② 리랭킹 (정확)     : cross-encoder 로 50개를 재채점 → top-5 만 남긴다
③ 프롬프트          : 5개만 넣는다
```

청크가 100만 개일 때 cross-encoder 로 전부 채점하면 질문 하나에 모델을 100만 번 돌려야 한다.
1차 검색으로 50개로 줄인 다음에 쓰면 50번이면 된다.

### 효과

- **k 를 줄일 수 있다** → 노이즈 감소 + 토큰 비용 감소
- 1차 검색에서 20위였던 진짜 정답이 1위로 올라온다

1차 검색 결과를 순서 그대로 프롬프트에 넣는 것은 흔한 실수로 꼽힌다. 1차 검색은 "후보를 빠짐없이 모으는" 단계이지 순서를 믿을 단계가 아니다.

### 선택지

| | 비고 |
| --- | --- |
| Cohere Rerank | API. 다국어 지원. 간단 |
| BGE-reranker-v2-m3 | 오픈소스. 한국어 괜찮음. 온프레미스 가능 |
| Azure AI Search 시맨틱 랭커 | Azure 스택이면 통합이 쉬움 |
| **LLM 리랭킹** | GPT/Claude 에게 "이 10개 중 관련 순서를 매겨라". 느리고 비싸지만 별도 인프라 불필요 |

**비용 감각:** 리랭킹은 질의마다 발생한다. 50개를 재채점하면 그만큼 지연이 붙는다(보통 100\~300ms).
"검색 3초"가 되면 채팅 UX 가 무너지므로, top-N 을 얼마나 넓게 잡을지는 **지연 예산과의 협상**이다.

## 3. 쿼리 쪽 개선 — 가장 저렴한 개선

문서와 인덱스는 그대로 두고 질문만 손보는 기법들이다. 재인덱싱이 필요 없어 시도하기 쉽다.

### ① 대화 맥락 압축 (condensing)

```
[이전] 사용자: 연차가 며칠이야?  AI: 15일입니다.
[지금] 사용자: 그럼 반차는?
   ↓ LLM 으로 재작성
"회사의 반차 사용 규정"
```

**챗 RAG 에서 이거 하나로 체감 품질이 크게 바뀐다.** 안 하면 후속 질문이 전부 실패한다.

### ② 다중 쿼리 (Multi-query)

하나의 질문을 여러 표현으로 확장해서 각각 검색하고 결과를 합친다 (RRF 로).

```
"연차 이월되나요?"
 → "연차휴가 이월 규정"
 → "미사용 연차 다음 해 사용 가능 여부"
 → "휴가 소멸 시효"
```

검색 누락(recall) 을 줄인다. 대가는 검색 횟수 × N.
규정이 "이월"이 아니라 "소멸"이라는 단어로 쓰여 있어도, 세 번째 표현이 그 청크를 잡아 온다.

### ③ HyDE (Hypothetical Document Embeddings)

질문을 임베딩하는 대신, **LLM 에게 가상의 답변을 쓰게 해서 그 답변을 임베딩**한다.

이유: 질문("연차 며칠?")과 문서("제15조 연차휴가는 15일을 부여한다")는 **문체가 달라서**
벡터 공간에서 생각보다 멀다. 가상 답변은 문서와 문체가 비슷해서 더 잘 매칭된다.

```
질문     : "연차 며칠?"
   ↓ LLM 에게 "이 질문에 답하는 사내 규정 조항을 지어내라"
가상 답변 : "제○조(연차휴가) 사용자는 1년간 80% 이상 출근한 근로자에게 ○일의 유급휴가를 주어야 한다."
   ↓ 이 문장을 임베딩해서 검색
실제 문서 : "제15조 연차휴가는 ... 15일을 부여한다"   ← 문체가 비슷해 가깝게 잡힌다
```

가상 답변의 숫자가 틀려도 상관없다. 검색에만 쓰고 사용자에게 보여 주지 않기 때문이다. 필요한 건 "규정 조항처럼 생긴 문장"이라는 모양이다.

- ✅ 효과가 큰 경우가 있다
- ❌ LLM 호출이 하나 더 붙는다 (지연 + 비용), 가상 답변이 엉뚱하면 오히려 악화

### ④ 메타데이터 자동 추출

```
"작년 3분기 영업팀 실적 보고서에서 매출 추이"
   ↓ LLM 으로 필터 추출
{ department: "영업", doc_type: "실적보고서", period: "2025-Q3" }
   ↓
메타데이터로 범위를 좁힌 뒤 벡터 검색
```

검색 공간이 1/100 로 줄면 정확도가 극적으로 올라간다.
"작년", "3분기" 같은 조건은 벡터 유사도로는 잘 걸러지지 않는다. 2024년 3분기 보고서와 2025년 3분기 보고서는 내용이 비슷해 벡터도 비슷하다.
이런 조건은 `WHERE period = '2025-Q3'` 처럼 정확한 필터로 거는 편이 맞다.

## 4. 평가 — 안 하면 조용히 나빠진다

평가셋(evaluation set)은 "이 질문에는 이 청크가 정답"이라는 쌍을 모아 둔 시험지다.
청킹·모델·프롬프트를 바꿀 때마다 같은 시험지로 채점해 점수를 비교한다. 실습의 `eval.jsonl` 이 25문항짜리 평가셋이다.

### 두 층을 반드시 분리한다

| 층 | 질문 | 지표 |
| --- | --- | --- |
| **검색** | 정답이 들어 있는 청크가 top-k 에 들어왔나 | Recall@k, MRR, nDCG |
| **생성** | 찾아온 근거대로 답했나 / 질문에 답했나 | Faithfulness, Answer Relevance |

**분리하지 않으면 "답이 나쁘다"에서 멈춰 프롬프트만 계속 만지게 된다.**
검색 점수가 높은데 답이 나쁘면 생성 쪽 문제다. 검색 점수부터 낮으면 프롬프트를 아무리 고쳐도 소용없다.

### 지표 계산

```python
# Recall@k — 가장 중요하고 가장 쉽다
def recall_at_k(retrieved_ids, gold_ids, k):
    top = set(retrieved_ids[:k])
    return len(top & set(gold_ids)) / len(gold_ids)

# MRR — 정답이 몇 등으로 나왔는지 (1등이면 1.0, 5등이면 0.2)
def mrr(retrieved_ids, gold_ids):
    for rank, doc_id in enumerate(retrieved_ids, 1):
        if doc_id in gold_ids:
            return 1 / rank
    return 0.0
```

**Recall@k 부터 시작해라.** 이것만 측정해도 청킹·모델·하이브리드 실험을 비교할 수 있다.

#### 숫자로 보는 세 지표

**Recall@k** 는 "정답 청크 중 몇 개가 상위 k 개 안에 들어왔나"다.
정답 청크가 `c3`, `c7` 두 개인데 상위 5개가 `[c1, c3, c5, c9, c2]` 라면 정답 2개 중 1개만 들어왔으므로 Recall@5 = 0.5 다.
실습 코드는 더 단순하게 "정답 중 하나라도 top-k 에 있으면 1, 없으면 0"으로 채점하고 질문 전체의 평균을 낸다.
한 질문에 답할 수 있는 청크 하나만 찾아도 충분하다고 보는 정의다.

**MRR** 은 "첫 정답이 몇 등에 나왔나"를 점수로 바꾼 것이다. 질문마다 `1 / 순위` 를 구해 평균한다.

| 질문 | 첫 정답의 순위 | 1 / 순위 |
| --- | ---: | ---: |
| Q1 | 1 | 1.000 |
| Q2 | 3 | 0.333 |
| Q3 | 못 찾음 | 0 |
| **MRR** | | (1 + 0.333 + 0) / 3 ≈ **0.444** |

Recall@5 로는 Q1·Q2 가 똑같이 "성공"이지만 MRR 은 1등과 3등을 구분한다.

**nDCG** (normalized Discounted Cumulative Gain) 는 정답이 여러 개이고 "더 좋은 정답"과 "그럭저럭인 정답"이 있을 때 쓴다.
청크마다 관련도 등급(예: 3 = 완벽, 2 = 관련, 1 = 조금, 0 = 무관)을 매기고 아래 순위일수록 할인해서 더한다.
i 번째 청크의 점수는 `관련도 / log₂(i + 1)` 이다. 이 합을 DCG 라고 한다. 가장 이상적인 순서일 때의 DCG(IDCG)로 나누면 nDCG 다.

```
검색 결과의 관련도 순서:  [0, 3, 2, 1]
DCG  = 0/log₂2 + 3/log₂3 + 2/log₂4 + 1/log₂5
     = 0       + 1.893   + 1.000   + 0.431    = 3.324

이상적인 순서:          [3, 2, 1, 0]
IDCG = 3/1     + 2/1.585 + 1/2     + 0        = 4.762

nDCG = 3.324 / 4.762 ≈ 0.70
```

가장 좋은 청크를 1등이 아니라 2등에 놓았을 뿐인데 0.70 으로 떨어진다. 1.0 이면 완벽한 순서다.
등급을 매기는 손이 많이 가므로, 처음에는 Recall@k 와 MRR 로 충분하다(실습 과제 6 에 `nDCG@k` 구현이 있다).

#### 생성 지표 두 개

- **Faithfulness (충실성)**: 답변의 모든 주장이 근거 청크에서 확인되는가. 그라운딩이 지켜졌는지 재는 지표다
- **Answer Relevance (답변 관련성)**: 답변이 질문에 실제로 답하는가

둘은 따로 실패한다. 예를 들어 근거 청크에 "연차 15일, 3년 이상 근속 시 2년마다 1일 가산"만 있다고 하자.

| 질문 "연차 며칠이야?"에 대한 답변 | Faithfulness | Answer Relevance |
| --- | --- | --- |
| "15일이고, 3년 이상 근속하면 2년마다 1일씩 늘어납니다 [1]" | ✅ | ✅ |
| "15일이고, 최대 25일까지 늘어납니다" | ❌ "25일"은 근거에 없다 | ✅ |
| "반차는 4시간 단위로 쓸 수 있습니다 [2]" | ✅ (근거에 있다면) | ❌ 질문에 답하지 않았다 |

두 번째 답변은 일반 상식으로는 맞는 말일 수 있다. 그래도 근거에 없으므로 unfaithful 이다. RAG 에서는 "사실인가"보다 "근거에 있는가"를 먼저 본다.

### 평가셋 만들기 — 현실적인 방법

이상적으로는 사람이 질문-정답문서 쌍을 50\~200개 만든다. 현실에서는:

1. **실제 사용 로그에서** 자주 나오는 질문 30개를 뽑는다
2. **LLM 으로 합성** — 각 문서를 주고 "이 문서로만 답할 수 있는 질문 3개를 만들어라"
   → 그 문서가 자동으로 정답 레이블이 된다. **빠르게 수백 개를 만들 수 있다**
3. **사용자 👎 피드백** — 실패 사례가 가장 값진 평가 데이터다

> ②의 함정: LLM 이 만든 질문은 문서의 표현을 그대로 쓰는 경향이 있어 **실제보다 쉽다.**
> "다른 말로 바꿔 물어라"를 프롬프트에 넣고, 일부는 사람이 검수한다.

정답 레이블(gold label)은 "이 질문의 정답은 이 청크"라고 평가셋에 적어 둔 표시다. 실습에서는 `gold_phrases` 필드가 그 역할을 한다.

### 평가셋을 만들다가 실제로 저지른 실수 두 개

`labs/lab2-mini-rag` 의 평가셋을 만들면서 **둘 다 직접 겪었다.** 둘 다 흔하고, 둘 다 위험하다.

#### 실수 ① 정답을 하나로만 잡았다

처음에 이렇게 썼다.

```jsonl
{"question": "두 시간만 자리를 비우고 싶습니다", "gold_phrase": "반반차(2시간 단위)"}
```

평가를 돌리니 이 질문이 **모든 설정에서 실패**로 찍혔다. "TF-IDF 가 의미를 몰라서 그렇구나"라고
결론 내리기 직전에, 실제로 뭘 가져왔는지 확인해 봤다.

```
1. [0.2666] 인사팀FAQ.md / Q. 쉬는 날을 두 시간만 쓰고 싶어요.
            "반반차 제도가 있습니다. 2시간 단위로 쓸 수 있고 팀장님 사전 승인이 필요합니다."
```

**1등으로 정답을 가져왔다.** 사용자 질문에 완벽히 답하는 청크다.
실패한 건 검색이 아니라 **내 정답 레이블**이었다. 같은 질문에 답할 수 있는 청크가
규정(제17조)과 FAQ 두 군데 있는데, 나는 규정 쪽 문구 하나만 정답으로 등록해 뒀던 것이다.

```jsonl
// 고친 뒤
{"question": "두 시간만 자리를 비우고 싶습니다",
 "gold_phrases": ["반반차(2시간 단위)", "2시간 단위로 쓸 수 있고"]}
```

> **이걸 못 잡았으면 무슨 일이 일어났을까.**
> 있지도 않은 검색 문제를 고치려고 청킹을 바꾸고, 임베딩 모델을 갈아끼우고,
> 그래도 안 되니 리랭커를 붙였을 것이다. **멀쩡한 시스템을 며칠 동안 망가뜨리는 길이다.**
>
> 그래서 규칙: **평가가 실패했다고 보고하면, 고치기 전에 무엇을 가져왔는지 눈으로 먼저 본다.**
> 실패의 상당수는 시스템이 아니라 레이블이 틀린 것이다.

정답 문구는 **리스트로 받게 설계해라.** 한 질문에 답이 되는 문서는 대개 하나가 아니다.

#### 실수 ② k 를 코퍼스 크기에 비해 크게 잡았다

청킹 설정을 비교했더니 `800자 청크` 가 Recall@5 = **1.000** 으로 압도적 1위였다.
"큰 청크가 좋구나"라고 쓸 뻔했는데, 청크 수를 같이 보니 **전체가 5개**였다.

```
fixed 800/80 → 청크 5개.  k=5 로 검색 = 전부 다 가져오기.
```

**검색기가 아무 일도 안 해도 만점이 나오는 설정이었다.** k=1 로 낮추자 순위가 완전히 뒤집혔다.

| | Recall@5 | Recall@3 | **Recall@1** |
| --- | ---: | ---: | ---: |
| fixed 800 (5청크) | 1.000 | 1.000 | 0.600 |
| heading (21청크) | 0.960 | 0.800 | **0.600** |

청크가 4배 많은데 Recall@1 이 같다 = **실제 규모에서는 구조 기반이 이긴다는 신호.**

> **규칙: `k` 는 전체 청크 수에 비해 충분히 작아야 한다.**
> `k / 전체 청크 수` 가 1% 를 넘으면 그 평가는 의심해라.
> 그리고 **Recall 하나만 보지 말고 MRR 을 같이 봐라** — 순위 품질은 k 선택에 덜 민감하다.

1% 규칙을 실제 숫자에 대 보면 이렇다. 청크가 1만 개면 k=5 는 0.05% 라 문제없다. 위 실험은 5/5 = 100% 였다.

#### 그래서 평가셋 체크리스트

```
[ ] 정답이 여러 개일 수 있는 질문에 정답을 하나만 잡지 않았나
[ ] k 가 전체 청크 수에 비해 너무 크지 않나
[ ] Recall 만 보고 MRR 을 빠뜨리지 않았나
[ ] 질문이 문서의 표현을 그대로 베끼지 않았나 (실제보다 쉬워진다)
[ ] 실패로 찍힌 케이스를 눈으로 확인했나  ← 가장 중요
[ ] 답이 문서에 아예 없는 질문("모른다"가 정답인 질문)도 넣었나
```

마지막 항목이 자주 빠진다. **"모른다고 답해야 하는 질문"** 이 평가셋에 없으면,
아무거나 그럴듯하게 지어내는 시스템이 만점을 받는다.

### 생성 품질 (LLM-as-judge)

LLM-as-judge 는 다른 LLM 에게 채점을 맡기는 방법이다. 사람이 답변 수백 개를 일일이 읽는 대신 아래 같은 채점 프롬프트를 돌린다.

```
근거 문서: {chunks}
질문: {q}
답변: {a}

답변의 각 주장이 근거 문서에서 확인되는가?
확인 불가한 주장이 하나라도 있으면 "unfaithful".
JSON 으로: {"faithful": bool, "unsupported_claims": [...]}
```

- 심판 모델은 **생성 모델보다 같거나 좋은 것**을 쓴다
- 사람 평가와 얼마나 일치하는지 한 번은 대조해 봐야 신뢰할 수 있다
- 도구: **RAGAS**, TruLens, DeepEval, promptfoo

사람 대조는 예를 들어 답변 50개를 사람과 심판 모델이 각각 채점해 보고 몇 개에서 판정이 같은지 세는 식으로 한다.

### CI 에 넣기 — 이게 핵심

CI(Continuous Integration)는 코드가 바뀔 때마다 테스트를 자동으로 돌리는 파이프라인이다. 평가셋을 여기에 넣으면 검색 품질이 단위 테스트처럼 지켜진다.

```yaml
# 프롬프트나 청킹 설정이 바뀌면 평가셋을 돌린다
- run: python eval.py --dataset eval/golden.jsonl --threshold-recall5 0.85
```

**Recall@5 가 0.85 아래로 떨어지면 빌드 실패.**

> 이건 내가 이미 해본 일의 같은 형태다. i18n 번역 누락과 한글 잔존을 CI 에서 차단한 것,
> FSD 구조 위반을 커밋 훅에서 막은 것 — **"품질을 사람의 주의력이 아니라 파이프라인으로 고정한다"**.
> RAG 품질에 이걸 적용하는 팀은 아직 많지 않다. **들어가서 제안할 수 있는 지점이다.**

## 6. 디버깅 체크리스트

답이 이상할 때 순서대로 확인한다.

```
[ ] 1. top-k 청크를 로그로 출력했나? (안 했으면 여기부터)
[ ] 2. 정답이 든 청크가 top-k 안에 있나?
        없다 → 검색 문제 (3~6번)
        있다 → 생성 문제 (7~9번)
[ ] 3. 그 청크가 인덱스에 존재하긴 하나? (인덱싱 실패/누락)
[ ] 4. 청킹 경계에서 잘렸나? 원문을 직접 확인
[ ] 5. 키워드로는 찾히나? (찾히면 → 하이브리드 도입)
[ ] 6. 쿼리가 대화 맥락 없이 들어갔나? (후속 질문 문제)
[ ] 7. 청크가 프롬프트의 가운데 묻혔나? (lost in the middle)
[ ] 8. 컨텍스트 길이를 초과해 잘렸나?
[ ] 9. 프롬프트가 "모른다고 답해도 된다"를 허용하나?
```

**1번을 위한 도구를 만드는 게 프론트엔드가 팀에 기여할 수 있는 가장 큰 일 중 하나다.**
내부 디버그 화면에서 질문 → top-k 청크 + 점수 + 최종 프롬프트를 볼 수 있으면,
백엔드·ML 사람들이 매번 로그를 뒤지지 않아도 된다.

앞 절들에서 흩어져 나온 실수를 한곳에 모았다. 리뷰나 설계 회의에서 이 목록과 대조해 보면 된다.

| 안티패턴 | 왜 문제인가 | 대신 할 것 |

| 벡터 검색만 쓴다 | 제품코드·사번·약어를 못 찾는다 | 하이브리드 + RRF (1절) |
| 메타데이터 필터 없이 전체에서 찾는다 | 권한 밖·기간 밖 문서가 섞인다 | 검색 전에 `WHERE` 로 범위를 좁힌다 |
| 1차 검색 결과를 그대로 넣는다 | 순서가 부정확하고 k 가 커진다 | 리랭킹 후 k 를 줄인다 (2절) |
| 컨텍스트를 꽉 채운다 | 관련 낮은 청크가 오답의 근거가 된다 | 점수 임계값 밑은 버린다 |
| 답변 품질만 본다 | 검색 문제인지 생성 문제인지 모른다 | 검색 지표와 생성 지표를 따로 잰다 (4절) |
| 문서가 바뀌어도 임베딩을 그대로 둔다 | 폐지된 규정·삭제된 문서로 답한다 | 증분 인덱싱 + 삭제 처리 (`02-chunking-embedding.md` 8절) |
| 모든 질문을 한 전략으로 처리한다 | 식별자 질문과 서술형 질문은 강한 검색기가 다르다 | 쿼리 라우팅 · 가중치 조절 (1절) |
| 평가 없이 "잘 되는 것 같다"로 간다 | 조용히 나빠진다 | 평가셋 + CI (4절) |
