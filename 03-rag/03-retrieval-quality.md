# 검색 품질

**RAG 실패의 대부분은 검색 실패다.** 여기를 고치는 방법들.

---

## 1. 하이브리드 검색

### 두 검색은 실패 유형이 다르다

| | BM25 (키워드) | 벡터 |
| --- | --- | --- |
| 원리 | 단어 빈도 · 희귀도 | 의미 벡터 거리 |
| 이기는 질문 | 고유명사, 제품코드, 사번, 정확한 용어 | 동의어, 풀어 쓴 질문, 개념적 질문 |
| 지는 질문 | 다른 단어로 표현된 같은 개념 | 의미 없는 식별자 (`SKU-4821`) |

**둘을 섞으면 각자의 실패를 서로 메운다.** 실무에서 하이브리드가 기본값인 이유.

### RRF (Reciprocal Rank Fusion) — 점수 합치는 표준 방법

문제: BM25 점수(0~30 아무 범위)와 코사인 유사도(0~1)를 그냥 더할 수 없다.

RRF 는 **점수 대신 순위만 쓴다.**

```python
def rrf(rankings: list[list[str]], k: int = 60) -> dict[str, float]:
    """rankings: 각 검색기의 결과 id 리스트 (순위 순)"""
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return dict(sorted(scores.items(), key=lambda x: -x[1]))
```

- 점수 정규화가 필요 없다 (순위만 보므로)
- 둘 다에서 상위인 문서가 강하게 올라간다
- `k=60` 이 관례적 기본값 — 1위와 2위의 차이를 완만하게 만든다

> 가중치를 주고 싶으면 `w / (k + rank)` 로 검색기별 `w` 를 둔다.
> 사내 규정처럼 용어가 정형화된 도메인은 BM25 가중치를 높이는 게 나을 수 있다.

### 한국어 BM25 의 함정

한국어는 교착어라 **"휴가를 / 휴가는 / 휴가가"가 전부 다른 토큰**이 된다.
PostgreSQL 의 기본 `to_tsvector('simple', ...)` 는 이걸 처리 못 한다.

대응:
- 형태소 분석기 (mecab-ko, Kiwi) 로 토크나이징
- Elasticsearch/OpenSearch 의 **nori** 애널라이저
- 간이 대안: n-gram (bigram/trigram) 인덱싱 — 정확도는 떨어지지만 형태소 분석기 없이 동작

> ❓ 입사 후 확인: 키워드 검색을 어떻게 구현하고 있나? PG full-text? Elasticsearch? Azure AI Search?
> (Azure AI Search 는 하이브리드 + 한국어 애널라이저 + 시맨틱 랭커를 다 제공한다. MS 파트너라면 유력)

## 2. 리랭킹

### 왜 필요한가

벡터 검색의 유사도는 **"대체로 관련 있음"** 까지만 판단한다.
질문과 청크를 각각 따로 벡터로 만들어 비교하기 때문에, 둘 사이의 미세한 관계를 못 본다.

**Cross-encoder 리랭커**는 (질문, 청크) 쌍을 **함께** 모델에 넣어 관련도를 점수화한다.
훨씬 정확하지만 훨씬 느리다 — 그래서 전체에 못 쓰고 **2단계**로 쓴다.

```
① 1차 검색 (빠름)   : 하이브리드로 top-50 을 넓게 가져온다
② 리랭킹 (정확)     : cross-encoder 로 50개를 재채점 → top-5 만 남긴다
③ 프롬프트          : 5개만 넣는다
```

### 효과

- **k 를 줄일 수 있다** → 노이즈 감소 + 토큰 비용 감소
- 1차 검색에서 20위였던 진짜 정답이 1위로 올라온다

### 선택지

| | 비고 |
| --- | --- |
| Cohere Rerank | API. 다국어 지원. 간단 |
| BGE-reranker-v2-m3 | 오픈소스. 한국어 괜찮음. 온프레미스 가능 |
| Azure AI Search 시맨틱 랭커 | Azure 스택이면 통합이 쉬움 |
| **LLM 리랭킹** | GPT/Claude 에게 "이 10개 중 관련 순서를 매겨라". 느리고 비싸지만 별도 인프라 불필요 |

**비용 감각:** 리랭킹은 질의마다 발생한다. 50개를 재채점하면 그만큼 지연이 붙는다(보통 100~300ms).
"검색 3초"가 되면 채팅 UX 가 무너지므로, top-N 을 얼마나 넓게 잡을지는 **지연 예산과의 협상**이다.

## 3. 쿼리 쪽 개선 — 가장 저렴한 개선

### ① 대화 맥락 압축 (condensing)

```
[이전] 사용자: 연차가 며칠이야?  AI: 15일입니다.
[지금] 사용자: 그럼 반차는?
   ↓ LLM 으로 재작성
"회사의 반차 사용 규정"
```

**챗 RAG 에서 이거 하나로 체감 품질이 크게 바뀐다.** 안 하면 후속 질문이 전부 실패한다.

### ② 다중 쿼리 (Multi-query)

하나의 질문을 여러 표현으로 확장해서 각각 검색하고 결과를 합친다 (RRF 로).

```
"연차 이월되나요?"
 → "연차휴가 이월 규정"
 → "미사용 연차 다음 해 사용 가능 여부"
 → "휴가 소멸 시효"
```

검색 누락(recall) 을 줄인다. 대가는 검색 횟수 × N.

### ③ HyDE (Hypothetical Document Embeddings)

질문을 임베딩하는 대신, **LLM 에게 가상의 답변을 쓰게 해서 그 답변을 임베딩**한다.

이유: 질문("연차 며칠?")과 문서("제15조 연차휴가는 15일을 부여한다")는 **문체가 달라서**
벡터 공간에서 생각보다 멀다. 가상 답변은 문서와 문체가 비슷해서 더 잘 매칭된다.

- ✅ 효과가 큰 경우가 있다
- ❌ LLM 호출이 하나 더 붙는다 (지연 + 비용), 가상 답변이 엉뚱하면 오히려 악화

### ④ 메타데이터 자동 추출

```
"작년 3분기 영업팀 실적 보고서에서 매출 추이"
   ↓ LLM 으로 필터 추출
{ department: "영업", doc_type: "실적보고서", period: "2025-Q3" }
   ↓
메타데이터로 범위를 좁힌 뒤 벡터 검색
```

검색 공간이 1/100 로 줄면 정확도가 극적으로 올라간다.

## 4. 평가 — 안 하면 조용히 나빠진다

### 두 층을 반드시 분리한다

| 층 | 질문 | 지표 |
| --- | --- | --- |
| **검색** | 정답이 들어 있는 청크가 top-k 에 들어왔나 | Recall@k, MRR, nDCG |
| **생성** | 찾아온 근거대로 답했나 / 질문에 답했나 | Faithfulness, Answer Relevance |

**분리하지 않으면 "답이 나쁘다"에서 멈춰 프롬프트만 계속 만지게 된다.**

### 지표 계산

```python
# Recall@k — 가장 중요하고 가장 쉽다
def recall_at_k(retrieved_ids, gold_ids, k):
    top = set(retrieved_ids[:k])
    return len(top & set(gold_ids)) / len(gold_ids)

# MRR — 정답이 몇 등으로 나왔는지 (1등이면 1.0, 5등이면 0.2)
def mrr(retrieved_ids, gold_ids):
    for rank, doc_id in enumerate(retrieved_ids, 1):
        if doc_id in gold_ids:
            return 1 / rank
    return 0.0
```

**Recall@k 부터 시작해라.** 이것만 측정해도 청킹·모델·하이브리드 실험을 비교할 수 있다.

### 평가셋 만들기 — 현실적인 방법

이상적으로는 사람이 질문-정답문서 쌍을 50~200개 만든다. 현실에서는:

1. **실제 사용 로그에서** 자주 나오는 질문 30개를 뽑는다
2. **LLM 으로 합성** — 각 문서를 주고 "이 문서로만 답할 수 있는 질문 3개를 만들어라"
   → 그 문서가 자동으로 정답 레이블이 된다. **빠르게 수백 개를 만들 수 있다**
3. **사용자 👎 피드백** — 실패 사례가 가장 값진 평가 데이터다

> ②의 함정: LLM 이 만든 질문은 문서의 표현을 그대로 쓰는 경향이 있어 **실제보다 쉽다.**
> "다른 말로 바꿔 물어라"를 프롬프트에 넣고, 일부는 사람이 검수한다.

### 생성 품질 (LLM-as-judge)

```
근거 문서: {chunks}
질문: {q}
답변: {a}

답변의 각 주장이 근거 문서에서 확인되는가?
확인 불가한 주장이 하나라도 있으면 "unfaithful".
JSON 으로: {"faithful": bool, "unsupported_claims": [...]}
```

- 심판 모델은 **생성 모델보다 같거나 좋은 것**을 쓴다
- 사람 평가와 얼마나 일치하는지 한 번은 대조해 봐야 신뢰할 수 있다
- 도구: **RAGAS**, TruLens, DeepEval, promptfoo

### CI 에 넣기 — 이게 핵심

```yaml
# 프롬프트나 청킹 설정이 바뀌면 평가셋을 돌린다
- run: python eval.py --dataset eval/golden.jsonl --threshold-recall5 0.85
```

**Recall@5 가 0.85 아래로 떨어지면 빌드 실패.**

> 이건 내가 이미 해본 일의 같은 형태다. i18n 번역 누락과 한글 잔존을 CI 에서 차단한 것,
> FSD 구조 위반을 커밋 훅에서 막은 것 — **"품질을 사람의 주의력이 아니라 파이프라인으로 고정한다"**.
> RAG 품질에 이걸 적용하는 팀은 아직 많지 않다. **들어가서 제안할 수 있는 지점이다.**

## 5. 개선 우선순위

투자 대비 효과 순. 위에서부터 하면 된다.

| 순위 | 개선 | 비용 | 효과 |
| --- | --- | --- | --- |
| 1 | **평가셋 만들기** | 하루 | 이게 없으면 나머지를 비교할 수 없다 |
| 2 | 구조 기반 청킹 | 문서 유형별 작업 | 크다 |
| 3 | 하이브리드 검색 | 중간 | 크다 (특히 고유명사) |
| 4 | 대화 맥락 압축 | 작다 | 챗 UI 에서 크다 |
| 5 | 청크에 맥락 주입 | 작다 | 중간 |
| 6 | 리랭킹 | 중간 (지연 증가) | 중간~크다 |
| 7 | 메타데이터 필터 | 중간 | 도메인에 따라 매우 크다 |
| 8 | 임베딩 모델 교체 | **재인덱싱 전체** | 예측 어려움 |
| 9 | HyDE / 다중 쿼리 | 지연·비용 증가 | 경우에 따라 |

**8번(모델 교체)이 아래에 있는 게 포인트다.** 사람들이 제일 먼저 하고 싶어 하지만
비용이 가장 크고 효과가 가장 불확실하다.

## 6. 디버깅 체크리스트

답이 이상할 때 순서대로 확인한다.

```
[ ] 1. top-k 청크를 로그로 출력했나? (안 했으면 여기부터)
[ ] 2. 정답이 든 청크가 top-k 안에 있나?
        없다 → 검색 문제 (3~6번)
        있다 → 생성 문제 (7~9번)
[ ] 3. 그 청크가 인덱스에 존재하긴 하나? (인덱싱 실패/누락)
[ ] 4. 청킹 경계에서 잘렸나? 원문을 직접 확인
[ ] 5. 키워드로는 찾히나? (찾히면 → 하이브리드 도입)
[ ] 6. 쿼리가 대화 맥락 없이 들어갔나? (후속 질문 문제)
[ ] 7. 청크가 프롬프트의 가운데 묻혔나? (lost in the middle)
[ ] 8. 컨텍스트 길이를 초과해 잘렸나?
[ ] 9. 프롬프트가 "모른다고 답해도 된다"를 허용하나?
```

**1번을 위한 도구를 만드는 게 프론트엔드가 팀에 기여할 수 있는 가장 큰 일 중 하나다.**
내부 디버그 화면에서 질문 → top-k 청크 + 점수 + 최종 프롬프트를 볼 수 있으면,
백엔드·ML 사람들이 매번 로그를 뒤지지 않아도 된다.
