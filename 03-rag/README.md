## 한 문장 정의

> 모델을 다시 학습시키는 대신, **질문이 들어올 때마다 관련 문서를 찾아 프롬프트에 근거로 끼워 넣어** 답하게 하는 방식.

RAG 는 Retrieval-Augmented Generation 의 줄임말이다. 글자 그대로 "검색(retrieval)으로 보강한 생성(generation)"이다.
예를 들어 "연차 며칠이야?"라는 질문이 오면 시스템은 사내 규정에서 "제15조 연차휴가는 15일을 부여한다"를 찾아
프롬프트에 붙인 뒤 LLM 에 "이 문서를 근거로 답하라"고 시킨다. 모델은 휴가 규정을 외운 적이 없어도 답할 수 있다.

## 왜 파인튜닝이 아닌가

파인튜닝(fine-tuning)은 이미 학습된 모델에 우리 데이터를 더 학습시켜 모델의 가중치 자체를 바꾸는 방법이다.
지식이 모델 안에 녹아 들어가므로 따로 문서를 찾을 필요가 없다. 그 대신 아래 표의 문제가 생긴다.

| | 파인튜닝 | RAG |
| --- | --- | --- |
| 문서가 바뀌면 | 재학습 | 인덱스만 갱신 |
| 출처 표시 | 불가능 | 가능 ← **엔터프라이즈에서 이게 결정적** |
| 사용자별 권한 분리 | 사실상 불가 | 검색 필터로 가능 |
| 비용 | 크다 | 질의당 검색 + 토큰 |
| 잘하는 것 | 말투·형식·도메인 어휘 학습 | **사실(fact) 주입** |

출처와 권한이 결정적인 이유는 이렇다. 파인튜닝한 모델은 "왜 그렇게 답했는지" 근거 문서를 댈 수 없다.
또 사원 A 는 인사 문서를 볼 수 있고 사원 B 는 볼 수 없는 상황을 모델 하나로 구분할 방법이 없다.
엔터프라이즈 계약에서는 이 둘이 기능이 아니라 조건이다.

둘은 경쟁 관계가 아니다. 파인튜닝은 *어떻게 말할지*, RAG 는 *무엇을 말할지*를 다룬다.
"우리 회사 휴가 규정"은 영원히 RAG 의 영역이다.

## 반드시 갖고 갈 감각 세 가지

1. **RAG 실패의 대부분은 LLM 이 아니라 검색(retriever)의 실패다.**
   리트리버(retriever)는 질문을 받아 관련 청크를 찾아오는 검색 담당 부품이다.
   답이 이상하면 모델 탓하기 전에 *어떤 청크가 들어갔는지* 부터 본다.

2. **품질을 가르는 건 모델이 아니라 청킹 전략과 검색 품질이다.**
   GPT-4o 를 Claude 로 바꿔서 해결되는 문제는 거의 없다. 근거로 엉뚱한 청크를 받으면 어떤 모델도 맞는 답을 못 한다.

3. **측정하지 않으면 조용히 나빠진다.**
   "잘 되는 것 같다"로 운영하면 문서가 늘면서 검색 품질이 서서히 무너져도 아무도 모른다.
   그래서 평가셋(질문과 정답 문서를 짝지어 둔 시험지)을 만들어 숫자로 지켜본다. `03-retrieval-quality.md` 4절에서 다룬다.
