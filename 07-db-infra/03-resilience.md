# 장애에 버티는 패턴

**외부 시스템은 느리고, 가끔 죽고, 호출 제한이 있다.** 이건 예외 상황이 아니라 평소 상태다.
랭코드는 고객사 시스템과 LLM API 를 붙이는 회사다. 둘 다 이 세 가지를 매일 한다.

이 문서의 패턴은 전부 하나의 질문에 대한 답이다: **"남이 느려질 때, 나까지 같이 죽지 않으려면?"**

---

## 1. 타임아웃 — 모든 것의 시작

```csharp
var res = await _http.GetAsync("https://customer-erp.example.com/api/orders");  // 타임아웃은?
```

`HttpClient` 의 기본 타임아웃은 **100초**다. 고객사 ERP 가 응답을 안 주면 이 요청은 100초 동안 매달려 있다.

```
고객사 API 가 멈춤
   ↓
우리 요청이 하나씩 100초씩 매달린다
   ↓
그 사이 들어온 요청들도 같은 API 를 기다린다
   ↓
DB 커넥션 · 스레드 · 메모리가 쌓인다 (01/03 커넥션 풀)
   ↓
고객사 API 와 무관한 기능까지 전부 느려진다   ← 장애 전파
```

**타임아웃이 없는 외부 호출 하나가 서비스 전체를 세운다.** 그래서 순서상 재시도보다 타임아웃이 먼저다.

| 호출 | 출발점 |
| --- | --- |
| 내부 마이크로서비스 | 1\~5초 |
| 고객사 시스템 | 측정해서 p99 의 2\~3배 |
| LLM 생성 (스트리밍) | 첫 토큰까지 / 토큰 사이 간격으로 따로 잡는다. 전체 시간으로 잡으면 긴 답변이 잘린다 |

## 2. 재시도 — 언제 하고, 언제 하면 안 되나

### 재시도해도 되는 실패 (일시적, transient)

| 신호 | 의미 |
| --- | --- |
| 네트워크 끊김 · 타임아웃 | 잠깐의 문제일 수 있다 |
| `408` Request Timeout | |
| `429` Too Many Requests | 호출 제한. **`Retry-After` 헤더를 따른다** |
| `502` · `503` · `504` | 상대 서버가 잠깐 불안정 |

### 재시도하면 안 되는 실패

| 신호 | 왜 |
| --- | --- |
| `400` · `422` | 요청이 틀렸다. 백 번 보내도 똑같이 틀린다 |
| `401` · `403` | 권한 문제. 재시도는 계정 잠금만 부른다 |
| `404` | 없는 것은 계속 없다 |

### 그리고 가장 중요한 조건: 멱등성

**결제 요청이 타임아웃 났다. 재시도해도 되나?** 타임아웃은 "실패"가 아니라 **"모름"** 이다.
상대방은 이미 결제를 처리했는데 응답만 늦었을 수 있다. 재시도하면 **두 번 결제된다.**

- `GET` · `PUT` · `DELETE` — 원래 멱등. 재시도 안전
- `POST` — 멱등하지 않다. **Idempotency-Key 가 있을 때만** 재시도 (→ `01-backend-basics/05-long-running-jobs.md` 4절)

### 지수 백오프 + 지터

```
❌ 즉시 재시도 3번      : 0ms, 0ms, 0ms        → 쓰러진 서버를 세 배로 때린다
△ 지수 백오프          : 1s, 2s, 4s           → 간격은 벌어지지만...
✅ 지수 백오프 + 지터    : 1.3s, 1.7s, 4.6s ...  → 무작위 편차를 섞는다
```

**지터(jitter)가 필요한 이유:** 서버 1000대가 같은 순간 실패하면, 지수 백오프만으로는 1000대가 **같은 순간 1초 뒤에, 같은 순간 2초 뒤에** 다시 몰려온다.
무작위 편차를 섞어야 재시도가 시간축에 흩어진다. `02-caching.md` 5절의 TTL 편차와 같은 원리다.

**재시도는 증폭기다.** 3계층(프론트 → API → 고객사)이 각자 3번씩 재시도하면 최악의 경우 3 × 3 × 3 = 27번이 된다.
재시도는 **한 계층에서만** 하는 게 원칙이다. 보통 외부 시스템에 가장 가까운 곳.

## 3. 서킷 브레이커 — 죽은 곳은 잠시 부르지 않는다

재시도는 "곧 살아날 것"을 가정한다. 상대가 **10분째 죽어 있으면** 모든 요청이 타임아웃까지 기다렸다가 재시도까지 하고 실패한다. 아무 의미 없이 느리기만 하다.

```
        실패율이 임계치 초과
 Closed ─────────────────▶ Open
 (정상 호출)                 (호출하지 않고 즉시 실패)
    ▲                          │
    │ 시험 호출 성공             │ 일정 시간 경과
    │                          ▼
    └──────────────────── Half-Open
                          (몇 개만 시험 삼아 보낸다)
```

두꺼비집과 같다. 과부하가 감지되면 끊어서 **양쪽을 다 보호**한다.
- 우리는 기다리지 않고 바로 실패 → 대체 응답("고객사 시스템 점검 중입니다")을 보여줄 수 있다
- 상대는 쏟아지는 요청 없이 회복할 시간을 얻는다

## 4. .NET 에서는 — 직접 짜지 않는다

위 1\~3 을 손으로 구현하면 반드시 버그가 생긴다. .NET 8+ 는 표준 구성을 한 줄로 제공한다.

```csharp
// Program.cs
builder.Services.AddHttpClient<CustomerErpClient>(c =>
{
    c.BaseAddress = new Uri(builder.Configuration["Erp:BaseUrl"]!);
})
.AddStandardResilienceHandler();     // Microsoft.Extensions.Http.Resilience
```

`AddStandardResilienceHandler()` 는 다음을 순서대로 쌓는다 (내부적으로 **Polly** 라이브러리):

| 순서 | 전략 | 하는 일 |
| ---: | --- | --- |
| 1 | 동시성 제한 | 이 클라이언트로 동시에 나가는 요청 수의 상한 |
| 2 | 전체 타임아웃 | 재시도를 다 합쳐서 이 시간을 넘으면 끝 |
| 3 | 재시도 | 일시적 실패에 지수 백오프 + 지터 |
| 4 | 서킷 브레이커 | 실패율이 높으면 잠시 차단 |
| 5 | 시도별 타임아웃 | 한 번의 시도가 이 시간을 넘으면 실패로 보고 다음 재시도 |

기본값으로 시작하고, **고객사·LLM 처럼 특성이 다른 클라이언트는 따로 조정한다.**
코드에서 `AddStandardResilienceHandler` 나 `Polly` 를 보면 "이 외부 호출은 보호받고 있구나"라고 읽으면 된다.

> ❓ 입사 후 확인: 고객사 연동 클라이언트에 레질리언스 설정이 붙어 있나? LLM 호출은 어떻게 재시도하나?

## 5. 레이트 리밋 — 우리가 남을 보호할 때

지금까지는 남이 느릴 때 우리를 지키는 법이었다. 반대로 **우리 API 를 지키는 법**이다.

| 이유 | 예 |
| --- | --- |
| 남용 방지 | 스크립트로 1초에 1000번 호출 |
| **비용 방지** | LLM 을 쓰는 API 는 호출 하나가 돈이다. 무한 루프 하나가 하룻밤에 청구서를 만든다 |
| 공정성 | 한 고객사가 전체 용량을 다 쓰지 않게 |

### 알고리즘

| 방식 | 동작 | 특징 |
| --- | --- | --- |
| 고정 윈도우 | 1분마다 카운터 리셋, 100개까지 | 단순. 경계에서 순간적으로 2배 가능 (59초에 100, 61초에 100) |
| 슬라이딩 윈도우 | 최근 60초 기준 | 경계 문제 완화 |
| **토큰 버킷** | 초당 N개씩 토큰이 차고, 요청마다 하나씩 쓴다 | 짧은 버스트는 허용하면서 평균을 제한 |
| 동시성 제한 | 동시에 처리 중인 요청 수 | 오래 걸리는 LLM 요청에 적합 |

### ASP.NET Core 내장 (.NET 7+)

```csharp
builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    o.AddPolicy("per-tenant", ctx =>
        RateLimitPartition.GetTokenBucketLimiter(
            ctx.User.FindFirst("tenant_id")?.Value ?? "anonymous",   // 테넌트별로 따로 센다
            _ => new TokenBucketRateLimiterOptions
            {
                TokenLimit = 20, TokensPerPeriod = 10,
                ReplenishmentPeriod = TimeSpan.FromSeconds(1),
            }));
});

app.UseRateLimiter();
app.MapPost("/api/chat", ...).RequireRateLimiting("per-tenant");
```

**내장 리미터의 함정:** 카운터가 **서버 메모리에 있다.** 서버가 5대면 한도가 사실상 5배가 된다.
정확한 한도가 필요하면 카운터를 Redis 에 두거나, 앞단(API Gateway, Azure Front Door/APIM)에서 제한한다.

### 프론트가 해야 할 일

`429` 를 받으면 **`Retry-After` 를 읽고 그만큼 기다렸다가** 재시도하거나, "잠시 후 다시 시도해 주세요"를 보여준다.
일반 에러처럼 즉시 재시도 버튼을 띄우면 사용자가 연타해서 상황을 악화시킨다.

## 6. 벌크헤드와 큐 — 느린 일은 격리한다

**벌크헤드(격벽)**: 배의 칸막이처럼, 한 칸에 물이 차도 다른 칸은 멀쩡하게 한다.
고객사 연동 하나가 느려도 채팅 기능은 영향받지 않도록 **자원(동시 처리 수, 커넥션)을 기능별로 나눈다.**

가장 확실한 격리는 **요청 처리에서 빼서 큐로 보내는 것**이다.

```
❌ API 요청 안에서 고객사 문서 1000개를 동기화
✅ API 는 잡만 등록하고 즉시 202 → 워커가 큐에서 꺼내 처리 (01/05)
```

**메모리 큐는 큐가 아니다.** `List<Job>` 이나 `Channel<T>` 에 넣어 두고 백그라운드에서 처리하면
서버가 재배포·재시작되는 순간 **대기 중이던 작업이 전부 사라진다.** 그리고 서버가 여러 대면 일이 고르게 나눠지지 않는다.
잃으면 안 되는 작업은 **DB 테이블 또는 진짜 큐(Azure Service Bus, RabbitMQ)** 에 넣는다.

## 7. 우아한 실패 (Graceful degradation)

모든 걸 지켜낼 수는 없다. 그렇다면 **무엇을 포기할지**를 미리 정한다.

| 실패 | 전부 실패시키는 대신 |
| --- | --- |
| 리랭커 API 다운 | 리랭킹 없이 1차 검색 결과로 답한다 |
| 추천 기능 타임아웃 | 추천 영역만 비우고 페이지는 보여준다 |
| 고객사 시스템 점검 | 마지막으로 동기화된 데이터 + "N분 전 기준" 표시 |
| LLM 429 | 대기열 위치를 보여주거나 더 작은 모델로 대체 |

**프론트가 이걸 표현할 수 있어야 한다.** 부분 실패를 표현하는 UI(영역별 에러, "최신이 아닐 수 있음" 배지)가 없으면, 백엔드는 전부 성공 아니면 전부 실패만 할 수 있다.
