# 관측성 (Observability)

프론트에서는 버그가 나면 **내 브라우저 콘솔**을 열었다. 서버에서는 그 콘솔이 없다.
사용자 화면은 볼 수 없고, 서버는 여러 대이며, 문제는 이미 몇 시간 전에 일어났다.
**그때 남겨 둔 기록만으로 무슨 일이 있었는지 재구성해야 한다.** 그게 관측성이다.

관측성은 "서버 밖에서 남은 기록만 보고 서버 안에서 무슨 일이 있었는지 알아낼 수 있는 정도"를 말한다. 기록을 잘 남겨 두면 관측성이 높고 문제가 날 때마다 코드를 고쳐 로그를 추가하고 재배포해야 한다면 낮다.

---

## 1. 세 가지 신호

| 신호 | 답하는 질문 | 예 |
| --- | --- | --- |
| **로그** | 무슨 일이 있었나 (사건 하나하나) | "tenant=A 의 문서 동기화가 403 으로 실패" |
| **메트릭** | 얼마나, 얼마나 자주 (숫자의 추이) | "채팅 API p95 지연 4.2초, 5분 전보다 2배" |
| **트레이스** | 요청 하나가 어디서 시간을 썼나 | "검색 120ms → 리랭킹 300ms → LLM 3.8초" |

프론트 도구로 치면 로그는 `console.log`, 메트릭은 Web Vitals 대시보드, 트레이스는 DevTools 의 Network 탭 워터폴(요청별 시간 막대)에 가깝다.
메트릭은 사건 하나하나를 저장하지 않고 **집계한 숫자만** 시간별로 남긴다. 그래서 싸고 오래 보관할 수 있지만 "어떤 요청이었나"는 알려주지 않는다.

보통 **메트릭으로 이상을 발견**하고 → **트레이스로 어디가 느린지 좁히고** → **로그로 왜 그런지 확인**한다.

## 2. 구조화 로그 — 문자열이 아니라 데이터로

구조화 로그는 로그 한 줄을 문장이 아니라 **필드가 있는 데이터(보통 JSON)** 로 남기는 방식이다.

```csharp
// ❌ 문자열 보간 — 사람만 읽을 수 있다
_logger.LogInformation($"문서 {docId} 동기화 완료, {elapsed}ms");

// ✅ 메시지 템플릿 — 값이 필드로 따로 저장된다
_logger.LogInformation("문서 {DocumentId} 동기화 완료, {ElapsedMs}ms", docId, elapsed);
```

둘 다 콘솔에는 같은 문장으로 찍힌다. 차이는 **저장될 때**다.
두 번째 줄의 `{DocumentId}` 는 C# 보간이 아니라 **메시지 템플릿**의 자리 표시자다. 뒤에 넘긴 인자가 순서대로 들어가고 이름(`DocumentId`)은 필드 이름이 된다.

```json
{
  "timestamp": "2026-10-02T09:14:03Z",
  "level": "Information",
  "message": "문서 7f3a 동기화 완료, 1840ms",
  "DocumentId": "7f3a",
  "ElapsedMs": 1840,
  "TenantId": "acme",
  "TraceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

그래서 나중에 **"ElapsedMs > 5000 인 동기화만"**, **"TenantId = acme 의 에러만"** 같은 검색이 된다.
`$"..."` 로 쓰면 값이 문장 안에 녹아버려서 이 검색이 불가능하다. C# 코드 리뷰에서 가장 자주 지적되는 로그 실수다.

### 모든 로그에 같은 필드 붙이기 — 스코프

위 JSON 의 `TenantId` 는 로그 호출마다 직접 넘긴 게 아니다. 요청 처리 초입에 **로그 스코프**를 열면 그 안에서 찍히는 모든 로그에 같은 필드가 붙는다.

```csharp
using (_logger.BeginScope(new Dictionary<string, object> { ["TenantId"] = tenantId }))
{
    _logger.LogInformation("문서 {DocumentId} 동기화 시작", docId);   // TenantId 도 같이 저장된다
    await SyncAsync(docId);
}
```

React Context 로 하위 컴포넌트 전체에 값을 내려 주는 것과 비슷하다. 보통 미들웨어에서 한 번 열어 두면 그 요청의 모든 로그에 테넌트와 사용자가 찍힌다.
(스코프 필드가 실제로 출력되는지는 로깅 설정에 따라 다르다. 콘솔 로거는 `IncludeScopes` 를 켜야 보인다.)

### 로그 레벨

| 레벨 | 언제 | 운영에서 |
| --- | --- | --- |
| `Trace` / `Debug` | 개발 중 상세 추적 | 보통 끈다 |
| `Information` | 정상 흐름의 주요 지점 (요청 완료, 잡 시작/끝) | 켠다 |
| `Warning` | 이상하지만 처리됨 (재시도 성공, 대체 경로 사용) | 켠다. **추이를 본다** |
| `Error` | 요청 하나가 실패함 | 켠다. 알림 대상 |
| `Critical` | 서비스 전체가 위험 (DB 연결 불가) | 즉시 알림 |

**`Warning` 을 무시하지 않는다.** "재시도해서 성공함"이 하루 10번에서 1000번이 되면 곧 재시도로도 못 버티는 날이 온다.

### 남기면 안 되는 것

| 금지 | 이유 |
| --- | --- |
| 비밀번호 · 토큰 · API 키 · 연결 문자열 | 로그는 생각보다 많은 사람이 본다 |
| 주민번호 · 카드번호 · 전화번호 등 개인정보 | 법적 문제. 마스킹하거나 빼라 |
| **사용자 질문·고객사 문서 원문 전체** | RAG 서비스에서 특히 주의. 고객사 계약 조건일 수 있다 |
| 요청 본문 전체 | 위 세 가지가 섞여 들어온다 |

마스킹은 값의 일부를 가려서 남기는 것이다 (`010-****-2222`). 원문이 꼭 필요하지 않다면 ID 나 길이만 남긴다.

> ❓ 입사 후 확인: 프롬프트와 검색 결과를 로그에 남기나? 남긴다면 보관 기간과 접근 권한은?

## 3. 추적 ID — 서버 10대에 흩어진 로그를 한 줄로 꿰기

요청 하나가 API → 검색 서비스 → LLM 프록시를 거치면 로그가 세 서버에 흩어진다.
**같은 요청에서 나온 로그에 같은 ID 를 붙여야** 나중에 모을 수 있다.

용어 두 개를 먼저 정리한다.

- **trace(트레이스)**: 요청 하나가 시스템을 지나가는 **전체 여정.** 고유한 trace id 하나를 가진다.
- **span(스팬)**: 그 여정 안의 **구간 하나.** "DB 쿼리 한 번", "리랭커 호출 한 번"처럼 시작 시각과 끝 시각이 있다. 스팬은 부모-자식으로 이어져 트리를 이룬다 (5절 그림).

택배로 치면 trace id 는 송장 번호이고 span 은 "집하 → 허브 → 배송" 같은 구간 기록 하나하나다.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                └─────── trace id (요청 전체) ───────┘└ span id (구간) ┘
```

W3C 표준 헤더 `traceparent` 를 쓰면 서비스 사이를 지나갈 때 ID 가 자동으로 전달된다. W3C 는 웹 표준을 정하는 단체다. 이 헤더 형식이 표준이라 언어와 프레임워크가 달라도 같은 trace id 를 이어받을 수 있다.
맨 앞 `00` 은 형식 버전, 맨 뒤 `01` 은 "이 트레이스를 기록한다(샘플링됨)"는 표시다.
ASP.NET Core 는 이 헤더를 읽고 쓰는 걸 기본으로 해 준다(`Activity`). .NET 에서 `Activity` 가 span 하나다. 우리가 할 일은 **로그에 TraceId 가 같이 찍히게 설정하는 것**뿐이다.

### 프론트와 연결하기

에러 응답에 traceId 를 담아 보내면 지원 업무가 완전히 달라진다.

```json
// ASP.NET Core ProblemDetails (02-csharp-dotnet/02 6절)
{ "status": 500, "title": "Internal Server Error", "traceId": "00-4bf92f35..." }
```

```
❌ 사용자: "아까 에러 났어요"            → 몇 시? 어떤 화면? 무슨 질문? ... 찾을 수 없다
✅ 화면: "오류가 발생했습니다 (문의 코드: 4bf92f35)"  → 그 ID 로 검색하면 전 구간 로그가 나온다
```

**에러 화면에 추적 ID 를 보여주는 건 프론트가 할 수 있는 가장 싼 운영 개선이다.**

## 4. 메트릭 — 무엇을 셀 것인가

### 모든 API 의 기본 네 가지 (Golden signals)

Google 의 SRE(사이트 신뢰성 엔지니어링) 책이 "서비스마다 최소한 이 넷은 보라"고 정리한 지표라서 golden signals 라고 부른다.

| 신호 | 예 |
| --- | --- |
| **지연 (Latency)** | 평균이 아니라 **p95 · p99** 를 본다 |
| **트래픽** | 초당 요청 수 |
| **에러율** | 5xx 비율 |
| **포화도** | CPU · 메모리 · DB 커넥션 풀 사용률 · 큐 길이 |

포화도(saturation)는 자원이 얼마나 꽉 찼는가다. 100% 에 가까워지면 아직 에러가 없어도 곧 느려지거나 거절이 시작된다.

### p95 · p99 — 백분위로 보는 이유

**p95** 는 요청을 빠른 순으로 줄 세웠을 때 95% 지점의 값이다. 대략 "100명 중 95명은 이만큼 안에 응답을 받았다"는 뜻이다. **p99** 는 99% 지점, 곧 가장 느린 1% 가 시작되는 경계다.
p50 은 정확히 가운데 값(중앙값)이다. p99 처럼 끝쪽 값을 흔히 **꼬리 지연(tail latency)** 이라고 부른다.

**평균은 거짓말을 한다.** 요청 100개 중 98개가 100ms, 2개가 10초면 평균은 약 300ms 로 "괜찮아" 보인다.
하지만 느린 순으로 1% 안에 드는 요청이 10초라서 p99 는 10초다. 하루 10만 요청이면 **2000명이 10초를 기다렸다.**

사용자 한 명은 페이지 하나를 열 때 API 를 여러 번 부른다. 그중 하나만 느려도 화면 전체가 느리다. 그래서 꼬리가 중요하다.

### AI 서비스에만 있는 메트릭

| 메트릭 | 왜 |
| --- | --- |
| 첫 토큰까지 시간 (TTFT) | 체감 속도는 전체 시간이 아니라 이것으로 결정된다 |
| 요청당 입력·출력 토큰 수 | **곧 비용이다.** 테넌트별로 쪼개서 본다 |
| 검색 1등 점수 분포 | 갑자기 낮아지면 인덱싱이 깨졌거나 문서가 바뀐 것 (`03-rag/00` 4절) |
| "모른다" 응답 비율 | 올라가면 검색 문제, 0 이면 지어내고 있을 가능성 |
| 👎 피드백 비율 | 품질의 직접 지표 |

TTFT(Time To First Token)는 요청을 보내고 첫 글자가 화면에 나타날 때까지의 시간이다. 프론트의 LCP 처럼 "사용자가 처음 뭔가를 보는 순간"을 잰다.

### 메트릭에 붙이는 태그는 종류가 적어야 한다

메트릭에는 `tenant`, `endpoint`, `status` 같은 태그(차원)를 붙여 쪼개 볼 수 있다. 저장소는 **태그 값의 조합마다** 시계열을 하나씩 따로 만든다.
그래서 `userId` · `documentId` · `traceId` 처럼 값이 수십만 가지인 것을 태그로 붙이면 시계열이 폭증해서 비용이 터지거나 수집이 막힌다. 이걸 **카디널리티 폭발**이라고 부른다. (카디널리티 = 서로 다른 값의 개수, `07-db-infra/01-relational-basics.md` 10절)

| 태그로 OK | 태그로 금지 → 로그나 트레이스에 |
| --- | --- |
| 엔드포인트, HTTP 상태, 모델 이름, 테넌트(수십\~수백 곳이면) | 사용자 ID, 문서 ID, 질문 원문, trace id |

## 5. 트레이스 — 요청 하나의 타임라인

```
POST /api/chat                                          4,380ms
├─ 쿼리 재작성 (LLM)                         410ms
├─ 권한 조회 (DB)                             12ms
├─ 하이브리드 검색                            95ms
│   ├─ 벡터 검색                     60ms
│   └─ BM25                          40ms
├─ 리랭킹 (외부 API)                         310ms
└─ 답변 생성 (LLM, 스트리밍)               3,520ms
```

한 줄 한 줄이 span 이고 전체가 trace 하나다. 들여쓰기가 부모-자식 관계다.

"채팅이 느려요"를 받았을 때 이 그림이 있으면 3초 만에 결론이 난다. **LLM 생성이 80%다. 검색을 튜닝해도 소용없다.**
없으면 며칠 동안 추측으로 엉뚱한 곳을 고친다.

`03-rag/01-pipeline.md` 5절의 "어떤 청크가 들어갔는지부터 본다"도 같은 이야기다.
**각 단계의 입력·출력·시간을 남겨 두는 것**이 RAG 디버깅의 전제다.

### 비즈니스 구간을 직접 span 으로 남기기

HTTP · DB 호출은 자동으로 span 이 생기지만 "리랭킹", "쿼리 재작성" 같은 구간은 직접 열어야 한다. .NET 에서는 `ActivitySource` 를 쓴다.

```csharp
private static readonly ActivitySource Source = new("Langcode.Rag");

public async Task<IReadOnlyList<Chunk>> RerankAsync(string query, IReadOnlyList<Chunk> chunks)
{
    using var activity = Source.StartActivity("rerank");       // span 시작. using 이 끝나면 span 종료
    activity?.SetTag("rerank.input_count", chunks.Count);      // 값이 적은 숫자·이름만 태그로

    var result = await _reranker.RerankAsync(query, chunks);
    activity?.SetTag("rerank.output_count", result.Count);
    return result;
}
```

`StartActivity` 는 아무도 이 소스를 수집하지 않으면 `null` 을 돌려준다. 그래서 `activity?.` 처럼 null 조건 연산자로 쓴다.
수집하려면 6절 설정에 `.AddSource("Langcode.Rag")` 를 추가해야 한다. 이걸 빠뜨리면 코드는 멀쩡한데 트레이스에 구간이 안 나온다.

## 6. 도구 — OpenTelemetry 와 Application Insights

| 도구 | 역할 |
| --- | --- |
| **OpenTelemetry** | 로그·메트릭·트레이스를 **수집하는 표준**. 어느 백엔드로든 보낼 수 있다 |
| Azure Monitor / **Application Insights** | Azure 의 저장·검색·대시보드·알림. MS 파트너라면 유력 |
| Grafana · Prometheus · Jaeger · Seq | 오픈소스 대안 |

**OpenTelemetry**(줄여서 OTel)는 특정 회사 제품이 아니라 CNCF 가 관리하는 오픈 표준이다. 계측 코드(데이터를 만드는 쪽)와 저장소(데이터를 보는 쪽)를 분리한다.
코드는 OTel 방식으로 한 번만 계측하고 보낼 곳은 설정에서 고른다. 나중에 Application Insights 에서 Grafana 로 옮겨도 앱 코드는 거의 그대로다.
계측(instrumentation)은 코드 곳곳에 측정 지점을 심어 로그·메트릭·span 을 만들어 내는 일이다. 내보내기 대상(exporter)은 그 데이터를 어디로 보낼지 정하는 부품이다.

```csharp
// Program.cs — 개념만
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSource("Langcode.Rag"))      // 5절에서 직접 만든 span 수집
    .WithMetrics(m => m.AddAspNetCoreInstrumentation())
    .UseAzureMonitor();    // 또는 다른 내보내기 대상
```

HTTP 요청·외부 호출·DB 쿼리는 계측 라이브러리가 **자동으로** 기록한다. 직접 추가하는 건 "리랭킹", "쿼리 재작성" 같은 비즈니스 구간뿐이다.
(DB 쿼리는 해당 계측 패키지를 추가했을 때 기록된다. 예: Npgsql 은 `Npgsql.OpenTelemetry` 패키지의 `.AddNpgsql()`.)

> ❓ 입사 후 확인: 로그·트레이스는 어디서 보나? (Application Insights? Seq? Grafana?) 알림은 누구에게 가나?

---

## 7. 알림 — 사람을 깨우는 기준

| ❌ 나쁜 알림 | ✅ 좋은 알림 |
| --- | --- |
| CPU 80% 초과 | 사용자가 체감하는 것: 에러율 · p95 지연 |
| 에러 로그 1건마다 | 5분간 에러율 2% 초과 |
| 아무도 행동하지 않는 알림 | **받으면 할 일이 정해져 있는** 알림 |

알림이 너무 많으면 사람들이 무시하기 시작하고 진짜 장애 알림도 같이 무시된다. 이걸 알림 피로(alert fatigue)라고 부른다.
