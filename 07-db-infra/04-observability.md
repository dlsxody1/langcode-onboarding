# 관측성 (Observability)

프론트에서는 버그가 나면 **내 브라우저 콘솔**을 열었다. 서버에서는 그 콘솔이 없다.
사용자 화면은 볼 수 없고, 서버는 여러 대이며, 문제는 이미 몇 시간 전에 일어났다.
**그때 남겨 둔 기록만으로 무슨 일이 있었는지 재구성해야 한다.** 그게 관측성이다.

---

## 1. 세 가지 신호

| 신호 | 답하는 질문 | 예 |
| --- | --- | --- |
| **로그** | 무슨 일이 있었나 (사건 하나하나) | "tenant=A 의 문서 동기화가 403 으로 실패" |
| **메트릭** | 얼마나, 얼마나 자주 (숫자의 추이) | "채팅 API p95 지연 4.2초, 5분 전보다 2배" |
| **트레이스** | 요청 하나가 어디서 시간을 썼나 | "검색 120ms → 리랭킹 300ms → LLM 3.8초" |

보통 **메트릭으로 이상을 발견**하고 → **트레이스로 어디가 느린지 좁히고** → **로그로 왜 그런지 확인**한다.

## 2. 구조화 로그 — 문자열이 아니라 데이터로

```csharp
// ❌ 문자열 보간 — 사람만 읽을 수 있다
_logger.LogInformation($"문서 {docId} 동기화 완료, {elapsed}ms");

// ✅ 메시지 템플릿 — 값이 필드로 따로 저장된다
_logger.LogInformation("문서 {DocumentId} 동기화 완료, {ElapsedMs}ms", docId, elapsed);
```

둘 다 콘솔에는 같은 문장으로 찍힌다. 차이는 **저장될 때**다.

```json
{
  "timestamp": "2026-10-02T09:14:03Z",
  "level": "Information",
  "message": "문서 7f3a 동기화 완료, 1840ms",
  "DocumentId": "7f3a",
  "ElapsedMs": 1840,
  "TenantId": "acme",
  "TraceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

그래서 나중에 **"ElapsedMs > 5000 인 동기화만"**, **"TenantId = acme 의 에러만"** 같은 검색이 된다.
`$"..."` 로 쓰면 값이 문장 안에 녹아버려서 이 검색이 불가능하다. C# 코드 리뷰에서 가장 자주 지적되는 로그 실수다.

### 로그 레벨

| 레벨 | 언제 | 운영에서 |
| --- | --- | --- |
| `Trace` / `Debug` | 개발 중 상세 추적 | 보통 끈다 |
| `Information` | 정상 흐름의 주요 지점 (요청 완료, 잡 시작/끝) | 켠다 |
| `Warning` | 이상하지만 처리됨 (재시도 성공, 대체 경로 사용) | 켠다. **추이를 본다** |
| `Error` | 요청 하나가 실패함 | 켠다. 알림 대상 |
| `Critical` | 서비스 전체가 위험 (DB 연결 불가) | 즉시 알림 |

**`Warning` 을 무시하지 않는다.** "재시도해서 성공함"이 하루 10번에서 1000번이 되면, 곧 재시도로도 못 버티는 날이 온다.

### 남기면 안 되는 것

| 금지 | 이유 |
| --- | --- |
| 비밀번호 · 토큰 · API 키 · 연결 문자열 | 로그는 생각보다 많은 사람이 본다 |
| 주민번호 · 카드번호 · 전화번호 등 개인정보 | 법적 문제. 마스킹하거나 빼라 |
| **사용자 질문·고객사 문서 원문 전체** | RAG 서비스에서 특히 주의. 고객사 계약 조건일 수 있다 |
| 요청 본문 전체 | 위 세 가지가 섞여 들어온다 |

> ❓ 입사 후 확인: 프롬프트와 검색 결과를 로그에 남기나? 남긴다면 보관 기간과 접근 권한은?

## 3. 추적 ID — 서버 10대에 흩어진 로그를 한 줄로 꿰기

요청 하나가 API → 검색 서비스 → LLM 프록시를 거치면 로그가 세 서버에 흩어진다.
**같은 요청에서 나온 로그에 같은 ID 를 붙여야** 나중에 모을 수 있다.

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                └─────── trace id (요청 전체) ───────┘└ span id (구간) ┘
```

W3C 표준 헤더 `traceparent` 를 쓰면 서비스 사이를 지나갈 때 ID 가 자동으로 전달된다.
ASP.NET Core 는 이 헤더를 읽고 쓰는 걸 기본으로 해 준다(`Activity`). 우리가 할 일은 **로그에 TraceId 가 같이 찍히게 설정하는 것**뿐이다.

### 프론트와 연결하기

에러 응답에 traceId 를 담아 보내면 지원 업무가 완전히 달라진다.

```json
// ASP.NET Core ProblemDetails (02-csharp-dotnet/02 6절)
{ "status": 500, "title": "Internal Server Error", "traceId": "00-4bf92f35..." }
```

```
❌ 사용자: "아까 에러 났어요"            → 몇 시? 어떤 화면? 무슨 질문? ... 찾을 수 없다
✅ 화면: "오류가 발생했습니다 (문의 코드: 4bf92f35)"  → 그 ID 로 검색하면 전 구간 로그가 나온다
```

**에러 화면에 추적 ID 를 보여주는 건 프론트가 할 수 있는 가장 싼 운영 개선이다.**

## 4. 메트릭 — 무엇을 셀 것인가

### 모든 API 의 기본 네 가지 (Golden signals)

| 신호 | 예 |
| --- | --- |
| **지연 (Latency)** | 평균이 아니라 **p95 · p99** 를 본다 |
| **트래픽** | 초당 요청 수 |
| **에러율** | 5xx 비율 |
| **포화도** | CPU · 메모리 · DB 커넥션 풀 사용률 · 큐 길이 |

**평균은 거짓말을 한다.** 요청 100개 중 99개가 100ms, 1개가 10초면 평균은 약 200ms 로 "괜찮아" 보인다.
하지만 p99 는 10초다. 하루 10만 요청이면 **1000명이 10초를 기다렸다.**

### AI 서비스에만 있는 메트릭

| 메트릭 | 왜 |
| --- | --- |
| 첫 토큰까지 시간 (TTFT) | 체감 속도는 전체 시간이 아니라 이것으로 결정된다 |
| 요청당 입력·출력 토큰 수 | **곧 비용이다.** 테넌트별로 쪼개서 본다 |
| 검색 1등 점수 분포 | 갑자기 낮아지면 인덱싱이 깨졌거나 문서가 바뀐 것 (`03-rag/00` 4절) |
| "모른다" 응답 비율 | 올라가면 검색 문제, 0 이면 지어내고 있을 가능성 |
| 👎 피드백 비율 | 품질의 직접 지표 |

## 5. 트레이스 — 요청 하나의 타임라인

```
POST /api/chat                                          4,380ms
├─ 쿼리 재작성 (LLM)                         410ms
├─ 권한 조회 (DB)                             12ms
├─ 하이브리드 검색                            95ms
│   ├─ 벡터 검색                     60ms
│   └─ BM25                          40ms
├─ 리랭킹 (외부 API)                         310ms
└─ 답변 생성 (LLM, 스트리밍)               3,520ms
```

"채팅이 느려요"를 받았을 때 이 그림이 있으면 3초 만에 결론이 난다 — **LLM 생성이 80%다. 검색을 튜닝해도 소용없다.**
없으면 며칠 동안 추측으로 엉뚱한 곳을 고친다.

`03-rag/01-pipeline.md` 5절의 "어떤 청크가 들어갔는지부터 본다"도 같은 이야기다.
**각 단계의 입력·출력·시간을 남겨 두는 것**이 RAG 디버깅의 전제다.

## 6. 도구 — OpenTelemetry 와 Application Insights

| 도구 | 역할 |
| --- | --- |
| **OpenTelemetry** | 로그·메트릭·트레이스를 **수집하는 표준**. 어느 백엔드로든 보낼 수 있다 |
| Azure Monitor / **Application Insights** | Azure 의 저장·검색·대시보드·알림. MS 파트너라면 유력 |
| Grafana · Prometheus · Jaeger · Seq | 오픈소스 대안 |

```csharp
// Program.cs — 개념만
builder.Services.AddOpenTelemetry()
    .WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation())
    .WithMetrics(m => m.AddAspNetCoreInstrumentation())
    .UseAzureMonitor();    // 또는 다른 내보내기 대상
```

HTTP 요청·외부 호출·DB 쿼리는 계측 라이브러리가 **자동으로** 기록한다. 직접 추가하는 건 "리랭킹", "쿼리 재작성" 같은 비즈니스 구간뿐이다.

> ❓ 입사 후 확인: 로그·트레이스는 어디서 보나? (Application Insights? Seq? Grafana?) 알림은 누구에게 가나?

## 7. 알림 — 사람을 깨우는 기준

| ❌ 나쁜 알림 | ✅ 좋은 알림 |
| --- | --- |
| CPU 80% 초과 | 사용자가 체감하는 것: 에러율 · p95 지연 |
| 에러 로그 1건마다 | 5분간 에러율 2% 초과 |
