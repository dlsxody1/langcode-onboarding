# DB 설계 — 어떤 순서로, 어떤 기준으로

`01-relational-basics.md` 는 테이블 · 키 · 정규화라는 **재료**를 줬고, `07-our-stack.md` 는 **어떤 저장소를 쓰는가**를 줬다.
이 문서는 그 둘을 이어서 **"새 기능이 들어왔을 때 DB 를 어떻게 설계하나"** 를 다룬다. 순서와 판단 기준이 중심이다.

> ⚠️ 여기 적은 것은 **B2B 멀티테넌트 SaaS 에서 일반적으로 쓰는 설계 방식**과, 이 레포의 다른 문서(스택 표 · 모듈러 모놀리스 · 멀티테넌시)에서 이어 낸 것이다.
> 랭코드가 실제로 어떤 규칙을 쓰는지는 아니다. 절마다 달린 ❓ 를 입사 후 확인해서 고쳐 써라.
> 확인하기 전까지는 **"이 기준으로 설계 리뷰를 읽고 말할 수 있다"** 가 목표다.

## 1. 설계는 테이블부터 그리는 게 아니다

프론트에서 컴포넌트를 만들 때 "화면이 먼저, 그 다음에 상태 모양"이었듯, DB 도 **쓰임새가 먼저, 모양이 나중**이다.
테이블부터 그리면 "일단 되는" 모양이 나오고, 그게 6개월 뒤 느린 쿼리와 마이그레이션 지옥이 된다.

| 순서 | 묻는 것 | 이 단계의 산출물 |
| --- | --- | --- |
| ① 요구사항 | 이 기능이 **무엇을 저장하고 무엇을 보여 주나** | 문장 몇 줄 |
| ② 접근 패턴 | 어떤 **쿼리**가 얼마나 자주, 얼마나 빨라야 하나 | 쿼리 목록 (읽기 · 쓰기 · 빈도) |
| ③ 저장소 선택 | Postgres · Mongo · Redis · Blob 중 어디에 | 2절의 표 |
| ④ 엔티티와 경계 | 무엇이 **독립된 것**이고 무엇이 **딸린 것**인가 | 엔티티 목록, 모듈 경계 |
| ⑤ 관계와 키 | 엔티티끼리 어떻게 이어지나, 무엇이 행을 식별하나 | ERD 초안 |
| ⑥ 제약 | DB 가 **스스로 막아야 할 잘못된 상태**는 | NOT NULL · UNIQUE · FK · CHECK |
| ⑦ 인덱스 | ②의 쿼리를 빠르게 하려면 | 인덱스 목록과 이유 |
| ⑧ 변화 | 나중에 이 모양이 **어떻게 바뀔 것 같나** | 마이그레이션 전략 (12절) |

**②가 핵심이다.** 같은 "대화 이력"이어도 "방 하나의 메시지를 시간순으로 읽는다"와 "모든 대화에서 키워드로 검색한다"는 설계가 전혀 다르다.
관계형 DB 는 접근 패턴을 **나중에 바꿔도 대체로 견디고**(인덱스만 추가), Cosmos DB 같은 문서형은 접근 패턴이 **파티션 키로 처음부터 박힌다**(`06-cosmos-db.md` 3절).
그래서 문서형일수록 ②를 더 앞에서 확실히 해야 한다.

> 접근 패턴을 적는 법: `"A 를 B 로 조회, 하루 N 회, 응답 M ms 이내"` 한 줄씩.
> 예) "대화방 하나의 최근 메시지 50개, 채팅 한 번에 1회, 100ms 이내", "테넌트 관리자가 지난 30일 토큰 사용량 합계, 하루 수 회, 2초 이내".

## 2. 어느 저장소에 넣나 — 데이터의 성격으로 묻는다

`07-our-stack.md` 2절의 규칙은 **"데이터의 성격을 먼저 본다"** 였다. 그걸 질문으로 바꾸면 설계 때 바로 쓸 수 있다.

| 질문 | 예 → | 아니오 → |
| --- | --- | --- |
| 틀리면 사고가 나나? (권한 · 과금 · 테넌트 설정) | **Postgres** | 다음 질문 |
| 여러 엔티티를 **한 번에 같이** 바꿔야 하나? (트랜잭션) | **Postgres** | 다음 질문 |
| 다른 데이터와 JOIN · 필터로 엮어서 조회하나? | **Postgres** | 다음 질문 |
| 쌓이기만 하고, 모양이 제각각이고, 한 덩어리로 읽고 쓰나? | **Mongo** (또는 Postgres `jsonb`) | 다음 질문 |
| 잃어도 되고 다시 만들 수 있나? 자주 읽나? | **Redis** | 다음 질문 |
| 크고 통째로 읽는 파일인가? | **Blob** (DB 에는 **위치만**) | 다시 ①로 |

**기본값은 Postgres 다.** 다른 저장소는 "Postgres 로 하면 곤란한 이유"를 **말로 설명할 수 있을 때만** 고른다. 이유는 보통 둘 중 하나다.

- **부하** — 쓰기가 폭주해서 권한 조회와 같은 DB 에 두면 서로를 느리게 한다
- **모양** — 프로바이더마다 · 고객사마다 JSON 모양이 달라서 고정 스키마가 안 맞는다

"Mongo 가 편해서"는 이유가 아니다. 두 번째 DB 를 쓰는 순간 **하나의 트랜잭션으로 못 묶는 비용**(`07-our-stack.md` 4절)이 생긴다.

### 경계에 걸치는 경우 — 주인을 정한다

한 개념이 두 저장소에 걸치면 (대화방은 Postgres, 메시지는 Mongo) **"주인(source of truth)"을 먼저 정한다.**

| | 주인 쪽 | 따라오는 쪽 |
| --- | --- | --- |
| 대화 | Postgres `conversations` (누구 것인가 · 권한 · 제목) | Mongo `messages` (내용) |
| 문서 | Postgres `documents` (메타 · ACL) | Blob (원본 파일), Postgres `chunks` (벡터) |
| 쓰기 순서 | 주인을 **먼저** 쓴다 | 실패하면 재시도 · 아웃박스 |
| 지울 때 | 주인을 지우면 따라오는 쪽도 **지워야 한다** — 이걸 빠뜨리면 고아 데이터 | |

따라오는 쪽에는 항상 **주인의 id 를 들고 다니게** 한다 (`messages.conversationId`). 거꾸로 주인이 따라오는 쪽의 id 목록을 들고 있으면 둘이 어긋난다.

> ❓ 입사 후 확인: 저장소 선택을 누가 정하나? (설계 리뷰에서? 아키텍트가?) "이건 Mongo 에" 라는 선례가 있나?

## 3. 엔티티와 경계 — 무엇이 한 덩어리인가

### 엔티티를 찾는 법

요구사항 문장에서 **명사**를 뽑고, 각각에 세 가지를 묻는다.

| 질문 | 예 | 결과 |
| --- | --- | --- |
| 혼자 존재하나, 다른 것에 딸려 있나? | 문서(혼자) · 문서의 청크(딸림) | 딸린 것은 부모 id 를 FK 로 |
| 고유한 식별자가 필요한가? | 사용자(필요) · 주소(값일 뿐) | 식별자 없이 값으로 비교하면 컬럼으로 |
| 시간이 지나며 **변하나, 사실로 남나?** | 고객 전화번호(변함) · 주문 당시 가격(사실) | 사실은 **복사해서 남긴다** (`01-relational-basics.md` 7절) |

### 경계 = 트랜잭션이 걸리는 단위

`01-backend-basics/06-architecture.md` 1절의 **애그리거트**는 "같이 바뀌어야 하는 것들의 묶음"이었다. DB 설계로 옮기면 이렇다.

```
한 트랜잭션 안에서 같이 바뀌는 것  →  같은 모듈, 같은 스키마, FK 로 이음
따로 바뀌어도 되는 것             →  다른 모듈, id 만 들고 있음 (FK 없음)
```

예) "문서 업로드" 는 `documents` 행과 `document_acl` 행이 **같이** 생겨야 한다 (둘 중 하나만 있으면 권한 없는 문서가 생긴다) → 같은 트랜잭션.
"문서가 업로드되면 임베딩을 만든다" 는 **나중에, 실패해도 재시도하면 되는** 일이다 → 이벤트로 넘기고, 결과 테이블은 따로.
(`01-backend-basics/05-long-running-jobs.md`)

이렇게 나눈 경계가 **모듈 경계**가 되고, 모듈 경계가 **스키마 경계**가 된다 (5절).

## 4. 키 설계 — 무엇이 행을 가리키나

| 선택 | 장점 | 단점 | 언제 |
| --- | --- | --- | --- |
| **`bigint` 자동 증가** | 작고 빠르다. 정렬이 곧 생성 순서 | URL 에 노출되면 개수를 짐작당한다. 서버 여러 대에서 미리 만들 수 없다. 환경 간 병합이 어렵다 | 내부 전용 테이블, 로그성 |
| **`uuid` v4 (랜덤)** | 어디서나 미리 만들 수 있다. 추측 불가 | 랜덤이라 인덱스 삽입 위치가 흩어져 **쓰기 · 캐시 효율이 떨어진다** | 거의 안 씀 |
| **`uuid` v7 (시간순)** | uuid 의 장점 + **앞부분이 시각이라 대체로 정렬된 삽입** | 16바이트. 생성 시각이 id 에 드러난다 | **새 설계의 기본 후보** |
| 자연키 (이메일, 사번) | 의미가 있다 | **바뀐다.** 바뀌면 이를 가리키는 FK 가 전부 따라 바뀌어야 한다 | 쓰지 않는다. 대신 `UNIQUE` 로만 |

**규칙: 기본 키는 의미 없는 값(대리키)으로, 의미 있는 값은 UNIQUE 제약으로.**
사번을 PK 로 썼는데 회사가 합병해서 사번 체계가 바뀌면, 사번을 FK 로 가진 테이블이 전부 영향을 받는다. `id` 는 안 바뀌고 `employee_no` 만 고치면 된다.

uuid v7 은 .NET 9 부터 `Guid.CreateVersion7()` 이, PostgreSQL 18 부터 `uuidv7()` 가 기본 제공된다.
v4 와 v7 의 차이는 인덱스(B-Tree)에 새 값이 **어디에 꽂히는가**다. v4 는 아무 데나 꽂혀서 인덱스 전체가 메모리에 올라와 있어야 빠르고,
v7 은 거의 끝에 꽂혀서 최근 부분만 메모리에 있으면 된다. 프론트의 배열에 `unshift` 가 `push` 보다 느린 것과 비슷한 이야기다.

**분산 환경의 이점:** 서버가 id 를 **DB 에 물어보지 않고** 만들 수 있다. 그러면 `INSERT` 전에 id 를 알 수 있어서,
"Postgres 에 행을 쓰고, 같은 id 로 Mongo 에 문서를 쓰고, 같은 id 를 이벤트에 싣는" 일이 순서 문제 없이 된다.

> ❓ 입사 후 확인: 이 레포의 실습 코드(`Pet.Id`)처럼 `Guid` 를 쓰나, `bigint` 를 쓰나? v4 인가 v7 인가? 외부에 노출하는 id 와 내부 PK 를 따로 두나?

## 5. 멀티테넌시를 스키마에 넣는 법

`01-backend-basics/04-auth.md` 5절은 테넌트 격리를 **접근 방식**(어떻게 거르나)으로 다뤘다. 여기서는 **테이블 모양**으로 어떻게 박느냐다.

### 5-1. 테넌트 소유 테이블에는 모두 `tenant_id`

```sql
CREATE TABLE documents (
  id         uuid PRIMARY KEY,
  tenant_id  uuid NOT NULL REFERENCES tenants(id),
  title      text NOT NULL,
  ...
);
CREATE INDEX ix_documents_tenant ON documents (tenant_id, created_at DESC);
```

두 가지가 따라온다.

| 규칙 | 이유 |
| --- | --- |
| **인덱스는 `tenant_id` 가 맨 앞** | 모든 쿼리에 `WHERE tenant_id = ...` 가 붙으니까. 복합 인덱스 순서 이야기 (`01-backend-basics/03-database.md` 1절) |
| **UNIQUE 도 `(tenant_id, 값)`** | `UNIQUE(email)` 이면 A 사에서 쓴 이메일을 B 사가 못 쓴다. 고객사가 늘수록 터진다 → `UNIQUE (tenant_id, email)` |

### 5-2. 자식 테이블도 `tenant_id` 를 들고, **복합 FK** 로 잇는다

```sql
-- 부모에 (tenant_id, id) 유니크를 만들어 둔다
ALTER TABLE documents ADD CONSTRAINT uq_documents_tenant_id UNIQUE (tenant_id, id);

CREATE TABLE document_chunks (
  id          uuid PRIMARY KEY,
  tenant_id   uuid NOT NULL,
  document_id uuid NOT NULL,
  content     text NOT NULL,
  -- 단순히 document_id 만 잇지 않고 tenant_id 까지 같이 잇는다
  FOREIGN KEY (tenant_id, document_id) REFERENCES documents (tenant_id, id)
);
```

**왜 이렇게까지 하나.** `document_id` 만 FK 로 걸면, 버그로 A 사의 청크가 B 사의 문서를 가리키는 행이 **DB 에 그대로 들어간다.**
복합 FK 면 "자식의 테넌트 = 부모의 테넌트"를 **DB 가 강제한다.** 앱 쿼리 필터(`HasQueryFilter`)와 RLS 가 **읽기**를 지킨다면,
복합 FK 는 **데이터가 애초에 잘못 이어지는 것**을 막는다. 세 겹의 안전망이다.

| 안전망 | 지키는 것 | 못 지키는 것 |
| --- | --- | --- |
| 앱의 전역 쿼리 필터 | 읽기에서 `tenant_id` 누락 | 필터를 끄는 코드, 원시 SQL |
| RLS | 앱이 뚫려도 읽기 · 쓰기 | 테이블 소유자 계정, 풀링된 커넥션의 잔여 설정 |
| 복합 FK | **교차 테넌트 참조** | 읽기 누락 |

### 5-3. 테넌트 정보 자체는 어디에

`tenants` 테이블은 그 자체가 테넌트 소유가 아니다 (`tenant_id` 가 자기 `id` 다). 테넌트별 설정은 두 층으로 나눈다.

| 종류 | 예 | 저장 |
| --- | --- | --- |
| 모든 테넌트가 같은 모양 | 이름, 플랜, 활성 여부, 사용 한도 | **컬럼** |
| 테넌트마다 모양이 다름 | 고객사별 커스텀 필드, 기능 플래그 묶음 | **`jsonb`** (8절) |

### 5-4. 큰 고객 하나가 DB 를 독점하면

행 단위 `tenant_id` 방식의 약점이다. 대응이 단계적으로 있다.

```
공유 DB · 공유 스키마 (tenant_id)     ← 시작은 이것
   ↓ 큰 고객이 생기면
테넌트별 스키마 / 테넌트별 DB          ← 격리 · 백업 · 데이터 위치 요구에 맞춰
```

설계 단계에서 할 일은 **"나중에 떼어 내기 쉽게"** 만드는 것이다 — 모든 테이블에 `tenant_id` 가 이미 있고, 쿼리가 항상 `tenant_id` 로 시작하면 특정 테넌트 데이터만 뽑아 다른 DB 로 옮기는 게 가능하다.
IDC 설치형 고객(`07-our-stack.md` 1절)은 애초에 **그 고객만의 DB** 이므로 `tenant_id` 가 하나뿐이다. 그래도 컬럼은 둔다 — 같은 코드가 돌아야 하니까.

> ❓ 입사 후 확인: 우리는 공유 DB + `tenant_id` 인가, 테넌트별 스키마 · DB 인가? 복합 FK 까지 쓰나? RLS 는 켜져 있나? `tenant_id` 가 없는 테이블(전역 설정)은 어떻게 구분하나?

## 6. 모듈러 모놀리스에서 스키마 나누기

`01-backend-basics/06-architecture.md` 6절의 규칙 2번 — **"다른 모듈의 테이블을 직접 조회하지 않는다. 모듈마다 DB 스키마(또는 테이블 접두어)를 나눈다"** — 를 실제 DB 로 옮기면 이렇다.

```
하나의 Postgres 데이터베이스
├─ 스키마 identity    : users, roles, tenants
├─ 스키마 documents   : documents, document_acl, document_chunks
├─ 스키마 chat        : conversations, conversation_members
└─ 스키마 llm         : llm_providers, llm_models, tenant_llm_settings
```

| 규칙 | 이유 |
| --- | --- |
| **모듈 하나 = 스키마 하나 = `DbContext` 하나** | 코드(모듈 경계)와 DB(스키마 경계)가 같은 선으로 그어진다 |
| **다른 모듈의 테이블로 FK 를 걸지 않는다** | FK 가 걸리면 그 모듈은 떼어 낼 수 없다. 나중에 MSA 로 갈 길이 막힌다 |
| **다른 모듈의 엔티티는 `id` 만 들고 있는다** | `documents.owner_user_id uuid` — 사용자 상세는 `identity` 모듈에 **물어본다** (Contracts · Mediator) |
| **JOIN 도 스키마를 넘지 않는다** | 넘는 순간 두 모듈의 테이블 구조가 서로에게 약속이 된다 |
| **마이그레이션 이력 테이블도 모듈별** | `HasDefaultSchema("documents")` 면 `__EFMigrationsHistory` 도 그 스키마 안에. 모듈마다 독립적으로 배포할 수 있다 |

### 트레이드오프 — FK 를 안 걸면 고아가 생긴다

`documents.owner_user_id` 에 FK 가 없으니 사용자를 지워도 DB 는 모른다.

| 대응 | 방법 |
| --- | --- |
| 사용자를 **지우지 않는다** | 소프트 삭제 · 비활성화. 대부분의 B2B 는 이쪽이다 |
| 이벤트로 알린다 | `UserDeactivated` 를 발행 → `documents` 모듈이 구독해서 정리 |
| 표시할 때만 확인 | 사용자가 없으면 "알 수 없는 사용자" 로 보이게 |

**같은 모듈 안에서는 FK 를 반드시 건다.** "모듈 사이에는 FK 가 없다"를 "FK 를 안 쓴다"로 오해하면 안 된다. 5-2 의 복합 FK 도 모듈 안의 이야기다.

### 읽기 모델은 예외다

"조회 화면용 JOIN 이 여러 모듈에 걸친다" 는 상황이 오면 (`01-backend-basics/06-architecture.md` 4절 CQRS) 두 길이 있다.

| | 방식 | 대가 |
| --- | --- | --- |
| 앱에서 조합 | 모듈마다 물어서 코드에서 합친다 | 호출이 늘고 N+1 위험 |
| 읽기 전용 뷰 · 사본 | 이벤트로 **화면용 사본 테이블**을 만든다 | 사본이 잠깐 어긋난다 (최종 일관성), 갱신 코드가 생긴다 |

처음부터 사본을 만들지 않는다. **느려진 것이 확인된 뒤에** 만든다.

> ❓ 입사 후 확인: 모듈마다 스키마를 쓰나, 한 스키마에 접두어인가, 아니면 서비스(MSA)마다 DB 가 따로인가? 모듈 사이 JOIN 이 실제로 있나? 이를 검사하는 아키텍처 테스트가 있나?

## 7. 관계를 모양으로 옮기는 패턴

`01-relational-basics.md` 3절의 1:1 · 1:N · N:M 은 이미 안다고 하고, 설계에서 **판단이 갈리는 지점**만 모았다.

### 7-1. N:M 에 속성이 붙으면 그 관계가 엔티티다

```
users ─┬─ user_roles ─┬─ roles        ← 단순 연결 (속성 없음)
       └──────────────┘

users ── conversation_members ── conversations
          (role: 'owner'|'viewer', joined_at, muted)  ← 속성이 있다 = 독립 엔티티
```

조인 테이블에 `joined_at` 이나 `role` 같은 컬럼이 **하나라도 생기면**, 그건 더 이상 "연결"이 아니라 이름을 가진 엔티티다. 이름을 붙이고 PK 를 주고 제약을 건다.
조인 테이블의 PK 는 `(user_id, role_id)` 복합키로 두면 같은 연결의 **중복을 막아 준다.**

### 7-2. "여러 종류의 것을 가리키는" 컬럼 — 다형성 연관

```
❌ comments(id, target_type, target_id, body)
   target_type = 'document' 이면 documents.id, 'conversation' 이면 conversations.id
```

`target_id` 에는 **FK 를 걸 수 없다.** 어느 테이블을 가리키는지가 행마다 다르기 때문이다. 그래서 존재하지 않는 id 가 들어가도 DB 는 모른다.

| 대안 | 모양 | 언제 |
| --- | --- | --- |
| **종류마다 테이블** | `document_comments`, `conversation_comments` | 종류가 적고 안 늘 때. FK 가 걸린다 |
| **nullable FK + CHECK** | `document_id`, `conversation_id` 둘 중 **정확히 하나**만 non-null (`CHECK (num_nonnulls(document_id, conversation_id) = 1)`) | 종류가 둘셋이고 JOIN 하고 싶을 때 |
| **다형성 유지** | `target_type + target_id` | 종류가 계속 늘고 FK 보다 유연성이 중요할 때. **앱이 정합성을 책임진다** |

기본은 첫 번째나 두 번째다. 세 번째는 "FK 를 포기한다"는 걸 알고 고른다.

### 7-3. 상태 — 현재 값 vs 이력

```
현재만:  documents.status = 'indexed'
이력도:  documents.status  +  document_status_history(document_id, from, to, at, by)
```

"현재 상태만 알면 되나, **언제 어떻게 거기까지 왔는지**도 알아야 하나"를 묻는다. 감사 · 분쟁 · 디버깅이 필요한 데이터(권한 변경, 문서 처리 단계)는 이력을 남긴다.
이력 테이블은 **쌓이기만 한다** — 수정 · 삭제를 허용하지 않는 것이 설계 의도다 (`UPDATE` 권한을 안 주거나 앱에서 막는다).

상태 값은 `text + CHECK` 또는 PG enum 으로 제한한다 (`01-relational-basics.md` 8절). 값이 **자주 늘면** enum 은 변경이 번거로우니 `text + CHECK` 나 참조 테이블이 낫다.

| | 장점 | 단점 |
| --- | --- | --- |
| PG `enum` | 저장이 작고 타입이 분명 | 값 **삭제**가 안 되고, 값 추가도 트랜잭션 제약이 있다 |
| `text + CHECK` | 변경이 쉽다 (제약만 바꾼다) | 오타를 CHECK 가 막아 주는 정도 |
| 참조 테이블 + FK | 값에 **속성**(표시 이름, 정렬, 비활성)을 달 수 있다 | JOIN · 테이블이 하나 더 |

### 7-4. 트리와 계층 — 폴더, 조직도

| 방식 | 모양 | 적합 |
| --- | --- | --- |
| 부모 id (`parent_id`) | 가장 단순. 한 단계는 쉽다 | 깊이가 얕거나, 재귀 쿼리(`WITH RECURSIVE`) 를 감수할 때 |
| 경로 문자열 (`/a/b/c`) | "하위 전체" 조회가 `LIKE '/a/b/%'` 로 쉽다 | 이동 시 하위 경로를 전부 갱신해야 함 |
| `ltree` 확장 | 경로 연산을 인덱스로 | PostgreSQL 전용 |

문서 폴더나 조직도는 대개 **부모 id + 재귀 쿼리**로 시작해서 충분하다. 깊이가 수십 단계인 경우는 거의 없다.

## 8. `jsonb` 는 언제 쓰나

`01-backend-basics/03-database.md` 6절에서 관계형 vs 문서형을 봤다. `jsonb` 는 그 **사이**에 있다 — 한 테이블 안의 문서형 컬럼이다.

| `jsonb` 가 맞다 | 컬럼이 맞다 |
| --- | --- |
| **행마다 모양이 다르다** (고객사별 커스텀 필드) | 모든 행이 같은 모양 |
| 통째로 읽고 쓴다 | `WHERE` · `JOIN` · `ORDER BY` 에 쓴다 |
| 외부에서 받은 응답 원본을 보관 | 값에 **제약**을 걸고 싶다 (NOT NULL, FK, 범위) |
| 설정 묶음, 플래그 묶음 | 통계 · 집계 대상이다 |

**규칙: 필터 조건이 되는 값은 꺼내서 컬럼으로 둔다.** `jsonb` 안의 값으로 자주 검색하게 됐다면 그건 이미 컬럼이라는 신호다.

```sql
-- 처음엔 이렇게 시작해도
metadata jsonb        -- {"department": "HR", "confidential": true}

-- department 로 자주 거르게 되면 컬럼으로 승격
department text,
metadata   jsonb      -- 나머지 모양이 제각각인 것만 남긴다
```

`jsonb` 의 함정은 **스키마가 없다는 것이 곧 아무 검증이 없다는 것**이라는 점이다.
오타 난 키(`departmnet`) 가 들어가도 DB 는 모른다. 앱에서 타입(C# `record`)으로 읽고 쓰는 경로를 **하나로** 좁히고, 중요한 값은 `CHECK` 로 DB 에서도 막는다.

## 9. 제약은 DB 에도 건다

"앱에서 검증하는데 DB 에까지 왜?" — 앱 하나만 DB 를 건드리는 게 아니기 때문이다.
마이그레이션 스크립트, 데이터 보정 쿼리, 다른 서비스, 사람이 직접 친 `UPDATE`. **앱 검증은 앱을 거치는 길만 막는다.**

| 제약 | 막는 것 | 예 |
| --- | --- | --- |
| `NOT NULL` | 빠진 값 | `documents.title` — **기본은 NOT NULL**. NULL 을 허용하려면 이유가 있어야 한다 |
| `UNIQUE` | 중복 | `UNIQUE (tenant_id, email)` |
| `FOREIGN KEY` | 없는 걸 가리키기 | 단, `ON DELETE` 를 **의식적으로** 정한다 (아래) |
| `CHECK` | 말이 안 되는 값 | `CHECK (end_at > start_at)`, `CHECK (chunk_size > 0)` |

### `ON DELETE` 를 정한다

| 옵션 | 동작 | 언제 |
| --- | --- | --- |
| `RESTRICT` (기본 성향) | 자식이 있으면 부모를 못 지운다 | **기본으로 이쪽.** 실수로 데이터가 사라지는 걸 막는다 |
| `CASCADE` | 부모를 지우면 자식도 지운다 | 자식이 부모 없이 의미 없는 **소유** 관계 (문서 → 청크) |
| `SET NULL` | 자식의 FK 를 NULL 로 | 부모가 사라져도 자식이 의미 있을 때 |

`CASCADE` 는 편하지만 **연쇄가 눈에 안 보인다.** 테넌트 하나를 지웠는데 `CASCADE` 가 이어져 수백만 행이 한 트랜잭션에서 지워지면 DB 가 멈춘다.
그래서 "소유 관계의 바로 아래"까지만 `CASCADE`, 큰 덩어리는 **배치로 나눠서 지우는 작업**으로 처리한다.

### 설계 단계에서 놓치기 쉬운 것

| 항목 | 질문 |
| --- | --- |
| 길이 | `text` 인가, 제한이 있는가. 사용자 입력이면 **한도**가 있어야 한다 (`CHECK (length(title) <= 200)`) |
| 시각 | `timestamptz` 인가. "날짜만" 이면 `date` |
| 금액 · 수량 | `numeric` 인가. 단위(통화)가 같이 저장되나 |
| 불리언 | 정말 두 값뿐인가? `is_active` 가 나중에 `suspended` · `pending` 이 되는 일이 흔하다 → **상태 컬럼**이 낫지 않은가 |

## 10. 지우기 · 보관 · 감사

`01-relational-basics.md` 8절의 소프트 삭제를 **설계 결정**으로 다시 본다. 삭제는 한 방식이 아니라 데이터마다 다른 선택이다.

| 방식 | 의미 | 쓰는 곳 |
| --- | --- | --- |
| **소프트 삭제** `deleted_at` | 지운 표시만. 복구 가능 | 사용자가 만든 것 (문서, 대화방). 실수 복구 · 감사 |
| **하드 삭제** | 진짜로 지운다 | 개인정보 삭제 요청, 임시 데이터 |
| **TTL / 보관 기간** | 기간이 지나면 자동으로 | 로그 · 대화 기록. 고객사별로 기간이 다름 |
| **익명화** | 행은 남기되 식별 정보를 지운다 | 통계는 남기고 개인정보만 지워야 할 때 |

### 개인정보와 소프트 삭제는 충돌한다

고객이 "내 데이터를 지워 달라"고 하면 소프트 삭제로는 **지운 게 아니다.** 설계 때 미리 정해 둔다.

- 어떤 테이블에 **개인정보**가 있는가 (이름, 이메일, 전화번호, 대화 내용)
- 삭제 요청이 오면 **어디까지 하드 삭제**하고 어디를 **익명화**하나
- **백업과 Mongo · 검색 인덱스 · Blob** 에도 사본이 있다 — 한 곳만 지우면 지운 게 아니다

### 감사 로그는 별도로

"누가 · 언제 · 무엇을 · 어떻게 바꿨나" 는 `updated_at` 한 컬럼으로 안 된다.

| 방식 | 모양 | 비고 |
| --- | --- | --- |
| 컬럼 2개 | `created_by`, `updated_by` | 최소한. 마지막 변경자만 안다 |
| **감사 테이블** | `audit_log(tenant_id, actor_id, action, entity, entity_id, before, after, at)` | 변경 이력 전체. `before`/`after` 는 `jsonb` 로 두면 모든 엔티티를 한 테이블로 받는다 |
| 이력 테이블 | 엔티티마다 `*_history` | 특정 엔티티의 상태 변화를 정밀하게 |

감사 로그는 **쌓이기만 하고 수정 · 삭제가 없다.** 이 성격이 `07-our-stack.md` 4절 Mongo 의 "쌓이기만 하고 모양이 제각각" 조건과 겹쳐서, 양이 많으면 Mongo 로 빼기도 한다.
단 **권한 변경처럼 틀리면 안 되는 감사 기록**은 원 데이터와 **같은 트랜잭션**으로 남겨야 해서 Postgres 에 둔다.

> ❓ 입사 후 확인: 삭제 정책이 어떻게 정해져 있나 (고객사 계약마다 다른가)? 감사 로그는 어디에 쌓이나? 금융권 고객사의 보관 · 파기 요구사항은?

## 11. 설계 예시 — 문서 RAG 의 DB 를 처음부터

위 기준을 이 제품(문서 RAG · 에이전트)의 한 기능에 끝까지 적용해 본다. **형식을 보는 연습**이다. 실제 랭코드 스키마가 아니다.

### ① 요구사항

> 테넌트 관리자가 문서를 올리면, 문서가 청크로 나뉘어 임베딩되고,
> 사용자는 **자기가 볼 수 있는 문서에서만** 질문에 맞는 청크를 검색한다. 대화 내용은 저장한다.

### ② 접근 패턴

| # | 쿼리 | 빈도 | 목표 |
| --- | --- | --- | --- |
| Q1 | 사용자가 볼 수 있는 문서 중 질문과 비슷한 청크 10개 | 질문마다 | 200ms |
| Q2 | 테넌트의 문서 목록 (페이지네이션, 상태 필터) | 화면마다 | 100ms |
| Q3 | 문서 업로드 + 권한 부여 | 가끔 | 트랜잭션 |
| Q4 | 대화방의 최근 메시지 50개 | 질문마다 | 100ms |
| Q5 | 테넌트의 월별 토큰 사용량 합계 | 하루 몇 회 | 2초 |

### ③ 저장소 (2절의 질문대로)

| 데이터 | 저장소 | 이유 |
| --- | --- | --- |
| 문서 메타 · ACL | Postgres | 권한 = 틀리면 사고. Q1 이 ACL 과 벡터를 **한 쿼리**로 |
| 청크 + 벡터 | Postgres (pgvector) | Q1 때문에. 권한 필터와 벡터 검색을 SQL 하나로 |
| 원본 PDF | Blob | 크고 통째로. DB 에는 **경로만** |
| 대화방 | Postgres | 주인 · 멤버십 |
| 메시지 · 인용 · 도구 호출 | Mongo | 쌓이기만 하고 모양이 제각각, Q4 는 `conversationId` 한 키 |
| 토큰 사용량 | Postgres 집계 테이블 (Q5) | 합계를 **쿼리**해야 하니 관계형. 원본 이벤트는 Mongo |

### ④~⑤ 엔티티 · 키 · 관계 (스키마 `documents`)

```sql
CREATE TABLE documents (
  id             uuid PRIMARY KEY,                       -- v7
  tenant_id      uuid NOT NULL,
  title          text NOT NULL CHECK (length(title) <= 200),
  blob_path      text NOT NULL,                          -- 전체 URL 이 아니라 상대 경로
  status         text NOT NULL DEFAULT 'uploaded'
                 CHECK (status IN ('uploaded','parsing','indexed','failed')),
  metadata       jsonb NOT NULL DEFAULT '{}',            -- 고객사별 모양이 다른 것만
  created_by     uuid NOT NULL,                          -- identity 모듈의 user id (FK 없음, 6절)
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now(),
  deleted_at     timestamptz,                            -- 소프트 삭제
  UNIQUE (tenant_id, id)                                 -- 자식의 복합 FK 용
);

CREATE TABLE document_acl (
  tenant_id    uuid NOT NULL,
  document_id  uuid NOT NULL,
  principal_type text NOT NULL CHECK (principal_type IN ('user','group')),
  principal_id   uuid NOT NULL,                          -- 다형성이지만 종류가 둘이라 허용 (7-2)
  PRIMARY KEY (document_id, principal_type, principal_id),
  FOREIGN KEY (tenant_id, document_id) REFERENCES documents (tenant_id, id) ON DELETE CASCADE
);

CREATE TABLE document_chunks (
  id             uuid PRIMARY KEY,
  tenant_id      uuid NOT NULL,
  document_id    uuid NOT NULL,
  ordinal        int  NOT NULL,                          -- 문서 안에서의 순서
  content        text NOT NULL,
  embedding      vector(1536) NOT NULL,
  embedding_model text NOT NULL,                         -- 어떤 모델로 만든 벡터인가
  UNIQUE (document_id, ordinal),
  FOREIGN KEY (tenant_id, document_id) REFERENCES documents (tenant_id, id) ON DELETE CASCADE
);
```

짚을 것:

| 결정 | 근거 |
| --- | --- |
| `blob_path` 는 상대 경로 | 전체 URL 을 저장하면 스토리지를 갈아 끼울 때 전부 고쳐야 한다 (`07-our-stack.md` 8절) |
| `status` 는 `text + CHECK` | 처리 단계가 늘 수 있다. enum 이면 변경이 번거롭다 (7-3) |
| `metadata` 는 `jsonb` | 고객사마다 다른 필드. 필터로 자주 쓰는 `department` 는 나중에 **컬럼으로 승격** (8절) |
| `embedding_model` 컬럼 | **임베딩 모델을 바꾸면 벡터를 전부 다시 만들어야** 한다. 어느 청크가 옛 모델인지 알아야 점진적으로 갈아 낄 수 있다 (`03-rag/02-chunking-embedding.md`) |
| 청크는 `CASCADE` | 청크는 문서 없이 의미가 없는 소유 관계 (9절) |
| `document_acl` 에 FK 는 문서로만 | `principal_id` 는 다른 모듈(identity)의 id — FK 를 걸지 않는다 (6절) |

### ⑥~⑦ 인덱스 — Q 마다 하나씩 이유를 댄다

```sql
-- Q2. 문서 목록: 테넌트 → 상태 → 최신순. 소프트 삭제된 건 제외
CREATE INDEX ix_documents_list ON documents (tenant_id, status, created_at DESC)
  WHERE deleted_at IS NULL;                              -- 부분 인덱스

-- Q1. 벡터 검색: 근사 최근접 이웃 인덱스
CREATE INDEX ix_chunks_embedding ON document_chunks
  USING hnsw (embedding vector_cosine_ops);

-- Q1. 권한 필터: principal 로 거꾸로 "이 사용자가 볼 수 있는 문서" 를 찾는다
CREATE INDEX ix_acl_principal ON document_acl (principal_type, principal_id);
```

**인덱스는 쿼리가 있어야 만든다.** "혹시 몰라서" 만든 인덱스는 쓰기 속도를 깎기만 한다 (`01-backend-basics/03-database.md` 1절 "대가").

Q1 은 설계상 가장 까다롭다. **벡터 인덱스(HNSW)와 권한 필터를 같이 쓰면**, 인덱스가 먼저 가까운 후보를 뽑은 뒤 필터가 걸러서 결과가 **10개보다 적게** 나올 수 있다.
사용자가 볼 수 있는 문서가 전체의 1% 뿐일 때 특히 그렇다. 이 문제를 어떻게 푸는지(사전 필터 · 후보 수 늘리기 · 테넌트별 분할)는 `03-rag/04-enterprise-rag.md` 에서 이어진다.
**이런 문제는 테이블을 그리는 단계가 아니라 ②의 접근 패턴을 적는 단계에서 보인다.** 그래서 ②가 먼저다.

### ⑧ 변화를 예상한다

| 앞으로 있을 법한 변화 | 지금 설계가 견디나 |
| --- | --- |
| 임베딩 모델 교체 (차원이 달라짐) | `vector(1536)` 은 차원이 박혀 있다 → 새 차원의 **새 컬럼 / 새 테이블**을 만들고 점진적으로 채운다. `embedding_model` 이 그 단서 |
| 문서 처리 단계 추가 | `status` 의 CHECK 만 바꾸면 된다 |
| 특정 고객이 문서 수천만 건 | `tenant_id` 로 파티셔닝하거나 테넌트별 DB 로 떼어 낸다 (5-4) — 모든 쿼리가 `tenant_id` 로 시작하니 가능 |
| 문서 폴더 구조 | `folder_id` 컬럼 + `folders(parent_id)` 를 **추가**하면 된다 — 기존 것을 안 건드린다 |

## 12. 변경에 강하게 — 마이그레이션까지가 설계다

설계한 모양은 **영원하지 않다.** 서버가 여러 대이고 배포 중에 옛 버전과 새 버전이 **같이 떠 있는 시간**이 있으므로(`07-db-infra/05-infra.md`),
스키마 변경은 "옛 코드도 새 스키마에서 돌고, 새 코드도 옛 스키마에서 돌 수 있게" 해야 한다.

### 컬럼 이름 바꾸기가 위험한 이유

```
1. DB 에서 컬럼 이름 변경 (title → name)
2. 아직 옛 코드(title 을 읽음)가 떠 있는 서버 몇 대 → 전부 에러
```

**확장 → 이전 → 수축(expand · migrate · contract)** 세 단계로 나눠서 배포한다.

| 단계 | DB | 코드 | 배포 |
| --- | --- | --- | --- |
| ① 확장 | `name` 컬럼을 **추가** (title 은 그대로) | 새 코드가 **두 컬럼에 다 쓴다**, title 에서 읽는다 | 배포 1 |
| ② 이전 | 기존 행의 `name` 을 `title` 로 **채운다** (배치) | 새 코드가 `name` 에서 읽는다 | 배포 2 |
| ③ 수축 | `title` 컬럼 **삭제** | `title` 을 더는 안 쓴다 | 배포 3 |

한 번에 끝낼 수 있는 일을 세 번에 나누는 이유는 **중간 어느 시점에 멈춰도 서비스가 돌기 때문**이다. 롤백도 된다.

### 안전한 변경 / 위험한 변경

| 안전 | 위험 |
| --- | --- |
| nullable 컬럼 **추가** | NOT NULL 컬럼 추가 (기본값 없이) — 옛 코드의 `INSERT` 가 실패 |
| 새 테이블 추가 | 컬럼 이름 · 타입 변경, 컬럼 삭제 |
| 인덱스 추가 (`CREATE INDEX CONCURRENTLY`) | 큰 테이블의 일반 `CREATE INDEX` — **쓰기를 막는다** |
| 기본값 있는 컬럼 추가 (최근 PG 는 빠름) | 제약(`CHECK`, `FK`) 을 이미 있는 큰 테이블에 바로 추가 — 전체를 훑는다 |

`NOT NULL` 을 나중에 추가해야 한다면 ① nullable 로 추가 ② 값 채우기 ③ `CHECK (col IS NOT NULL) NOT VALID` 로 새 행부터 검사 ④ `VALIDATE CONSTRAINT` 로 기존 행 검사, 순서로 쪼갠다.

### 설계할 때 이미 해 둘 수 있는 것

| 습관 | 효과 |
| --- | --- |
| **지우지 말고 추가해라** | 컬럼 삭제 · 이름 변경이 필요한 상황 자체를 줄인다 |
| 값에 **단위를 이름에 넣는다** (`timeout_ms`, `price_krw`) | 단위가 바뀌면 컬럼이 새로 생기지, 의미가 몰래 바뀌지 않는다 |
| 상태는 `bool` 대신 **상태 컬럼** | 두 값이 세 값이 될 때 타입을 못 바꾸는 사고를 막는다 |
| ERD 가 아니라 **마이그레이션 파일이 진실** | 코드와 함께 리뷰 · 되돌리기 가능 (`01-backend-basics/03-database.md` 7절) |

> ❓ 입사 후 확인: 마이그레이션 전략은? (배포 시 자동 적용 / 수동 승인 / 별도 파이프라인) 다운타임을 허용하나? 롤백은 어떻게?

## 13. 설계 리뷰 체크리스트

새 테이블이나 컬럼을 추가하는 PR 을 만들거나 리뷰할 때 이 질문을 위에서부터 던진다.

**저장소와 경계**
- [ ] 이 데이터는 Postgres 에 두는 게 맞나? 다른 곳이라면 "Postgres 로는 안 되는 이유"를 설명할 수 있나?
- [ ] 두 저장소에 걸치면 **주인**이 정해져 있고, 지울 때 따라오는 쪽도 지우나?
- [ ] 모듈 경계를 넘는 FK · JOIN 이 없나?

**멀티테넌시**
- [ ] 테넌트 소유 테이블에 `tenant_id` 가 있나?
- [ ] 인덱스가 `tenant_id` 로 시작하나? `UNIQUE` 가 `(tenant_id, ...)` 인가?
- [ ] 자식 테이블이 **같은 테넌트의 부모**만 가리키게 막혀 있나?

**모양**
- [ ] PK 가 의미 없는 값인가? 의미 있는 값은 `UNIQUE` 로 걸었나?
- [ ] 한 사실이 **한 곳에만** 있나? 복사본이 있다면 "그 시점의 사실" 이라는 이유가 있나?
- [ ] 필터 · JOIN 에 쓰는 값이 `jsonb` 안에 숨어 있지 않나?
- [ ] `bool` 이 나중에 세 값이 될 가능성은 없나?

**제약**
- [ ] `NOT NULL` 이 기본이고, NULL 허용에는 이유가 있나?
- [ ] 말이 안 되는 값을 `CHECK` 가 막나? 문자열 길이 한도가 있나?
- [ ] `ON DELETE` 를 의식적으로 정했나? `CASCADE` 의 범위가 좁나?

**시간 · 삭제 · 감사**
- [ ] 시각이 `timestamptz` 인가? `created_at` · `updated_at` 이 있나?
- [ ] 삭제 방식(소프트 · 하드 · TTL · 익명화)이 정해져 있나? 소프트 삭제면 `UNIQUE` 가 부분 인덱스인가?
- [ ] 개인정보가 있나? 삭제 요청 시 어디까지 지우나?

**성능 · 변화**
- [ ] 접근 패턴(Q) 마다 이를 받쳐 주는 인덱스가 있나? 반대로 **쿼리 없이 만든 인덱스**는 없나?
- [ ] 이 변경이 **옛 코드와 새 코드가 같이 떠 있는 동안** 안전한가? 큰 테이블에 락을 거는 DDL 이 없나?
- [ ] 이 테이블이 100배 커지면 어디가 먼저 아픈가?

## 14. 정리

| 단계 | 한 줄 |
| --- | --- |
| 설계 순서 | **쓰임새(접근 패턴) → 저장소 → 엔티티 · 경계 → 키 · 관계 → 제약 → 인덱스 → 변화** |
| 저장소 | 기본은 Postgres. 다른 곳은 "부하" 나 "모양" 이유를 말로 설명할 수 있을 때 |
| 경계 | 같이 바뀌는 것 = 같은 트랜잭션 = 같은 모듈 · 스키마. 모듈 사이엔 id 만 |
| 키 | 의미 없는 uuid(v7) 가 PK, 의미 있는 값은 UNIQUE |
| 테넌트 | `tenant_id` + 복합 UNIQUE + 복합 FK + 쿼리 필터 + RLS, 여러 겹 |
| `jsonb` | 행마다 모양이 다르고 통째로 읽는 것만. 필터에 쓰이면 컬럼으로 |
| 제약 | 앱 검증과 별개로 DB 가 **스스로** 막게 |
| 변화 | 확장 → 이전 → 수축으로, 옛 코드와 새 코드가 같이 떠 있어도 안전하게 |

**한 문장으로:** DB 설계는 테이블을 그리는 일이 아니라, **"이 데이터를 어떻게 읽고 쓰고 바꿀 것인가"를 먼저 정하고 그 답을 DB 가 스스로 지키게 만드는 일**이다.

## 스스로 답해보기

1. 테이블을 그리기 전에 **접근 패턴**을 먼저 적는 이유는? 관계형과 Cosmos DB 에서 이 순서의 중요도가 어떻게 다른가?
2. 새 데이터를 Postgres 에 둘지 Mongo 에 둘지 정할 때 던지는 질문을 세 개 말해 보라. "Mongo 가 편해서"가 왜 이유가 안 되나?
3. 대화방은 Postgres, 메시지는 Mongo 에 둔다. **주인**은 어느 쪽이고, 대화방을 지울 때 무엇을 해야 하나?
4. 사번이나 이메일을 PK 로 쓰지 않는 이유는? 대신 어떻게 하나?
5. `UNIQUE(email)` 이 멀티테넌트에서 문제가 되는 이유는? 어떻게 고치나?
6. 자식 테이블에 `document_id` 로만 FK 를 걸면 어떤 잘못된 데이터가 DB 에 들어갈 수 있나? **복합 FK** 는 이걸 어떻게 막나?
7. 모듈러 모놀리스에서 다른 모듈의 테이블로 FK 를 걸지 않는 이유는? 그러면 생기는 고아 데이터는 어떻게 다루나?
8. N:M 조인 테이블에 `joined_at` 컬럼이 생겼다. 이건 무엇이 된 것이고, 설계상 무엇을 해야 하나?
9. `comments(target_type, target_id)` 형태의 **다형성 연관**에는 FK 를 걸 수 없다. 대안을 두 가지 들어 보라.
10. `jsonb` 에 넣어도 되는 것과 컬럼으로 뽑아야 하는 것의 기준은?
11. `ON DELETE CASCADE` 는 언제 쓰고, 언제 위험한가?
12. 고객이 "내 개인정보를 지워 달라"고 했다. 소프트 삭제로는 왜 부족하고, 어디까지 확인해야 하나?
13. 컬럼 이름을 `title` → `name` 으로 한 번에 바꾸면 안 되는 이유는? **확장 → 이전 → 수축** 순서로 설명해 보라.
14. 청크 테이블에 `embedding_model` 컬럼을 두는 이유는? 임베딩 모델을 바꾸는 날 이 컬럼이 어떻게 도움이 되나?
