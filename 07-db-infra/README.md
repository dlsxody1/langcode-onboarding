## 왜 이걸 따로 배워야 하나

프론트에서는 이게 전부 **누군가 이미 해 둔 것**이었다.

| 프론트에서 당연했던 것 | 실제로는 누가 해 주고 있었나 |
| --- | --- |
| `fetch` 하면 데이터가 온다 | 백엔드가 DB 에서 조인·필터·페이지네이션을 했다 |
| TanStack Query 가 캐시해 준다 | 서버도 같은 고민(언제 버리나)을 Redis 로 한다 |
| 요청이 실패하면 재시도 버튼 | 서버는 **사용자 없이** 재시도 여부를 스스로 결정해야 한다 |
| 콘솔에 에러가 보인다 | 서버 10대 중 어디서 났는지 찾으려면 로그 설계가 필요하다 |
| Vercel 에 배포하면 끝 | 컨테이너 · 환경 변수 · 비밀값 · DB 마이그레이션 순서 |

**랭코드 특유의 이유:** 고객사 시스템을 붙이는 회사다. 남의 API 는 느리고, 가끔 죽고, 호출 제한이 있다.
그리고 LLM API 자체가 **가장 느리고 가장 자주 429 를 주는 외부 시스템**이다.
03 문서(장애에 버티는 패턴)가 이 회사에서는 이론이 아니라 매일의 일이다.

## 반드시 갖고 갈 감각 세 가지

1. **서버는 여러 대라고 가정한다.** 메모리에 둔 것(캐시, 세션, 카운터, 큐)은 다른 서버에서 안 보이고, 재시작하면 사라진다.
2. **모든 외부 호출에는 타임아웃이 있어야 한다.** 타임아웃 없는 호출 하나가 커넥션 풀과 스레드를 말려 서비스 전체를 세운다.
3. **로그는 나중에 검색할 사람을 위해 쓴다.** "에러 났음"이 아니라 *어떤 요청 · 어떤 테넌트 · 어떤 단계*에서 났는지.
