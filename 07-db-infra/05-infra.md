# 인프라 지도

인프라를 직접 구축할 일은 당장 없을 수 있다. 하지만 **"이 요청이 어디를 거쳐 어디서 실행되는가"** 를 그릴 수 없으면,
"로컬에서는 되는데 운영에서 안 돼요"를 혼자 풀 수 없다. 이 문서는 그 지도를 그린다.

---

## 1. 요청 하나가 서버에 닿기까지

```
브라우저
   │  ① DNS          app.langcode.io → IP 주소
   ▼
CDN / WAF            ② 정적 파일은 여기서 바로 응답. 공격 패턴 차단
   │
   ▼
로드밸런서 / 게이트웨이   ③ TLS(HTTPS) 종료. 살아 있는 서버 중 하나로 보낸다
   │
   ├──▶ API 서버 #1 ─┐
   ├──▶ API 서버 #2 ─┼──▶ DB · Redis · Vector DB · 큐 · 외부 API
   └──▶ API 서버 #3 ─┘
                     ④ 같은 코드가 여러 대에서 동시에 돈다
```

| 구간 | 여기서 생기는 전형적인 문제 |
| --- | --- |
| ① DNS | 도메인을 바꿨는데 캐시 때문에 일부 사용자만 옛 주소로 간다 |
| ② CDN | 배포했는데 옛 JS 가 내려온다 (캐시 무효화 누락) |
| ③ 로드밸런서 | **SSE 스트리밍이 중간에 끊긴다** — 유휴 타임아웃·버퍼링 설정 (`05-realtime-ui/`) |
| ③ 로드밸런서 | 서버가 보는 클라이언트 IP 가 전부 로드밸런서 IP 다 → `X-Forwarded-For` 를 읽어야 한다 |
| ④ 서버 여러 대 | 메모리에 둔 것이 서버마다 다르다 (다음 절) |

## 2. 무상태 (Stateless) — 수평 확장의 조건

트래픽이 늘면 **서버를 더 큰 것으로 바꾸거나(수직 확장)**, **같은 서버를 더 띄운다(수평 확장)**.
클라우드에서는 거의 항상 수평 확장이다. 그런데 서버를 늘리는 순간 이런 코드가 전부 깨진다.

| 서버 메모리에 둔 것 | 서버가 여러 대가 되면 | 어디로 옮기나 |
| --- | --- | --- |
| 로그인 세션 | 다른 서버로 가면 로그아웃 | Redis · 토큰(JWT) |
| `IMemoryCache` | 서버마다 다른 값 | Redis / `HybridCache` (`02-caching.md`) |
| 레이트 리밋 카운터 | 한도가 서버 수만큼 늘어난다 | Redis · 게이트웨이 (`03-resilience.md`) |
| `Channel<T>` 작업 큐 | 재배포하면 사라진다 | DB 테이블 · Service Bus |
| 업로드한 파일을 로컬 디스크에 | 다른 서버에서 못 찾는다 | Blob Storage |
| `static` 변수에 저장한 상태 | 서버마다 다르고, 재시작하면 초기화 | 위 중 하나 |
| SignalR 연결 | 서버 A 에 붙은 사용자에게 B 가 못 보낸다 | Redis 백플레인 · Azure SignalR Service |

**원칙: 서버는 언제든 죽고, 새로 뜨고, 개수가 바뀐다고 가정한다.**
요청을 처리하는 데 필요한 상태는 전부 **서버 바깥**(DB · Redis · Blob)에 둔다. 그러면 서버는 그냥 "코드를 실행하는 상자"가 된다.

로컬 개발에서는 서버가 1대라서 이 문제가 **절대 안 보인다.** 그래서 운영에서 처음 터진다.

## 3. 컨테이너 — "내 컴퓨터에서는 되는데"를 끝내는 상자

컨테이너 이미지 = **앱 + 런타임 + 의존성을 통째로 묶은 실행 단위.** 어디서 돌려도 같다.

```dockerfile
# .NET API 의 전형적인 Dockerfile — 2단계 빌드
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build          # ① 빌드용 (SDK 포함, 무겁다)
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:9.0                # ② 실행용 (런타임만, 가볍다)
WORKDIR /app
COPY --from=build /app .
ENTRYPOINT ["dotnet", "MyApi.dll"]
```

프론트로 치면 `npm run build` 결과물과 Node 런타임을 같이 포장한 것이다.

| 용어 | 뜻 |
| --- | --- |
| 이미지 | 실행할 수 있는 포장 (읽기 전용). 레지스트리(ACR, Docker Hub)에 올린다 |
| 컨테이너 | 이미지를 실행한 것. **꺼지면 안에 쓴 파일은 사라진다** → 2절 무상태 |
| `docker compose` | 여러 컨테이너(API + Postgres + Redis)를 한 번에 띄우는 로컬 개발용 도구 |
| Kubernetes (AKS) | 컨테이너 수백 개를 배치·재시작·확장하는 오케스트레이터 |

README 의 `docker run ... pgvector/pgvector:pg17` 이 바로 이것이다. Postgres 를 설치하지 않고 이미지를 받아 실행했다.

## 4. Azure 에서 무엇이 무엇인가

랭코드는 MS 파트너다. Azure 서비스 이름이 대화에 자주 나온다. **역할로 묶어서 기억한다.**

### 코드를 실행하는 곳

| 서비스 | 한 줄 | 언제 |
| --- | --- | --- |
| **App Service** | 코드나 컨테이너를 올리면 서버 관리를 대신 해 준다 | 웹 API 의 가장 흔한 출발점 |
| **Container Apps** | 컨테이너를 올리면 확장·HTTPS 를 알아서 | 컨테이너 기반, Kubernetes 는 부담스러울 때 |
| **AKS** (Kubernetes) | 직접 다 제어 | 서비스가 많고 전담 인원이 있을 때 |
| **Functions** | 이벤트가 오면 함수 하나만 실행 | 큐 메시지 처리, 예약 작업 |

### 데이터를 두는 곳

| 서비스 | 대응하는 것 |
| --- | --- |
| Azure Database for **PostgreSQL** (Flexible Server) | 관리형 Postgres (+ pgvector 확장) |
| **Azure SQL** | 관리형 SQL Server |
| **Cosmos DB** | 문서형 DB (MongoDB 호환 API 제공) |
| **Azure Cache for Redis** | 관리형 Redis |
| **Blob Storage** | 파일 (업로드 원문, PDF, 이미지) |
| **Azure AI Search** | 하이브리드 검색 + 벡터 + 한국어 분석기 (`03-rag/03` 1절) |
| **Service Bus** | 메시지 큐 (`03-resilience.md` 6절) |

### 그 외

| 서비스 | 역할 |
| --- | --- |
| **Key Vault** | 비밀값 보관 (다음 절) |
| **Entra ID** (구 Azure AD) | 사용자·서비스 인증 |
| **Azure OpenAI** | 데이터가 Azure 밖으로 안 나가는 OpenAI 모델 (`03-rag/02` 6절) |
| **Application Insights** | 로그·트레이스·메트릭 (`04-observability.md`) |
| **Front Door / API Management** | 전역 진입점 · WAF · 레이트 리밋 · API 게이트웨이 |

**"관리형(managed)"의 의미:** 백업·패치·장애 조치·복제를 클라우드가 해 준다. 비싸지만, 그 일을 사람이 하는 비용보다는 싸다.

> ❓ 입사 후 확인: API 는 어디서 도나(App Service? Container Apps? AKS?) 고객사 온프레미스 설치는 어떤 형태로 나가나(컨테이너 이미지? 설치 패키지?)

## 5. 설정과 비밀값 — 코드에 넣지 않는다

```
코드        : 환경과 무관하게 같다
설정        : 환경마다 다르다 (DB 주소, 외부 API URL, 기능 플래그)
비밀값      : 환경마다 다르고 + 노출되면 사고 (DB 비밀번호, API 키)
```

| 환경 | 설정은 어디서 | 비밀값은 어디서 |
| --- | --- | --- |
| 로컬 | `appsettings.Development.json` | `dotnet user-secrets` (Git 밖에 저장) |
| 운영 | 환경 변수 · App Configuration | **Key Vault** |

`02-csharp-dotnet/02-aspnet-core.md` 4절의 설정 시스템이 이 값들을 하나로 합쳐 준다. 코드는 어디서 왔는지 몰라도 된다.

### Managed Identity — 비밀번호 자체를 없앤다

```
❌ 연결 문자열에 비밀번호:  Host=...;Username=app;Password=Sup3r!
✅ Managed Identity:        "이 App Service 는 이 DB 에 접근 가능" 을 Azure 가 보증
```

Azure 가 서버(App Service 등)에 **신분증**을 발급하고, DB · Key Vault · Blob 이 그 신분증을 확인한다.
**코드와 설정 어디에도 비밀번호가 없다.** 유출될 비밀번호가 없으니 교체할 일도 없다. 새로 짜는 Azure 코드에서는 이게 기본값이다.

**Git 에 비밀값을 커밋했다면** 커밋을 지우는 걸로 끝나지 않는다. 이미 누군가 받아 갔다고 가정하고 **즉시 키를 교체(rotate)** 한다.

## 6. 환경과 배포 파이프라인

```
feature 브랜치 ─PR─▶ main ─▶ CI ─▶ dev ─▶ staging ─▶ production
                            │
                            ├─ 빌드 · 테스트 · 린트
                            ├─ (RAG) 평가셋 Recall@k 임계값 (03-rag/03 4절)
                            └─ 컨테이너 이미지 빌드 → 레지스트리에 푸시
```

| 환경 | 목적 | 데이터 |
| --- | --- | --- |
| dev | 개발자가 자유롭게 | 가짜 |
| staging | **운영과 최대한 같게.** 배포 전 마지막 확인 | 운영 사본(마스킹) 또는 현실적인 가짜 |
| production | 실제 사용자 | 진짜 |

### 배포와 DB 마이그레이션의 순서

배포 중에는 **구버전 서버와 신버전 서버가 동시에 돈다**(롤링 배포). 그래서:

```
① 마이그레이션 먼저 (컬럼 추가처럼 구버전 코드가 깨지지 않는 변경만)
② 새 코드 배포 — 구버전과 신버전이 잠시 공존해도 둘 다 동작
③ 다음 배포에서 안 쓰는 컬럼 정리
```

`01-backend-basics/03-database.md` 7절의 **확장/수축 패턴**이 이 순서를 지키는 방법이다.
"컬럼 이름 변경"을 한 번에 배포하면, 배포 중 몇 분 동안 구버전 서버가 없는 컬럼을 찾다가 500 을 낸다.

### 헬스 체크

```csharp
builder.Services.AddHealthChecks().AddNpgSql(connectionString);   // AddNpgSql 은 AspNetCore.HealthChecks.NpgSql 패키지
app.MapHealthChecks("/health");
```

로드밸런서는 이 주소를 주기적으로 찔러서 **응답이 없는 서버로는 요청을 보내지 않는다.**
새 버전이 뜨자마자 죽으면 트래픽이 안 가므로, 배포 실패가 장애로 번지지 않는다.

## 7. DB 운영 — 앱 개발자도 알아야 할 것

### 커넥션 수 × 서버 수

```
Npgsql 기본 Max Pool Size = 100   (01/03 4절)
API 서버 10대                      → 최대 1,000 커넥션
PostgreSQL 기본 max_connections = 100
```

**서버를 늘렸더니 DB 가 커넥션을 거부한다.** 수평 확장할 때 가장 흔히 놓치는 계산이다.
대응: 풀 크기를 서버 수에 맞춰 줄이거나, 앞에 **PgBouncer** 같은 커넥션 풀러를 둔다.

### 읽기 복제본 (Read Replica)

```
쓰기 ──▶ Primary ──(복제, 수십 ms ~ 수 초 지연)──▶ Replica ◀── 읽기
```

읽기를 복제본으로 보내면 Primary 부하가 준다. 대가는 **복제 지연**이다.

```
사용자가 이름을 수정 (Primary 에 씀)
   → 바로 목록을 다시 불러옴 (Replica 에서 읽음)
   → 아직 복제가 안 돼서 옛 이름이 보인다    ← "저장이 안 됐어요" 버그 리포트
```

**"방금 쓴 것을 바로 읽는" 화면은 Primary 에서 읽어야 한다.** 프론트가 낙관적 업데이트로 이 틈을 가려주는 경우도 많다.

### 백업과 복구

| 용어 | 뜻 |
| --- | --- |
| 백업 | 정기적인 전체 사본 |
| **PITR** (특정 시점 복구) | "어제 14:32 상태로" 되돌리기. 관리형 DB 는 대부분 기본 제공 |
| **RPO** | 최대 얼마만큼의 데이터를 잃어도 되나 (5분? 하루?) |
| **RTO** | 복구하는 데 최대 얼마나 걸려도 되나 |

**복구해 본 적 없는 백업은 백업이 아니다.** 실제로 복원이 되는지 주기적으로 확인한다.

> ❓ 입사 후 확인: 운영 DB 에 개발자가 직접 접근할 수 있나? 데이터를 고쳐야 할 때의 절차는? 백업 보관 기간은?

## 8. 정리 — "로컬에서는 되는데 운영에서 안 돼요" 체크리스트

```
[ ] 서버 메모리에 상태를 두지 않았나? (세션 · 캐시 · 카운터 · 큐 · 파일 · static)    → 2절
[ ] 환경마다 다른 값을 코드에 박아 두지 않았나?                                   → 5절
[ ] 비밀값이 환경에 실제로 들어가 있나? (Key Vault 권한 · Managed Identity)        → 5절
[ ] 마이그레이션이 운영에 적용됐나? 구버전 코드와 공존 가능한가?                    → 6절
[ ] 로드밸런서·프록시가 스트리밍을 버퍼링하거나 끊지 않나?                         → 1절
[ ] 클라이언트 IP 를 X-Forwarded-For 로 읽고 있나?                              → 1절
[ ] 방금 쓴 데이터를 복제본에서 읽고 있지 않나?                                   → 7절
[ ] 외부 호출에 타임아웃이 있나? 운영망에서 그 주소에 접근 가능한가? (방화벽)        → 03 문서
```

## 스스로 답해보기

1. 로드밸런서 뒤에서 서버가 보는 클라이언트 IP 가 전부 같은 이유는? 진짜 IP 는 어디서 얻나?
2. 업로드 파일을 서버 로컬 디스크에 저장했다. 서버가 3대가 되면 무슨 일이 일어나나?
3. 컨테이너 안에 쓴 파일은 컨테이너를 재시작하면 어떻게 되나?
4. Managed Identity 를 쓰면 연결 문자열에서 무엇이 사라지나? 그게 왜 좋은가?
5. 컬럼 이름 변경을 마이그레이션 하나로 배포하면 롤링 배포 중에 무슨 일이 일어나나?
6. API 서버를 3대에서 10대로 늘렸더니 DB 에러가 났다. 무엇을 계산해 봐야 하나?
7. 이름을 수정하고 저장했는데 목록에는 옛 이름이 보인다. 읽기 복제본과 어떤 관계가 있나?
8. Git 에 API 키를 커밋했다는 걸 발견했다. 커밋을 지우면 끝나나?
