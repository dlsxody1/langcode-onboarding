# 요즘 풀스택은 어떻게 일하는가

"프론트 + 백엔드를 둘 다 한다"가 아니다. **경계를 어떻게 다루느냐**가 달라진 것이다.

여기서 경계는 프론트와 백엔드가 만나는 지점, 곧 API 다. 어떤 주소에 어떤 형태의 요청을 보내면 어떤 형태의 응답이 오는지에 대한 약속이다. 예전에는 이 약속을 백엔드가 정해 문서로 넘겼다면, 지금은 양쪽이 함께 정하고 도구로 강제한다.

---

## 1. 무엇이 달라졌나

| 예전 | 지금 |
| --- | --- |
| 프론트가 API 명세를 기다린다 | **스키마를 먼저 합의**하고 양쪽이 동시에 시작 |
| 백엔드가 응답 형태를 정한다 | 화면에 필요한 형태를 프론트가 제안하고 협상 |
| 타입을 손으로 맞춘다 | **OpenAPI → 타입 자동 생성** |
| 통합은 배포 직전에 | 매일 |
| "이건 백엔드 일" | **한 사람이 한 기능을 끝까지** (vertical slice) |

핵심은 **수직 슬라이스**다. 레이어별로 사람을 나누지 않고, 기능 하나를
DB 스키마부터 화면까지 한 사람이 관통한다. 20명 규모 회사에서는 이게 기본이다.

케이크를 생각하면 이름이 이해된다. 가로로 자르면 시트, 크림, 과일 층이 따로 나오고 세로로 자르면 모든 층이 조금씩 들어간 한 조각이 나온다. "견적서 승인 기능"이라면 DB 에 상태 컬럼 추가, 승인 API, 권한 검사, 목록 화면의 승인 버튼까지가 한 조각이다. 층마다 담당자가 다르면 층 사이를 오가는 대기 시간이 생긴다. 한 사람이 한 조각을 맡으면 그 대기가 사라진다.

## 2. 계약(contract)을 먼저 정한다

계약은 1장에서 말한 경계의 약속을 기계가 읽을 수 있는 형태로 적어 둔 것이다. 보통 OpenAPI 문서가 그 역할을 한다. OpenAPI 는 "이 API 에는 이런 경로가 있고 각 경로는 이런 파라미터를 받아 이런 JSON 을 돌려준다"를 JSON 이나 YAML 로 적는 표준 형식이다. Swagger 라는 이름으로 더 익숙할 수 있다. Swagger 는 OpenAPI 의 옛 이름이자 관련 도구 이름이다.

```
① 화면 시안/요구사항을 보고 "무엇이 필요한가" 정리
② OpenAPI 스키마 초안을 같이 작성            ← 여기가 합의점
③ 백엔드: 구현 시작 / 프론트: 타입 생성 + 목으로 화면 시작
④ 실제 연결
```

③의 목(mock)은 실제 서버 대신 약속된 형태의 가짜 응답을 돌려주는 대역이다. MSW 같은 도구로 계약에 맞는 가짜 응답을 만들어 두면 백엔드가 완성되기 전에도 화면을 끝까지 만들 수 있다. 계약이 같으니 ④에서 목을 실제 서버로 바꿔 끼우기만 하면 된다.

### 타입 생성

```bash
# .NET 이 OpenAPI 를 내보내고, 프론트가 그걸로 타입을 만든다
npx openapi-typescript http://localhost:5000/openapi/v1.json -o src/shared/api/schema.d.ts
```

ASP.NET Core 는 컨트롤러와 DTO 클래스를 읽어 OpenAPI 문서를 자동으로 만든다. 위 주소가 그 문서다. `openapi-typescript` 는 그 문서를 읽어 TypeScript 타입 파일로 바꾼다. C# 의 `PetDto` 클래스가 TS 의 `components["schemas"]["PetDto"]` 타입이 되는 식이다.

`openapi-fetch` 를 쓰면 경로·파라미터·응답 타입이 전부 추론된다.

```ts
const { data, error } = await client.GET("/api/pets/{id}", { params: { path: { id } } });
//     ^ PetDto 로 추론됨
```

**이게 되면 백엔드가 필드명을 바꿨을 때 프론트 빌드가 깨진다.** 런타임에 발견하는 것보다 훨씬 낫다.
CI 에서 스키마 생성 → 타입 재생성 → 타입체크를 돌리면 계약 위반이 자동으로 막힌다.

예를 들어 백엔드가 `PetDto.name` 을 `PetDto.displayName` 으로 바꿨다고 하자. 타입 생성이 없으면 화면에 이름이 빈칸으로 나오고 누군가 눈으로 발견할 때까지 아무도 모른다. 타입 생성이 있으면 `pet.name` 을 쓰는 모든 줄에서 `tsc` 가 에러를 낸다. CI(지속적 통합, PR 마다 빌드와 테스트를 자동으로 돌리는 파이프라인)에 이 단계를 넣으면 그 PR 은 머지되기 전에 멈춘다.

> 내가 i18n 에서 한 것과 같은 구조다. **사람이 맞추던 것을 파이프라인이 강제하게 만든다.**

### 실제로 협상하는 것들

| 논점 | 판단 기준 |
| --- | --- |
| 리소스 중심 vs 화면 중심 API | 화면 하나에 5번 호출해야 하면 잘못 나눈 것. **BFF 성격의 집계 엔드포인트**를 둘 수 있다 |
| 오버페칭 | 응답에 안 쓰는 필드가 절반이면 DTO 를 나눈다 (`PetSummaryDto` / `PetDetailDto`) |
| 페이지네이션 방식 | 무한 스크롤이면 커서, 페이지 번호 UI 면 offset |
| 에러 포맷 | 필드별 검증 오류를 프론트가 폼에 매핑할 수 있는 형태인가 |
| 날짜·시간 | **항상 UTC ISO 8601 로 주고받고, 표시만 로컬** |
| null vs 빈 배열 | 목록은 절대 null 을 주지 않는다 |

표의 항목을 하나씩 풀어 둔다.

리소스 중심 API 는 `/pets`, `/owners`, `/visits` 처럼 데이터 종류별로 엔드포인트를 나눈 것이다. 깔끔하지만 "진료 대시보드" 화면 하나에 다섯 개를 모두 불러야 할 수 있다. BFF(Backend For Frontend)는 특정 화면이나 클라이언트에 맞춰 여러 데이터를 모아 한 번에 돌려주는 엔드포인트, 또는 그런 역할의 서버 계층이다. `/dashboard/summary` 하나가 다섯 번의 호출을 대신한다. 화면이 실제로 어떻게 쓰이는지에 맞추는 것이니 타협이 아니라 설계의 일부다.

오버페칭(over-fetching)은 화면에 필요 없는 데이터까지 받아 오는 것이다. 목록 화면에 이름과 사진만 필요한데 진료 기록 전체가 딸려 오면 응답이 무겁다. 그래서 목록용 `PetSummaryDto` 와 상세용 `PetDetailDto` 를 나눈다. 같은 이유로 DB 엔티티를 API 응답으로 그대로 내보내지 않는다. 엔티티에 컬럼이 하나 추가되면 의도치 않게 응답에도 노출되기 때문이다(`01-backend-basics/02-layers-and-di.md` 2장).

offset 페이지네이션은 "앞에서 40개 건너뛰고 20개"처럼 위치로 자른다. 페이지 번호 UI 와 잘 맞는다. 단점은 사용자가 보는 사이 앞쪽에 새 항목이 들어오면 다음 페이지에서 같은 항목이 또 나온다는 점이다. 커서(cursor) 페이지네이션은 "마지막으로 본 항목 다음부터 20개"처럼 기준점으로 자른다. 서버가 응답에 다음 요청용 커서 값을 실어 주고 클라이언트는 그 값을 그대로 돌려보낸다. 무한 스크롤에서 중복이나 누락이 없다.

에러 포맷은 ASP.NET Core 의 ProblemDetails 형식을 쓰는 경우가 많다. 검증 실패라면 `errors` 안에 `{ "email": ["이메일 형식이 아닙니다"] }` 처럼 필드 이름별로 메시지가 들어온다. 이 필드 이름이 폼 필드 이름과 같으면 react-hook-form 의 `setError` 로 그대로 꽂을 수 있다. 협상할 것은 필드 이름 규칙(camelCase 인지)과 중첩 필드 표기다(`02-csharp-dotnet/02-aspnet-core.md` 6\~7장).

ISO 8601 은 `2025-03-14T05:30:00Z` 같은 날짜·시간 표기 표준이다. 끝의 `Z` 는 UTC 라는 뜻이다. 서버와 DB 는 UTC 로만 저장하고 주고받는다. 한국 시간으로 바꾸는 건 화면에 그리는 순간에만 한다. 서버마다 시간대가 달라도, 해외 고객사가 생겨도 데이터가 꼬이지 않는다.

목록에 null 을 주지 않는 이유는 프론트의 모든 `.map()` 앞에 null 검사를 강제하기 때문이다. 결과가 없으면 `[]` 를 준다. "없음"과 "아직 모름"을 구분해야 하는 경우라면 그 의미를 별도 필드로 표현한다.

## 3. 로컬 개발 환경

한 명이 전체를 띄울 수 있어야 한다.

```yaml
# docker-compose.yml — 이게 없으면 온보딩에 하루가 더 걸린다
services:
  db:
    image: pgvector/pgvector:pg17
    environment: { POSTGRES_PASSWORD: dev }
    ports: ["5432:5432"]
  # 필요하면 redis, azurite(Azure Storage 에뮬레이터) 등
```

```bash
docker compose up -d
dotnet ef database update
dotnet watch run          # 백엔드
pnpm dev                  # 프론트
```

Docker Compose 는 여러 컨테이너를 설정 파일 하나로 같이 띄우는 도구다. DB 를 직접 설치하지 않고 `docker compose up -d` 한 줄로 버전까지 맞춘 Postgres 를 띄운다. `pgvector` 이미지는 벡터 검색 확장이 들어 있는 Postgres 로, RAG 의 벡터 저장소로 쓴다(`03-rag/01-pipeline.md`). `dotnet ef database update` 는 코드에 있는 마이그레이션을 DB 에 적용해 테이블을 만든다. `dotnet watch run` 은 파일이 바뀌면 다시 빌드하고 재시작한다. 프론트의 개발 서버와 같은 역할이다. 컨테이너 자체는 `07-db-infra/05-infra.md` 3장에서 다룬다.

> ❓ 입사 후 확인: 로컬에서 전체 스택을 띄우는 문서가 있나? 없으면 **내가 만들 첫 기여가 될 수 있다.**
> (새로 들어온 사람만이 "무엇이 막히는지"를 안다. 두 번째 사람이 들어오기 전에 적어두면 가치가 크다)

## 4. AI 중심 개발 워크플로우

공고 공통사항에 적혀 있는 항목. **이미 하고 있는 일이지만, 새 스택에서 다시 세팅해야 한다.**

### 들어가서 처음 며칠에 할 것

1. **저장소에 CLAUDE.md 가 있나 확인** — 없으면 내가 읽으면서 만든다
2. **빌드·테스트·린트를 한 줄로 돌리는 명령** 을 확인하고 적어둔다. AI 가 자기 작업을 검증할 수 있게
3. **하지 말아야 할 것** 을 명문화 — 마이그레이션 자동 생성 금지, 특정 디렉터리 수정 금지 등
4. **프로젝트 구조와 의존 방향** 을 적어둔다 (`.csproj` 참조 그래프)

CLAUDE.md 는 Claude Code 가 작업을 시작할 때 자동으로 읽는 저장소 안내서다. 사람 신입에게 주는 온보딩 문서를 AI 용으로 쓴 것이라고 보면 된다. 2번이 특히 중요하다. AI 가 코드를 고친 뒤 `dotnet build && dotnet test` 를 스스로 돌려 결과를 확인할 수 있어야 "고쳤다고 말만 하는" 상황을 막는다.

4번의 `.csproj` 는 .NET 프로젝트 하나의 설정 파일이다. `package.json` 과 비슷하게 의존 패키지와 다른 프로젝트 참조를 적는다. "Api 프로젝트는 Application 을 참조하고 Application 은 Domain 만 참조한다" 같은 방향을 적어 두면 AI 가 계층을 거꾸로 참조하는 코드를 쓰는 일이 줄어든다(`02-csharp-dotnet/04-reading-a-dotnet-codebase.md`).

### C#/.NET 에서 AI 를 쓸 때 다른 점

| | TS 프로젝트 | .NET 프로젝트 |
| --- | --- | --- |
| 타입 검증 | `tsc --noEmit` | `dotnet build` — **컴파일이 곧 타입 검증** |
| 포맷 | prettier | `dotnet format` |
| 정적 분석 | eslint | Roslyn 분석기 (`.editorconfig`) |
| 테스트 | vitest | `dotnet test` |
| **피드백 루프** | 빠름 | **느리다** — 빌드가 수 초\~수십 초 |

Roslyn 은 C# 컴파일러의 이름이다. Roslyn 분석기는 컴파일 과정에 끼어들어 코드 스타일과 잠재적 버그를 경고하는 규칙 모음이다. eslint 처럼 규칙을 켜고 끄는 설정은 `.editorconfig` 에 적는다. 별도 린트 명령 없이 빌드할 때 같이 돈다.

**마지막 줄이 실제로 워크플로우를 바꾼다.** TS 는 저장할 때마다 타입 에러를 보지만,
.NET 은 빌드를 돌려야 안다. 그래서 **AI 에게 한 번에 더 큰 단위를 맡기고, 빌드로 한 번에 검증**하는
리듬이 맞는다. TS 에서처럼 잘게 반복하면 빌드 대기에 시간을 다 쓴다.

피드백 루프는 "코드를 고친다 → 결과를 확인한다"의 한 바퀴다. TS 에서는 에디터의 언어 서버가 저장 즉시 빨간 줄을 그어 주니 한 바퀴가 1초도 안 걸린다. .NET 도 IDE 가 일부를 바로 보여 주지만 확실한 검증은 빌드다. 솔루션이 크면 빌드 한 번에 수십 초가 걸린다. 예를 들어 "DTO 필드 하나 추가 → 빌드 → 매핑 수정 → 빌드 → 컨트롤러 수정 → 빌드" 로 쪼개 AI 에게 시키면 빌드 대기만 세 번이다. "DTO, 매핑, 컨트롤러, 테스트까지 한 번에 바꾸고 마지막에 빌드와 테스트로 확인" 으로 묶어 맡기는 편이 빠르다.

### 이 스택에서 AI 가 특히 잘하는 것 / 못하는 것

| 잘함 | 못함 |
| --- | --- |
| C# 문법 · LINQ 변환 | **이 프로젝트가 왜 이렇게 설계됐는지** |
| 보일러플레이트 (DTO, 매핑, 컨트롤러) | 고객사별 예외 사정 |
| 테스트 코드 초안 | EF Core 가 만드는 SQL 의 성능 영향 ← **직접 봐야 한다** |
| 에러 메시지 해석 | 프롬프트 품질 (자기가 만든 프롬프트를 자기가 평가 못 함) |
| 문서 요약 · 코드 설명 | 마이그레이션의 운영 영향 |

**"EF Core 가 만드는 SQL"** 을 강조하는 이유: AI 가 문법적으로 완벽한 LINQ 를 써주지만
그게 N+1 을 만드는지는 모른다. SQL 로깅을 켜고 직접 보는 습관이 유일한 방어다.

N+1 은 목록 1번 조회한 뒤 항목마다 관련 데이터를 1번씩 더 조회해 쿼리가 N+1 번 나가는 문제다. 반려동물 50마리 목록을 가져온 다음 반복문에서 `pet.Owner.Name` 을 읽으면, 설정에 따라 보호자 조회가 50번 따로 나간다. 코드는 한 줄짜리 반복문이라 멀쩡해 보이고 로컬의 데이터 5건으로는 느리지도 않다. 운영 데이터에서야 드러난다. `Include` 로 한 번에 가져오거나 필요한 필드만 `Select` 로 뽑아 해결한다(`02-csharp-dotnet/03-ef-core.md`, `07-db-infra/01-relational-basics.md` 4장).

## 5. 배포와 운영

| | |
| --- | --- |
| **CI** | PR 마다 빌드 + 테스트 + 린트. .NET 은 `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes` |
| **환경** | dev / staging / prod. 고객사 온프레미스가 있으면 설치본도 |
| **마이그레이션** | 배포 파이프라인에서 자동 적용할지, 승인 후 수동일지 |
| **비밀값** | Azure Key Vault + Managed Identity. **OIDC 페더레이션은 이미 해봤다** |
| **관측** | Application Insights / OpenTelemetry. 로그·메트릭·트레이스 |
| **에러 추적** | Sentry 등. 이미 해봤다 |
| **피처 플래그** | 고객사별로 기능을 켜고 끄는 데 쓴다. B2B 에서 특히 유용 |

몇 가지만 덧붙인다. 온프레미스(on-premises)는 우리 클라우드가 아니라 고객사 자체 서버에 설치해 운영하는 형태다. 금융권처럼 데이터를 밖으로 내보낼 수 없는 고객사에서 흔하다. Managed Identity 는 Azure 가 앱에 신원을 부여해 비밀번호나 키 없이 Key Vault, DB 에 접근하게 하는 기능이다(`07-db-infra/05-infra.md` 5장). 피처 플래그(feature flag)는 코드는 배포해 두고 기능의 켜짐 여부를 설정값으로 정하는 방식이다. 고객사 A 에만 새 기능을 먼저 열어 보는 식으로 쓴다. 관측의 세 신호는 `07-db-infra/04-observability.md` 에서 자세히 다룬다.

**AI 제품 고유:** 프롬프트와 모델 버전도 배포 대상이다.
- 프롬프트를 코드에 두면 배포가 필요하고, DB 에 두면 즉시 바꿀 수 있지만 버전 관리가 어렵다
- 모델을 바꾸면 **기존 평가셋을 다시 돌려야 한다** (→ `03-rag/03-retrieval-quality.md`)

프롬프트 한 줄 수정은 코드 변경과 똑같이 동작을 바꾼다. 그래서 어느 쪽에 두든 "어떤 실행이 어떤 프롬프트 버전으로 돌았는지"를 추적 기록에 남긴다(`04-agent/01-what-is-an-agent.md` 6장의 프롬프트 버전).

## 6. 스스로 답해보기 / 첫 주 체크리스트

```
[ ] 로컬에서 전체 스택을 띄울 수 있다

[ ] SQL 로깅을 켜고 화면 하나가 만드는 쿼리를 봤다
[ ] 작은 PR 하나를 머지했다 (오타 수정이라도)

```

**마지막 두 개가 가장 중요하다.** 새로 들어온 사람만이 "무엇이 설명되어 있지 않은지"를 안다.
그 감각은 2주면 사라진다.
