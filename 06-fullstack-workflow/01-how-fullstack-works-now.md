# 요즘 풀스택은 어떻게 일하는가

"프론트 + 백엔드를 둘 다 한다"가 아니다. **경계를 어떻게 다루느냐**가 달라진 것이다.

---

## 1. 무엇이 달라졌나

| 예전 | 지금 |
| --- | --- |
| 프론트가 API 명세를 기다린다 | **스키마를 먼저 합의**하고 양쪽이 동시에 시작 |
| 백엔드가 응답 형태를 정한다 | 화면에 필요한 형태를 프론트가 제안하고 협상 |
| 타입을 손으로 맞춘다 | **OpenAPI → 타입 자동 생성** |
| 통합은 배포 직전에 | 매일 |
| "이건 백엔드 일" | **한 사람이 한 기능을 끝까지** (vertical slice) |

핵심은 **수직 슬라이스**다. 레이어별로 사람을 나누지 않고, 기능 하나를
DB 스키마부터 화면까지 한 사람이 관통한다. 20명 규모 회사에서는 이게 기본이다.

---

## 2. 계약(contract)을 먼저 정한다

```
① 화면 시안/요구사항을 보고 "무엇이 필요한가" 정리
② OpenAPI 스키마 초안을 같이 작성            ← 여기가 합의점
③ 백엔드: 구현 시작 / 프론트: 타입 생성 + 목으로 화면 시작
④ 실제 연결
```

### 타입 생성

```bash
# .NET 이 OpenAPI 를 내보내고, 프론트가 그걸로 타입을 만든다
npx openapi-typescript http://localhost:5000/openapi/v1.json -o src/shared/api/schema.d.ts
```

`openapi-fetch` 를 쓰면 경로·파라미터·응답 타입이 전부 추론된다.

```ts
const { data, error } = await client.GET("/api/pets/{id}", { params: { path: { id } } });
//     ^ PetDto 로 추론됨
```

**이게 되면 백엔드가 필드명을 바꿨을 때 프론트 빌드가 깨진다.** 런타임에 발견하는 것보다 훨씬 낫다.
CI 에서 스키마 생성 → 타입 재생성 → 타입체크를 돌리면 계약 위반이 자동으로 막힌다.

> 내가 i18n 에서 한 것과 같은 구조다. **사람이 맞추던 것을 파이프라인이 강제하게 만든다.**

### 실제로 협상하는 것들

| 논점 | 판단 기준 |
| --- | --- |
| 리소스 중심 vs 화면 중심 API | 화면 하나에 5번 호출해야 하면 잘못 나눈 것. **BFF 성격의 집계 엔드포인트**를 둘 수 있다 |
| 오버페칭 | 응답에 안 쓰는 필드가 절반이면 DTO 를 나눈다 (`PetSummaryDto` / `PetDetailDto`) |
| 페이지네이션 방식 | 무한 스크롤이면 커서, 페이지 번호 UI 면 offset |
| 에러 포맷 | 필드별 검증 오류를 프론트가 폼에 매핑할 수 있는 형태인가 |
| 날짜·시간 | **항상 UTC ISO 8601 로 주고받고, 표시만 로컬** |
| null vs 빈 배열 | 목록은 절대 null 을 주지 않는다 |

## 3. 로컬 개발 환경

한 명이 전체를 띄울 수 있어야 한다.

```yaml
# docker-compose.yml — 이게 없으면 온보딩에 하루가 더 걸린다
services:
  db:
    image: pgvector/pgvector:pg17
    environment: { POSTGRES_PASSWORD: dev }
    ports: ["5432:5432"]
  # 필요하면 redis, azurite(Azure Storage 에뮬레이터) 등
```

```bash
docker compose up -d
dotnet ef database update
dotnet watch run          # 백엔드
pnpm dev                  # 프론트
```

> ❓ 입사 후 확인: 로컬에서 전체 스택을 띄우는 문서가 있나? 없으면 **내가 만들 첫 기여가 될 수 있다.**
> (새로 들어온 사람만이 "무엇이 막히는지"를 안다. 두 번째 사람이 들어오기 전에 적어두면 가치가 크다)

## 4. AI 중심 개발 워크플로우

공고 공통사항에 적혀 있는 항목. **이미 하고 있는 일이지만, 새 스택에서 다시 세팅해야 한다.**

### 들어가서 처음 며칠에 할 것

1. **저장소에 CLAUDE.md 가 있나 확인** — 없으면 내가 읽으면서 만든다
2. **빌드·테스트·린트를 한 줄로 돌리는 명령** 을 확인하고 적어둔다. AI 가 자기 작업을 검증할 수 있게
3. **하지 말아야 할 것** 을 명문화 — 마이그레이션 자동 생성 금지, 특정 디렉터리 수정 금지 등
4. **프로젝트 구조와 의존 방향** 을 적어둔다 (`.csproj` 참조 그래프)

### C#/.NET 에서 AI 를 쓸 때 다른 점

| | TS 프로젝트 | .NET 프로젝트 |
| --- | --- | --- |
| 타입 검증 | `tsc --noEmit` | `dotnet build` — **컴파일이 곧 타입 검증** |
| 포맷 | prettier | `dotnet format` |
| 정적 분석 | eslint | Roslyn 분석기 (`.editorconfig`) |
| 테스트 | vitest | `dotnet test` |
| **피드백 루프** | 빠름 | **느리다** — 빌드가 수 초~수십 초 |

**마지막 줄이 실제로 워크플로우를 바꾼다.** TS 는 저장할 때마다 타입 에러를 보지만,
.NET 은 빌드를 돌려야 안다. 그래서 **AI 에게 한 번에 더 큰 단위를 맡기고, 빌드로 한 번에 검증**하는
리듬이 맞는다. TS 에서처럼 잘게 반복하면 빌드 대기에 시간을 다 쓴다.

### 이 스택에서 AI 가 특히 잘하는 것 / 못하는 것

| 잘함 | 못함 |
| --- | --- |
| C# 문법 · LINQ 변환 | **이 프로젝트가 왜 이렇게 설계됐는지** |
| 보일러플레이트 (DTO, 매핑, 컨트롤러) | 고객사별 예외 사정 |
| 테스트 코드 초안 | EF Core 가 만드는 SQL 의 성능 영향 ← **직접 봐야 한다** |
| 에러 메시지 해석 | 프롬프트 품질 (자기가 만든 프롬프트를 자기가 평가 못 함) |
| 문서 요약 · 코드 설명 | 마이그레이션의 운영 영향 |

**"EF Core 가 만드는 SQL"** 을 강조하는 이유: AI 가 문법적으로 완벽한 LINQ 를 써주지만
그게 N+1 을 만드는지는 모른다. SQL 로깅을 켜고 직접 보는 습관이 유일한 방어다.

## 5. 배포와 운영

| | |
| --- | --- |
| **CI** | PR 마다 빌드 + 테스트 + 린트. .NET 은 `dotnet build`, `dotnet test`, `dotnet format --verify-no-changes` |
| **환경** | dev / staging / prod. 고객사 온프레미스가 있으면 설치본도 |
| **마이그레이션** | 배포 파이프라인에서 자동 적용할지, 승인 후 수동일지 |
| **비밀값** | Azure Key Vault + Managed Identity. **OIDC 페더레이션은 이미 해봤다** |
| **관측** | Application Insights / OpenTelemetry. 로그·메트릭·트레이스 |
| **에러 추적** | Sentry 등. 이미 해봤다 |
| **피처 플래그** | 고객사별로 기능을 켜고 끄는 데 쓴다. B2B 에서 특히 유용 |

**AI 제품 고유:** 프롬프트와 모델 버전도 배포 대상이다.
- 프롬프트를 코드에 두면 배포가 필요하고, DB 에 두면 즉시 바꿀 수 있지만 버전 관리가 어렵다
- 모델을 바꾸면 **기존 평가셋을 다시 돌려야 한다** (→ `03-rag/03-retrieval-quality.md`)

## 6. 스스로 답해보기 / 첫 주 체크리스트

```
[ ] 로컬에서 전체 스택을 띄울 수 있다
[ ] 엔드포인트 하나를 Controller → Service → Repository → DB 까지 따라갔다
[ ] SQL 로깅을 켜고 화면 하나가 만드는 쿼리를 봤다
[ ] 작은 PR 하나를 머지했다 (오타 수정이라도)
[ ] CLAUDE.md 를 읽었거나, 없어서 초안을 만들었다
[ ] 첫 주에 내가 막힌 지점을 문서로 남겼다   ← 다음 사람을 위한 것이자 가장 확실한 첫 기여
[ ] 각 문서의 `> ❓` 질문에 답을 채웠다
```

**마지막 두 개가 가장 중요하다.** 새로 들어온 사람만이 "무엇이 설명되어 있지 않은지"를 안다.
그 감각은 2주면 사라진다.
