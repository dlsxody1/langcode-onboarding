# Agentic RAG

`03-rag/` 에서 만든 RAG 는 고정 파이프라인이다. 질문이 오면 무조건 검색하고, 검색 결과가 나빠도 그대로 답하고, 질문이 모호해도 되묻지 못한다.
이 문서는 그 파이프라인에 **판단하는 주체**를 얹는 이야기다. 검색을 LLM 이 골라 쓰는 도구로 바꾸고, 언제·어떻게·몇 번 검색할지를 모델에게 맡긴다. 이것을 Agentic RAG 라고 부른다.

> 전제: `01-what-is-an-agent.md` 의 도구 호출 루프(2장)를 읽었다고 가정한다. 여기서는 그 루프를 RAG 에 적용했을 때 새로 생기는 판단과, 실무에서 그 판단을 어디까지 모델에게 맡기는지를 다룬다.

---

## 1. 파이프라인에서 선택 가능한 도구로

### 고정 파이프라인이 못 하는 세 가지

`03-rag/01-pipeline.md` 5절의 실패 목록을 다시 보면, 그중 몇 개는 "판단할 주체가 없어서" 생긴다.

| 상황 | 고정 파이프라인 | 필요한 판단 |
| --- | --- | --- |
| 검색 결과가 질문과 무관하다 | 그 결과로 그냥 답한다 | "부족하다, 검색어를 바꿔 다시 찾자" |
| "그거 신청하려면?" 처럼 모호하다 | 아무거나 검색해 애매하게 답한다 | "무엇을 신청하는지 되묻자" |
| "고마워요" 같은 인사다 | 굳이 검색을 돌린다 | "검색할 필요 없다" |

세 판단 모두 코드로 미리 규칙을 짜기 어렵다. "검색 결과가 충분한가"는 질문과 문서의 내용을 읽어야 알 수 있기 때문이다. 그래서 이 판단을 LLM 에 맡긴다.

### 검색을 도구로 만든다

방법은 단순하다. 검색 함수를 순서도의 한 단계로 박아 두지 않고, 도구 목록에 올려 둔다.

```
고정 파이프라인 :  질문 → [검색] → [프롬프트 조립] → [생성] → 답
Agentic RAG     :  질문 → 모델 ─┬─ search_documents("반품 절차") → 결과 보고 다시 판단
                               ├─ 결과 부족 → search_documents("교환 환불 기준")
                               ├─ 모호함 → 사용자에게 되묻기
                               └─ 충분함 → 답 (근거 표시)
```

모델은 목표를 달성할 때까지 "생각 → 행동(도구 호출) → 관찰(결과 확인)" 을 반복한다(`01-what-is-an-agent.md` 4장의 ReAct). 도구를 쥐고 이 반복을 도는 LLM 실행 구조가 에이전트다.

### "에이전트"라는 말의 폭 — 판별 기준은 제어권

시장에서는 LLM 이 들어간 거의 모든 것을 에이전트라고 부른다. 대화가 엇나가지 않으려면 기준이 필요하다.
Anthropic 의 글 "Building effective agents" 가 쓰는 구분이 실무에서 가장 많이 인용된다.

- **워크플로우(workflow)**: 미리 짜인 코드 경로를 따라 LLM 과 도구가 실행된다. 다음 단계를 정하는 건 코드다.
- **에이전트(agent)**: LLM 이 스스로 다음 단계와 도구 사용을 동적으로 결정한다. 다음 단계를 정하는 건 모델이다.

이 기준으로 보면 "에이전트"로 팔리는 시스템 상당수는 워크플로우다. 나쁜 게 아니다. 2장과 5장에서 보듯 운영 제품은 일부러 워크플로우 쪽에 무게를 둔다.

넓은 뜻의 Agentic AI 는 계획·기억·행동으로 최소한의 감독 아래 목표를 수행하는 시스템을 가리킨다. 이 말은 "있다/없다"가 아니라 자율성의 정도를 나타내는 스펙트럼 위의 용어로 읽는다.

### RAG 는 에이전트의 기본 스킬 중 하나가 된다

이 관점에서 RAG 는 독립 시스템이 아니라 에이전트가 쥔 도구 하나다. 웹 검색, 계산기, 코드 실행과 같은 반열이다.

다만 **검색 도구 내부의 품질은 여전히 `03-rag/` 가 결정한다.** 파싱이 표를 망가뜨렸거나 청킹이 조항을 반으로 잘랐다면, 모델이 검색어를 아무리 잘 바꿔도 좋은 결과가 나오지 않는다. Agentic 은 검색을 대체하지 않는다. "언제, 어떻게 쓸지"의 층이 그 위에 하나 얹히는 것이다.

## 2. 기반 기술 ① Function Calling 과 강제 호출

메커니즘 자체는 `01-what-is-an-agent.md` 2장에 있다. 요점만 다시 적는다.

- LLM 에게 도구 목록(이름 · 설명 · 파라미터 스키마)을 알려주면, 모델은 답변 텍스트 대신 "이 도구를 이 인자로 불러 달라"는 구조화된 요청을 낸다.
- **LLM 이 도구를 실행하는 게 아니다.** 모델은 호출 의사만 출력하고 실행은 앱 코드가 한다. 결과를 대화에 다시 넣어 주면 모델이 이어서 판단한다.
- 세 요소 중 **설명(description)이 품질을 좌우한다.** "언제 이 도구를 쓸지"의 유일한 판단 근거라 사실상 프롬프트의 일부다.

```
사용자 질문
 → LLM: "지식검색 도구를 '반품 절차'로 호출" (tool call)
 → 앱: 실제 검색 실행, 결과를 대화에 추가
 → LLM: 결과를 보고 판단. 더 검색할까, 답할까
 → (반복) → 최종 답변
```

### 강제 호출 — "검색 없이 답하지 않는다"를 구조로 보장한다

여기서 Agentic RAG 에 새로 필요한 기능이 하나 있다. 대부분의 API 는 "이번 턴에는 반드시 이 도구를 불러라"를 지정하는 옵션을 제공한다(`tool_choice` 류 파라미터).

```jsonc
// Anthropic API 예: 첫 호출에서 search_documents 를 반드시 부르게 한다
"tool_choice": { "type": "tool", "name": "search_documents" }

// 기본값은 auto — 부를지 말지 모델이 정한다
"tool_choice": { "type": "auto" }
```

왜 필요한가. 검색 여부를 모델에게 완전히 맡기면, 모델이 "이건 내가 아는 내용이네" 하고 검색 없이 학습 지식으로 답하는 경우가 생긴다. 사내 규정 챗봇에서 이건 그라운딩(`03-rag/01-pipeline.md` ⑥) 위반이다.
그래서 실무에서 흔히 쓰는 구성은 **첫 호출만 검색을 강제하고, 두 번째부터는 auto** 로 돌리는 것이다. 첫 검색은 반드시 일어나고, 재검색 여부만 모델이 판단한다.

프롬프트에 "반드시 먼저 검색하라"고 적는 것과의 차이는 확실성이다. 프롬프트는 대부분 지켜지지만 가끔 어긴다. 강제 호출은 API 가 보장하므로 어길 수 없다. 반드시 지켜져야 하는 규칙은 프롬프트가 아니라 구조로 건다 — 이 문서 전체에 반복되는 원칙이다.

## 3. 기반 기술 ② 구조화 출력

### 출력을 읽는 건 사람이 아니라 코드다

Agentic 시스템에서 모델 출력의 상당수는 사람에게 보여 주는 답이 아니다. "이 검색 결과가 질문과 관련 있는가", "이 질문은 어느 갈래인가" 같은 **판정**이고, 그 판정을 코드가 읽고 분기한다.

```ts
const verdict = await judgeRelevance(question, chunks);
if (verdict.relevant) return answer(chunks);
else return retry(verdict.betterQuery);
```

코드가 읽으려면 모양이 정해져 있어야 한다. "네, 관련 있어 보입니다! 다만…" 같은 자유 서술은 `if` 에 넣을 수 없다. 그래서 출력을 JSON 스키마로 강제한다. 이것이 구조화 출력(structured output)이다.

### 두 가지 강제 방식

| | 프롬프트 강제 | API 강제 |
| --- | --- | --- |
| 방법 | 프롬프트에 "아래 JSON 형식으로만 답하라" + 예시 | `response_format` 등에 JSON 스키마를 넘김 |
| 지원 | 어떤 모델이든 가능 | 지원하는 모델·API 에서만 |
| 보장 | 대체로 지켜지지만 가끔 깨진다 | 스키마를 벗어난 출력 자체가 생성되지 않는다 |
| 필수 장치 | **파서 안전망** | 그래도 값 검증은 한다 |

프롬프트 강제에서 흔히 깨지는 모양은 정해져 있다. JSON 앞뒤에 설명 문장이 붙거나, ` ```json ` 코드펜스로 감싸거나, 필드 이름을 살짝 바꾼다. 그래서 파서 안전망이 필요하다.

```ts
import { z } from "zod";

const Relevance = z.object({
  relevant: z.boolean(),
  reason: z.string(),
  betterQuery: z.string().optional(),
});

function parseVerdict(raw: string) {
  // 1) 코드펜스·앞뒤 설명을 걷어내고 첫 { ~ 마지막 } 만 취한다
  const s = raw.slice(raw.indexOf("{"), raw.lastIndexOf("}") + 1);
  try {
    // 2) 스키마로 검증한다 — 파싱이 됐다고 맞는 모양이라는 보장은 없다
    return Relevance.parse(JSON.parse(s));
  } catch {
    // 3) 실패하면 안전한 기본값. 여기서는 "관련 없음"으로 보고 재검색 쪽으로 보낸다
    return { relevant: false, reason: "parse_error" };
  }
}
```

3번의 기본값을 어느 쪽으로 둘지가 설계 판단이다. 판정이 깨졌을 때 "관련 있음"으로 두면 엉뚱한 근거로 답하고, "관련 없음"으로 두면 재검색 한 번이 더 돈다. 보통은 비용이 드는 쪽(재검색)이 틀린 답보다 싸다.

지원 모델에서는 API 강제가 안전하다. 다만 API 강제도 **모양**만 보장한다. `relevant: true` 가 정말 맞는 판정인지는 여전히 모델의 몫이다.

### 판정 호출은 temperature 0

temperature 는 모델이 다음 토큰을 고를 때 얼마나 무작위로 고를지 정하는 값이다. 0 에 가까우면 가장 확률 높은 토큰만 고르고, 높으면 다양한 표현이 나온다.
최종 답변은 약간의 다양성이 있어도 괜찮지만, **시스템의 분기를 결정하는 판정은 흔들리면 안 된다.** 같은 질문이 어제는 검색으로, 오늘은 잡담으로 분류되면 재현도 디버깅도 안 된다.

그래서 판정·분류·라우팅 호출의 흔한 공통 패턴은 **temperature 0 + JSON 출력**이다. (temperature 0 도 완전한 결정성을 보장하지는 않는다. 같은 입력에 가끔 다른 결과가 나올 수 있다. 다만 흔들림이 크게 줄어든다.)

### 프레임워크 없이도 된다

에이전트 프레임워크(`02-maf.md`)나 네이티브 tool calling 이 없어도 이 구조는 만들 수 있다. LLM 을 원시 호출하고, 프롬프트로 JSON 을 강제하고, 앱이 파싱해서 분기하면 된다. 실제로 프롬프트와 파싱만으로 멀티에이전트 파이프라인 전체를 운영하는 사례도 있다.
프레임워크가 주는 건 이 반복 작업의 편의이지, 없으면 불가능한 능력이 아니다. 코드베이스에서 프레임워크 호출이 안 보인다고 "에이전트가 없다"고 판단하지 말 것.

## 4. Agentic RAG 루프

### 여섯 단계

1. **검색 필요 판단** — 인사나 잡담이면 검색 없이 응답한다.
2. **검색어 작성** — 사용자 질문을 그대로 넣지 않고 대화 맥락을 반영해 모델이 검색어를 쓴다. "그럼 금액은?" → "출산 축하금 지원 금액" (`03-rag/03-retrieval-quality.md` 3절 ①의 condensing 을 모델이 루프 안에서 하는 것).
3. **결과 평가** — 검색 결과가 답하기에 충분한지, 질문과 관련 있는지 판단한다. 3장의 구조화 출력이 여기서 쓰인다.
4. **재검색** — 부족하면 검색어를 바꿔 다시 찾는다. **횟수 제한은 필수다.** 없으면 결과가 영영 "부족"하다고 판정되는 질문에서 루프가 끝나지 않고, 한 바퀴마다 지연과 토큰이 쌓인다(`01-what-is-an-agent.md` 3장).
5. **명확화** — 질문이 여러 갈래로 해석되면 사용자에게 되묻는다. "육아휴직 신청 말씀이세요, 육아휴직 급여 신청 말씀이세요?"
6. **답변 생성** — 그라운딩과 출처 표시는 `03-rag/01-pipeline.md` ⑥·⑦ 그대로다.

이 루프는 보통 서브에이전트 하나로 구현한다. 검색 · 관련성 확인 · 질의 재작성 같은 도구를 쥐여 주고, 첫 검색은 강제하고(2장), 재검색 횟수는 상한을 둔다. 상한은 프롬프트에 적기도 하지만, 반드시 지켜져야 한다면 루프 코드의 반복 카운터로 거는 편이 확실하다.

### 1장 실패 모드와의 대응

| `03-rag` 의 실패 | Agentic 대응 |
| --- | --- |
| 검색이 무관한 문서를 가져왔다 | 결과 평가 → 재검색 |
| 질문이 모호하다 | 명확화 (되묻기) |
| 검색이 필요 없는 입력이다 | 검색 스킵 |

업계에서는 이런 패턴을 **Self-RAG**, **Corrective RAG(CRAG)** 같은 이름으로 부른다. 논문마다 세부 구조는 다르지만 본질은 같다 — **결과를 평가하고 교정하는 루프**다. 이름을 외울 필요는 없고, "검색 → 평가 → 교정" 의 3박자를 알아보면 된다.

### 반대로, 고칠 수 없는 것

재검색으로 해결되지 않는 실패도 있다. 문서가 아예 색인돼 있지 않거나, 파싱 단계에서 표가 숫자 나열로 망가졌거나, 권한 필터가 잘못 걸려 있으면 검색어를 몇 번 바꿔도 같은 결과가 나온다. 이 경우 재검색 상한까지 돌다가 "확인할 수 없습니다" 로 끝난다.
그래서 **재검색 상한에 도달해 끝난 실행은 로그에 따로 표시해 둔다.** 그 목록이 인덱싱·파싱 쪽 결함을 찾는 가장 좋은 출발점이다(`01-what-is-an-agent.md` 6장의 종료 사유와 같은 이야기).

## 5. 실무: 전부 자율에 맡기지 않는다

### 자율의 비용

| 비용 | 내용 |
| --- | --- |
| 지연 | LLM 왕복 한 번에 수백 ms 에서 수 초. 판정 → 재검색 → 판정이면 그게 몇 번 겹친다 |
| 토큰 | 루프 한 바퀴마다 대화 전체가 다시 들어간다 |
| 예측 불가능성 | 같은 질문에 다른 경로, 다른 답 |
| 테스트 곤란 | "이 입력이면 이 행동" 을 단위 테스트로 고정할 수 없다 |

그래서 실제 운영 제품은 완전 자율과 완전 고정 사이의 **중간 지점을 설계**한다. 흔히 쓰는 기법이 세 가지다.

### ① extract / decide 분리

LLM 은 **판단 재료만 추출**하고, **최종 행동은 코드 규칙이 결정**한다.

```ts
// LLM — 재료 추출만 (temperature 0 + JSON)
const facts = await extract(question, chunks);
// → { relevance: 0.42, readings: ["육아휴직 신청", "육아휴직 급여 신청"] }

// 코드 — 행동 결정
if (facts.readings.length >= 2) return askClarify(facts.readings);   // 선택지 칩
if (facts.relevance >= 0.7)     return answer(chunks);              // 직답
return answerWithCaveat(chunks);                                     // 약한 근거 표시 후 답
```

LLM 에게 "직답할지 되물을지 정해서 행동하라"고 맡기는 것과 비교하면 차이가 분명하다.

- 같은 재료면 같은 행동이 나온다. 행동의 흔들림이 사라진다.
- `if` 부분은 단위 테스트가 된다. "갈래가 둘이면 되묻는다" 를 테스트로 고정할 수 있다.
- 임계값(0.7)을 바꿔 가며 운영 데이터로 튜닝할 수 있다. 프롬프트 문구를 고치는 것보다 훨씬 통제된 실험이다.

### ② fast-path

버튼 클릭, 메뉴 선택, 도메인 고유어처럼 **뻔한 입력은 LLM 왕복 없이 규칙으로 즉시 분기**한다.
사용자가 "반품 안내" 버튼을 눌렀다면 의도를 분류하는 LLM 호출은 필요 없다. 버튼이 이미 의도다.

같은 발상으로, 뻔한 첫 검색은 모델의 tool call 을 기다리지 않고 코드가 바로 실행해 둘 수 있다. 첫 검색이 어차피 강제라면(2장) 모델에게 "검색해 주세요"를 받는 왕복 한 번을 아낄 수 있다. 체감 지연이 왕복 하나만큼 줄어든다.

### ③ 자율 루프는 R&D 트랙부터

완전 자율 tool 루프(모델이 모든 도구를 스스로 고르고 반복)는 연구 경로에서 먼저 검증하고, 효과가 확인된 부분부터 운영에 점진적으로 들인다. 운영은 하이브리드를 유지하는 게 보통이다.

### 제어권 기준으로 판정해 보기

같은 회사 안에서도 제품마다, 같은 제품 안에서도 경로마다 판정이 갈린다. 흔한 구성 세 가지를 1장의 기준으로 판정하면 이렇다.

| 구성 | 판정 | 근거 |
| --- | --- | --- |
| 고정 순차 파이프라인 (분류 → 처리 → 응답) | 워크플로우 | LLM 은 각 단계 안의 판단만, 흐름은 코드가 결정 |
| 상담 챗봇 운영 경로 | 하이브리드 | 큰 흐름은 코드가 결정, RAG 서브에이전트 내부의 재검색·질의 재작성만 모델이 결정 |
| 상담 챗봇 R&D 경로 | 에이전트 | 검색 · 시나리오 · 기억 · 명확화 도구를 모델이 스스로 고르고 반복 |

여기서 가져갈 감각은 두 가지다.

- 워크플로우와 에이전트는 대립이 아니라 **합성**이다. 판정은 제품 단위가 아니라 **경로와 부분 단위**로 갈린다.
- "얼마나 자율적으로 만들 것인가"는 기능이 아니라 **트레이드오프 축**이다. 자율성을 올리면 유연성을 얻고 예측 가능성·비용·테스트 용이성을 낸다.

> ❓ 입사 후 확인: 우리 제품의 각 경로는 위 표의 어디에 놓이나? 첫 검색은 강제인가, 코드가 직접 실행하나? 재검색 상한은 프롬프트로 거나 코드로 거나?

## 6. RAG 가 에이전트에 노출되는 세 가지 형태

| 형태 | 구조 | 장점 | 단점 |
| --- | --- | --- | --- |
| ① 파이프라인 내장 | 검색이 코드 흐름에 고정 (`03-rag` 의 형태) | 단순 · 빠름 · 예측 가능 | 유연성 없음 |
| ② 도구로 노출 | "지식 검색" 도구를 에이전트에 등록 | 필요할 때만 호출, 여러 에이전트가 재사용 | 호출 여부가 모델 판단에 달림 |
| ③ 원격 에이전트 위임 | 검색과 답변 전체를 외부 에이전트에 맡김. 질문을 보내고 답만 받음 | 자체 RAG 없이 도메인 지식을 붙일 수 있다 (RAG-as-a-service) | 내부 품질을 통제하기 어렵다, 근거 추적이 한 단계 멀어진다 |

현재의 표준은 ② 다. 하지만 실제 제품은 섞여 있는 경우가 많다.

- ①+② 혼합: 코드가 첫 검색을 실행하고(①), 재검색 여부는 모델이 판단한다(②). 5장 ②의 fast-path 가 정확히 이 모양이다.
- ③: 오케스트레이터가 자체 RAG 를 갖지 않고, 도메인별 원격 에이전트에게 질문을 넘긴 뒤 답을 받아 종합한다. 다음 문서(`05-orchestration.md`)의 라우팅과 이어진다.

**시사점:** "RAG 를 잘 만든다"는 것은 두 가지다. 검색 품질(`03-rag/`) + 그 검색을 재사용 가능한 능력 단위로 포장하는 설계(이 문서). 앞의 것만 잘하면 한 제품에서만 쓰이고, 뒤의 것만 잘하면 어디서나 쓰이지만 답이 틀린다.

## 7. MCP — 도구 연결의 표준화

자세한 구조는 `03-mcp.md` 에 있다. Agentic RAG 관점에서 짚을 것만 적는다.

- **문제:** 도구 정의 방식이 벤더와 프레임워크마다 제각각이다. 도구 제공자 M 개와 에이전트 앱 N 개를 잇는 데 M×N 번의 통합 비용이 든다.
- **MCP(Model Context Protocol):** 도구를 노출하는 공개 표준 프로토콜. "AI 도구계의 USB-C" 로 비유된다. 도구를 제공하는 서버(지식 검색, 이슈 트래커, 파일시스템)와 도구를 쓰는 클라이언트(에이전트 앱) 구조다. 이러면 통합 비용이 M+N 으로 준다.
- **지식 검색을 MCP 도구로 노출하면 6장 형태 ②의 표준화 버전이 된다.** 어떤 에이전트 앱이든 같은 검색 능력을 재사용한다.
- **보안:** 외부 도구는 외부 코드와 데이터가 들어오는 통로다. 허용 목록과 인증으로 통제하고, 도구 결과는 `03-rag/04-enterprise-rag.md` 3절의 원칙 그대로 **"자료이지 지시가 아니다"** 로 다룬다. 검색 결과 안에 "이전 지시를 무시하고…" 라는 문장이 있어도 따르지 않게 프롬프트에서 자료 영역을 구분해 못 박는다.
