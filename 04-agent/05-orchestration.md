# 에이전트 오케스트레이션

여러 LLM 호출, 에이전트, 도구를 조율해 요청 하나를 끝까지 처리하는 상위 구조를 오케스트레이션이라고 한다(용어 자체는 `01-what-is-an-agent.md` 4장).
설계의 실체는 `04-agentic-rag.md` 1장의 워크플로우/에이전트 스펙트럼 위에서 **"어디는 코드가, 어디는 모델이 결정하게 할지"** 를 정하는 일이다.

---

## 1. 오케스트레이션의 세 축

오케스트레이터가 답해야 하는 질문은 세 개다. 이 문서의 2\~5장이 각각을 다룬다.

| 축 | 질문 | 이 문서 |
| --- | --- | --- |
| 라우팅 | 이 질문을 누구에게 보낼 것인가 | 2장 |
| 지휘 | 여러 에이전트와 단계를 누가, 어떤 순서로 지휘하는가 | 3장 멀티에이전트 · 4장 워크플로우 |
| 맥락 | 대화의 맥락과 기억은 누가 관리하는가 | 5장 멀티턴 · 메모리 |

6장은 셋 모두에 걸치는 운영 이야기다.

---

## 2. 라우팅: 누구에게 보낼 것인가

라우팅(routing)은 들어온 요청을 어느 에이전트·처리 경로로 보낼지 정하는 단계다. 모든 요청이 이 단계를 거치므로 **정확도와 속도가 둘 다 제품 전체에 곱해진다.**

실무 프로젝트들의 공통 패턴은 거의 같다. **경량 모델 + temperature 0 + JSON 출력** (`04-agentic-rag.md` 3장).

### 패턴 A — 분류기 + 후처리 규칙

가장 흔한 형태다. 상담 챗봇을 예로 든다.

**① LLM 호출 전 fast-path 검사**

- 칩·버튼 클릭: 이미 의도가 정해져 있으니 분류할 필요가 없다.
- 도메인 고유어 목록: 자체 브랜드명, 상품명, 이벤트명 같은 단어가 들어오면 바로 해당 경로로 보낸다.

도메인 고유어 목록이 왜 필요한가. 범용 LLM 은 학습 때 본 적 없는 고유어를 **무의미한 입력이나 오타로 오판**하기 쉽다. 신상품 이름 하나만 입력했는데 "무슨 말씀인지 모르겠어요" 가 나오는 식이다. 목록을 코드가 아니라 **DB 에서 관리**하면 신조어가 생길 때 배포 없이 운영자가 추가할 수 있다.

**② 경량 모델이 분류** — 예: 잡담 / 지식 질문 / 처리 불가

**③ 후처리 규칙이 핵심이다**

분류 결과를 그대로 따르지 않고, 틀렸을 때의 비용이 큰 쪽을 코드로 보정한다.

```ts
const c = await classify(text);                // { label, confidence, malicious }

if (c.label === "chitchat" && c.confidence < 0.8) c.label = "knowledge";  // 애매한 잡담 → 검색으로 강등
if (c.label === "unsupported" && !c.malicious)   c.label = "knowledge";  // 처리 불가도 악성 아니면 일단 검색
```

이유는 실패 비용의 비대칭이다. 지식 질문을 잡담으로 잘못 분류하면 사용자는 근거 없는 수다를 받는다. 검색할 필요 없는 잡담을 검색으로 보내면 비용이 조금 더 들 뿐이다. "처리할 수 없습니다" 는 더 나쁘다 — 사용자 입장에서 가장 좌절스러운 응답이고, 실제로 답할 수 있는 질문이었던 경우가 적지 않다. 그래서 **의심스러우면 검색 쪽으로 보낸다.**

**④ "누가 묻는가"도 라우팅의 입력이다**

같은 "반품 어떻게 해요?" 라도 고객이 물으면 고객 안내 에이전트로, 임직원이 물으면 매장 운영 매뉴얼 에이전트로 가야 한다. 분류 결과(무엇을 묻나)와 사용자 유형(누가 묻나)을 결합해 최종 서브에이전트를 정한다. 사용자 유형은 LLM 이 추측하지 않는다. 인증 정보에서 코드가 읽는다(`01-backend-basics/04-auth.md`).

### 패턴 B — 레지스트리 기반 2단계 라우팅

에이전트가 수십 개로 늘어나는 플랫폼형 구조에서 쓴다.

**레지스트리**: 에이전트들이 DB 에 자기 정보를 등록한다 — 이름, 설명, 예시 발화, 입력 스키마. 라우터는 이 목록을 프롬프트에 넣고 판단한다. 도구의 description 이 도구 선택을 좌우하듯(`01-what-is-an-agent.md` 2장), 여기서는 **에이전트 설명과 예시 발화가 라우팅 품질을 좌우한다.**

**1차 — 후보 좁히기**: 정형 워크플로우에 해당하는 요청인지 판정한다. 후보와 점수를 낸다.

**2차 — 상세 선정**:

- 워크플로우에 해당하면 라우터가 **상태머신** 역할을 한다. 지금 어느 스텝인지, 진행할지 · 입력을 기다릴지 · 반복할지 · 완료할지를 정한다.
- 해당하지 않으면 에이전트들을 점수화해 고른다. 여러 에이전트가 필요하면 **병렬 실행 그룹**과 **되묻기 계획**까지 라우터가 낸다.

**후처리는 코드**가 한다 — 신뢰도 임계값 미만 후보 제거, 실행 순서 확정.

왜 두 단계로 나누나. 에이전트 50 개의 상세 설명을 매 요청마다 전부 프롬프트에 넣으면 토큰이 크고 판단도 흐려진다. 1차에서 짧은 정보로 후보를 좁히고, 2차에서는 남은 후보의 상세 정보만 넣는다. **토큰을 아끼면서 정확도를 올리는** 구조다.

### 대비 — 라우팅의 "결과물"부터 설계 결정이다

| | 패턴 A | 패턴 B |
| --- | --- | --- |
| 라우팅이 내는 것 | 서브에이전트 **하나의 선택** | 에이전트 **실행 계획** (순서 · 병렬 · 상태) |
| 적합 | 갈래 수가 적고 고정된 제품 | 에이전트가 계속 늘어나는 플랫폼 |

같은 "라우팅"이라도 무엇을 결과물로 삼을지가 다르다. 그 결정이 뒤따르는 오케스트레이터의 모양 전체를 정한다.

### 모델 티어링

분류와 판정은 **매 요청** 실행되므로, 여기를 경량화한 효과는 요청 수만큼 누적된다.

| 호출 | 모델 | 이유 |
| --- | --- | --- |
| 분류 · 판정 · 라우팅 | 경량 모델 | 출력이 JSON 한 조각. 속도와 비용에 민감 |
| 잡담 응대 | 경량 모델 | 틀려도 피해가 작다 |
| 최종 답변 | 상위 모델 | 품질이 곧 제품 경험 |

경량 모델이 상위 모델보다 빠르고 싸다는 건 당연하지만, 감을 잡아 두면 좋다. 요청 하나에 판정 호출이 서너 번 들어가는 구조라면 그 서너 번이 전체 지연의 대부분을 차지한다. 최종 답변은 스트리밍으로 첫 토큰부터 보여 줄 수 있지만(`05-realtime-ui/`), 판정은 끝나야 다음으로 넘어갈 수 있기 때문이다.

## 3. 멀티에이전트: 전문가를 나눠 지휘하기

왜 나누는지는 `01-what-is-an-agent.md` 4장에 있다. 에이전트 하나에 도구 10 개와 규칙 전부를 넣으면 프롬프트가 비대해지고 도구 선택이 혼란스러워진다. 나누면 각자 좁은 책임, 적은 도구, 짧은 프롬프트를 갖는다. 여기서는 **나눈 뒤 어떻게 엮는지**의 패턴을 본다.

### 라우터 → 전문 서브에이전트

2장의 분류 결과에 따라 전문 에이전트가 처리한다. 예: 잡담 / 상품 안내 / 정형 시나리오 / RAG(지식 질문). 각 서브에이전트는 자기 영역의 도구와 지시만 갖는다.

### 핸드오프 (순차 체이닝)

앞 에이전트의 산출을 다음 에이전트의 입력으로 넘긴다.

```
"다음 주 화요일 팀 회의실 잡아줘"
 → 일정 확인 에이전트   : 참석자들의 화요일 빈 시간 → 14:00~15:00
 → 회의실 조회 에이전트 : 14:00~15:00 · 6인 이상 → 3층 A 회의실
 → 예약 에이전트        : A 회의실 예약
 → 캘린더 에이전트      : 참석자 초대 발송
```

> 용어 주의: `02-maf.md` 의 핸드오프는 "대화의 주도권 자체를 다른 에이전트에게 넘기는 것"(전화 돌려주기)을 가리킨다. 여기의 핸드오프는 "산출물을 다음 단계 입력으로 넘기는 것"(조립 라인)이다. 문서와 프레임워크마다 같은 말을 다르게 쓰니 문맥으로 구분한다.

### 병렬 실행

서로 의존하지 않는 작업은 동시에 돌린다. "이번 주 내 일정이랑 미결 결재 건 알려줘" 라면 일정 조회와 결재 조회는 독립이다. 패턴 B 처럼 라우터가 병렬 그룹까지 지정하면 오케스트레이터는 그룹 단위로 `Task.WhenAll` 하면 된다.

### 오케스트레이터-워커

지휘 에이전트(오케스트레이터)가 계획을 세워 워커들에게 일을 나눠 주고, 워커 결과를 종합한다. 모델이 직접 지휘하므로 에이전트 쪽에 가까운 구조다.

알려진 약점: **참가 에이전트가 많을수록 지휘 품질이 떨어진다.** 후보가 20 명이면 누구에게 무엇을 맡길지 헷갈린다. 흔한 보완책은 **사전 선별(pre-selection)** 이다. 요청마다 필요한 워커만 미리 골라 등록하고 지휘를 시작한다. 패턴 B 의 1차 라우팅이 같은 역할을 한다.

### Slot filling — 폼을 대화로 채우기

실행에 필요한 인자(날짜, 인원, 건물 등)를 슬롯이라고 부른다. 대화에서 슬롯을 추출하고, 빈 슬롯은 되물어 채운다.

```
사용자 : "회의실 잡아줘"
          slots = { date: ?, people: ?, building: ? }
봇     : "날짜와 인원을 알려주세요."
사용자 : "내일 6명"
          slots = { date: 2026-10-03, people: 6, building: ? }
봇     : "어느 건물로 잡을까요?"
```

역할 분담이 중요하다. **추출은 LLM(구조화 출력), 검증은 코드**다. "내일" 을 날짜로 바꾸는 건 LLM 이 잘하지만, 그 날짜가 과거인지, 인원이 회의실 최대 수용 인원을 넘는지는 코드가 확인한다. LLM 에게 검증까지 맡기면 가끔 틀린 슬롯이 통과한다.

핸드오프와 결합하면 효과가 커진다. 앞 단계(일정 확인)가 이미 날짜와 인원을 알아냈다면 그 산출을 다음 단계의 슬롯에 주입해 같은 질문을 두 번 하지 않는다.

### 에이전트를 코드가 아닌 구성(config)으로

에이전트를 코드 클래스로 만들지 않고 **DB 문서로 등록**하는 방식이 있다. 이름 · 설명 · 프롬프트 · 연동할 API 엔드포인트 · 입력 스키마를 문서 하나에 담는다. 같은 연동 방식을 쓰는 신규 봇은 문서를 등록하면 끝이다. 배포가 필요 없다.
2장 패턴 B 의 레지스트리와 같은 데이터다. 라우터는 그 문서의 설명을 읽고 고르고, 실행기는 같은 문서의 엔드포인트를 부른다.

## 4. 워크플로우: 흐름을 그래프로 설계

### 노드와 엣지

워크플로우는 흐름을 **노드(단계)와 엣지(연결)의 그래프**로 미리 정의해 실행한다.

| 노드 종류 | 예 |
| --- | --- |
| 트리거 | 수동 실행, 챗 메시지 수신, 스케줄 |
| 액션 | LLM 호출, 검색, HTTP 호출 |
| 제어 | 조건 분기, 반복, 사용자 입력 대기 |

| 엣지 종류 | 의미 |
| --- | --- |
| 직행 | A 끝나면 B |
| 조건 분기 | 결과에 따라 B 또는 C |
| 병렬 분기 (fan-out) | A 끝나면 B, C 동시 시작 |
| 합류 (fan-in) | B, C 둘 다 끝나야 D |

```
[챗 트리거] → [LLM: 의도 추출] ─조건─┬─ 출장 신청 → [슬롯 채우기] → [사람 확인] → [결재 상신]
                                    └─ 그 외    → [RAG 서브에이전트] → [응답]
```

프론트 개발자라면 상태 다이어그램이나 XState 의 머신 정의를 떠올리면 가깝다. 차이는 노드 안에서 LLM 이 판단을 한다는 것뿐이다.

### human-in-the-loop

되돌리기 어려운 단계(발송, 결재, 삭제) 앞에 **사람의 확인 노드**를 세운다. 위 그래프의 [사람 확인] 이 그것이다. 구현은 `01-what-is-an-agent.md` 4장과 같다 — 실행을 멈추고 "승인 대기" 상태로 저장한 뒤, 승인되면 이어서 실행한다.
"전부 자동"이 목표가 아니다. 사람이 확인해야 하는 지점을 설계에 명시하는 것이 엔터프라이즈 자동화의 기본이다.

### 언제 무엇을 쓰나

| | 워크플로우 | 에이전트 |
| --- | --- | --- |
| 업무 성격 | 반복적이고 규정된 절차, 감사가 필요한 업무 | 탐색적이고 비정형, 경로를 미리 모르는 업무 |
| 얻는 것 | 결정적 · 검증 가능 · 설명 가능 | 동적 판단 자체가 가치 |

업계 권고(Anthropic, "Building effective agents"): **가능한 한 단순하게 시작하고, 필요할 때만 에이전트로.** 단일 LLM 호출로 되면 그걸로 끝내고, 안 되면 워크플로우, 그래도 안 되면 에이전트.

실무는 둘의 합성이다. **큰 흐름은 그래프로 통제하고, 판단이 필요한 구간만 에이전트에 맡긴다.** 위 그래프에서 [RAG 서브에이전트] 노드 하나가 `04-agentic-rag.md` 의 자율 루프 전체를 품고 있는 식이다.

## 5. 멀티턴과 메모리: 맥락은 누가 관리하나

LLM 은 stateless 다(`01-what-is-an-agent.md` 1장). 매 호출에 이력을 다시 넣어 줘야 한다. 대화가 길어지면 비용, 컨텍스트 한계, 노이즈가 같이 따라오므로 **"무엇을 얼마나 넣을지"가 설계 대상**이 된다.

### 단기 기억 — 대화 이력

**전체 주입**은 단순하지만 긴 대화에서 비용이 바로 늘어난다. 흔한 대안이 **슬라이딩 윈도우** — 최근 N 턴만 잘라 붙인다(예: 최근 3턴). 옛날 대화는 잊는 대신 비용이 일정해진다.

**질의 독립화**가 멀티턴 품질의 최상류 문제다. "그럼 금액은?" 을 그대로 검색하면 아무것도 못 찾는다. 이전 대화를 반영해 "출산 축하금 지원 금액" 같은 독립 질의로 바꾼 뒤 검색해야 한다(`03-rag/03-retrieval-quality.md` 3절 ①). 슬라이딩 윈도우로 이력을 잘라도 질의 독립화가 제대로 되면 검색은 맞는다. 반대로 이력을 전부 넣어도 독립화를 안 하면 검색이 틀린다. 그래서 대부분의 제품이 이 문제를 공통으로 푼다.

### 장기 기억 — working memory

턴 수를 넘어 기억해야 하는 것(사용자가 지난주에 말한 선호, 진행 중인 이슈)은 별도 저장소에 둔다. 두 가지 방식이 있다.

| 방식 | 동작 | 특징 |
| --- | --- | --- |
| 백그라운드 정리 | 턴이 끝날 때마다 LLM 이 대화를 주제별 스레드로 정리(요약, 엔티티, 미해결 이슈)해 저장. **응답을 먼저 보내고 정리는 뒤에서** | 사용자 체감 지연 0. 무엇을 남길지 시스템이 정한다 |
| 기억을 도구로 | `save_fact`, `recall` 같은 도구를 에이전트에 준다 | 에이전트가 스스로 기억을 관리. 유연하지만 덜 예측 가능 |

백그라운드 정리는 `01-backend-basics/05-long-running-jobs.md` 의 "응답 먼저, 무거운 일은 뒤로" 와 같은 구조다. 앞의 방식은 워크플로우 쪽, 뒤의 방식은 에이전트 쪽이라는 점도 눈여겨볼 만하다. 기억에도 같은 스펙트럼이 있다.

**기억은 자동 부산물이 아니라 설계 대상이다.** 무엇을, 언제, 어떤 형태로 남기고 불러올지를 정해야 한다. 아무거나 남기면 오래된 정보가 새 질문의 답을 오염시키고, 개인정보 보관 기간 문제(`03-rag/04-enterprise-rag.md` 6절)도 따라온다.

### 대화 상태는 이력과 따로 보존한다

대화 이력 말고도 다음 턴에 반드시 필요한 상태가 있다.

- 명확화 칩의 정답표: 봇이 "A / B / C 중 무엇인가요?" 칩을 보여 줬다면, 다음 턴에 사용자가 B 를 눌렀을 때 B 가 무엇이었는지 알아야 한다.
- 진행 중인 워크플로우의 현재 스텝과 지금까지 수집된 슬롯.

이것들은 **이력 트리밍과 무관하게 별도로 저장**한다. 슬라이딩 윈도우가 3턴 전 대화를 잘라냈다고 진행 중인 예약의 슬롯까지 사라지면 안 된다. 서버가 여러 대라면 공유 저장소(DB, Redis)에 둔다(`07-db-infra/05-infra.md` 의 무상태 서버).

## 6. 운영 감각: 오케스트레이션을 신뢰할 수 있게

### 진행 노출

여러 단계를 거치는 요청은 길다. 사용자가 기다리는 동안 무엇을 보여 줄지가 체감 품질을 정한다.

- 토큰 스트리밍: 최종 답변을 첫 토큰부터 흘려보낸다(`05-realtime-ui/`).
- 단계별 로딩 메시지: "일정 확인 중 → 회의실 조회 중 → 예약 중".

에이전트 시대에는 "지금 문서 검색 중", "결과 확인 중" 같은 **행동 단위 진행 노출**이 표준이 되어 가고 있다. 서버가 단계 이벤트를 SSE 로 보내고 프론트가 타임라인처럼 그리는 구조다.

### 실패 대비

외부 호출은 실패한다는 전제로 설계한다(`07-db-infra/03-resilience.md`).

- 재시도: 지수 백오프 + 지터
- 폴백: 상위 모델이 실패하면 경량 모델로, 서브에이전트가 실패하면 일반 RAG 로
- 타임아웃: 단계별로 건다. 전체 타임아웃 하나만 있으면 어느 단계가 느린지 모른다
- 중단된 실행 복구: 진행 상태를 저장해 두면 서버 재시작 후 이어 갈 수 있다(`01-backend-basics/05-long-running-jobs.md`)

**"한 단계 실패가 전체 실패는 아니다"** 가 오케스트레이터의 책임이다. 병렬로 돌린 세 에이전트 중 하나가 실패했다면, 나머지 둘의 결과로 답하고 "결재 정보는 지금 확인할 수 없습니다" 를 덧붙이는 게 전체 에러보다 낫다.

### 관측성

남길 것: 단계별 실행 로그, 라우팅 로그(어떤 분류가 어떤 신뢰도로 나왔고 후처리가 무엇을 바꿨나), 단계별 토큰 집계, 사용자 피드백.
품질 이슈 진단은 이 로그에서 시작한다. `03-rag/01-pipeline.md` 5절의 "어느 단계가 깨졌는지" 를 오케스트레이션 수준으로 올린 것이다. 답이 틀렸을 때 라우팅이 틀렸는지, 서브에이전트가 검색을 잘못했는지, 생성이 근거를 무시했는지를 가려야 고칠 곳이 보인다.

### 평가(eval) — 바꿨으면 숫자로 증명한다

라우팅 프롬프트 한 줄, 후처리 임계값 하나를 바꿔도 전체 동작이 달라진다. "좋아진 것 같다" 로는 안 된다.
LLM-as-judge(`03-rag/03-retrieval-quality.md` 4절) 하네스를 흔히 이렇게 구성한다.

```
① 운영 실데이터 추출   — 실제 사용자 질문과 대화 맥락 (개인정보 마스킹)
② 변경 전후 재현(replay) — 같은 입력을 기존 버전과 새 버전에 각각 흘린다
③ 판정 모델 채점        — 두 답을 판정 모델이 기준표에 따라 채점
④ A/B 리포트            — 이긴 쪽 · 진 쪽 · 비긴 쪽 비율과 대표 사례
⑤ 사람 검수             — 판정 모델의 확신이 낮은 케이스만
```

①이 중요하다. 개발자가 상상한 질문 50 개보다 운영에서 실제로 들어온 질문 50 개가 훨씬 많은 문제를 드러낸다. ⑤는 판정 모델도 틀린다는 사실을 인정하는 장치다. 전부 사람이 보면 느리고, 전부 모델에 맡기면 판정 모델의 편향이 그대로 결론이 된다.

> ❓ 입사 후 확인: 우리 제품의 라우팅은 패턴 A 와 B 중 어느 쪽에 가까운가? 대화 상태(칩 정답표, 진행 중 슬롯)는 어디에 저장하나? 변경 전후 재현 평가는 어떻게 돌리나?
