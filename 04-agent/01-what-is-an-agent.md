# 에이전트란 무엇인가

마케팅 용어를 걷어내면 생각보다 단순하다.

---

## 1. 한 줄 정의

> **에이전트 = LLM + 도구 + 루프.**
> 모델이 "무엇을 할지" 정하고, 시스템이 그걸 실행하고, 결과를 다시 모델에게 준다. 끝날 때까지 반복.

세 단어를 하나씩 풀면 이렇다.

- LLM 은 글을 받아 다음 글을 만들어 내는 모델이다. 혼자서는 인터넷을 보거나 DB 를 조회하지 못한다. 할 수 있는 일은 텍스트(정확히는 토큰)를 출력하는 것 하나뿐이다.
- 도구(tool)는 우리가 미리 만들어 둔 함수다. 문서 검색, 계산, 사내 API 호출 같은 것들이다. 모델에게는 함수 본체가 아니라 이름과 설명, 인자 형태만 보여 준다.
- 루프(loop)는 "모델에게 묻고 → 모델이 도구를 요청하면 실행하고 → 결과를 붙여 다시 묻는" 반복이다. 모델이 더 이상 도구를 요청하지 않고 최종 답을 내면 끝난다. 이 반복을 에이전트 루프(agent loop)라고 부른다.

프론트엔드에 비유하면 모델은 "다음에 어떤 액션을 dispatch 할지"만 정하는 리듀서 바깥의 판단자이고 실제 부수 효과(fetch, 저장)는 우리 쪽 미들웨어가 처리하는 구조다. 모델은 결정만 하고 실행은 언제나 우리 코드가 한다.

### 토큰과 컨텍스트 윈도우

이 문서 곳곳에 나오는 두 단어를 먼저 짚는다.

토큰(token)은 모델이 글을 읽고 쓰는 단위다. 단어보다 잘게 쪼갠 조각이라 "안녕하세요" 가 토큰 여러 개가 되기도 한다. 쪼개는 방식(토크나이저)은 모델마다 다르다. 중요한 건 요금, 속도, 입력 한도가 전부 토큰 수로 계산된다는 사실이다.

컨텍스트 윈도우(context window)는 모델이 한 번 호출될 때 볼 수 있는 토큰의 최대치다. 시스템 지시, 지금까지의 대화, 도구 목록과 설명, 도구 실행 결과가 모두 이 안에 들어가야 한다. 넘치면 호출이 실패하거나 앞부분을 잘라내야 한다.

여기에 한 가지가 더 붙는다. 모델은 이전 호출을 기억하지 않는다(stateless). 세션 없는 HTTP API 처럼 매번 전체 대화를 처음부터 다시 보내야 한다. 그래서 루프를 한 바퀴 돌 때마다 입력 토큰이 쌓이고 비용도 같이 늘어난다. 3장의 "비용 폭주"와 "컨텍스트 초과"가 여기서 나온다.

### RAG 와의 관계

| | RAG | 에이전트 |
| --- | --- | --- |
| 흐름 | 검색 → 생성 (1회, 고정) | 모델이 다음 행동을 매번 결정 (n회, 가변) |
| 할 수 있는 것 | 질문에 문서로 답한다 | 검색하고, 계산하고, API 를 부르고, 파일을 쓴다 |
| 예측 가능성 | 높다 | 낮다 ← 이게 운영의 어려움 |

**RAG 는 에이전트의 도구 중 하나로 들어간다.** "문서 검색" 도구를 가진 에이전트가 CXP Agent 다.
RAG 는 "질문이 오면 무조건 검색부터 한다"는 고정 경로이고 에이전트는 검색이 필요한지부터 모델이 판단한다. 인사말에는 검색을 건너뛰고 어려운 질문에는 검색을 두세 번 다른 검색어로 반복할 수도 있다. 검색 자체를 잘하는 방법은 `03-rag/01-pipeline.md` 에서 다룬다.

## 2. Tool Calling — 실제 메커니즘

모델이 코드를 실행하는 게 아니다. **모델은 "이 함수를 이 인자로 부르고 싶다"는 JSON 을 뱉을 뿐이고,
실행은 우리 코드가 한다.**

이 구조를 tool calling 이라고 한다. OpenAI 쪽 문서에서는 function calling 이라는 이름을 먼저 썼다. 두 말은 같은 것을 가리킨다. 모델이 "도구 호출 요청"이라는 특별한 형식의 출력을 낼 수 있도록 학습돼 있다. 우리는 그 출력을 파싱해 해당 함수를 부를 뿐이다.

흐름은 네 단계다. 아래 예시는 "연차 이월 규정 알려줘" 라는 질문 하나를 따라간다. JSON 필드 이름(`tool_use`, `tool_result`)은 Anthropic API 형식이다. 다른 프로바이더는 이름만 조금 다르다.

### ① 도구를 스키마로 알려준다

```json
{
  "name": "search_documents",
  "description": "사내 문서를 검색한다. 규정·정책·매뉴얼 질문에 사용.",
  "input_schema": {
    "type": "object",
    "properties": {
      "query":      { "type": "string", "description": "검색어" },
      "department": { "type": "string", "enum": ["hr", "finance", "legal"] }
    },
    "required": ["query"]
  }
}
```

`input_schema` 부분은 JSON Schema 라는 표준 형식이다. JSON 데이터가 어떤 모양이어야 하는지를 JSON 으로 적는 규격이다. TypeScript 로 옮기면 이 정도다.

```ts
type SearchDocumentsInput = {
  query: string;                                // 필수
  department?: "hr" | "finance" | "legal";      // 선택. 셋 중 하나
};
```

zod 스키마를 써 봤다면 같은 역할이라고 보면 된다. 모델은 이 스키마를 보고 인자를 만들고 우리 코드는 같은 스키마로 모델이 보낸 인자를 검증할 수 있다. 직접 손으로 쓰는 경우는 드물다. 보통은 C# 메서드 시그니처나 zod 정의에서 자동으로 만든다(`02-maf.md` 3장).

**`description` 이 프롬프트다.** 모델은 이 설명만 보고 언제 이 도구를 쓸지 판단한다.
설명이 모호하면 안 써야 할 때 쓰거나, 써야 할 때 안 쓴다. **도구 설명을 다듬는 게 에이전트 튜닝의 절반이다.**

좋은 설명은 "무엇을 하는지"와 함께 "언제 쓰는지"를 적는다. 예를 들어 "문서를 검색한다" 보다 "사내 문서를 검색한다. 규정·정책·매뉴얼 질문에 사용. 일반 상식 질문에는 쓰지 않는다" 가 낫다. 인자 하나하나의 `description` 도 같은 역할을 한다. `department` 에 `enum` 을 걸어 두면 모델이 "인사팀" 같은 엉뚱한 값을 지어내는 일이 줄어든다.

### ② 모델이 호출을 요청한다

```json
{ "type": "tool_use", "id": "toolu_01", "name": "search_documents",
  "input": { "query": "연차 이월 규정", "department": "hr" } }
```

모델의 응답 안에 일반 텍스트 대신(또는 함께) 이 블록이 들어온다. `id` 는 이 호출 요청의 번호다. 한 응답에 도구 요청이 여러 개 들어올 수 있어서 어떤 결과가 어떤 요청의 것인지 짝을 맞출 때 쓴다.

### ③ 우리 코드가 실행하고 결과를 돌려준다

```json
{ "type": "tool_result", "tool_use_id": "toolu_01",
  "content": "[1] 제15조... [2] 제16조..." }
```

우리 코드는 `name` 을 보고 실제 함수를 찾아 `input` 을 넘겨 실행한다. 결과는 문자열로 만들어 `tool_use_id` 와 함께 대화에 덧붙인다. 그리고 지금까지의 대화 전체(질문 + 모델의 도구 요청 + 도구 결과)를 들고 모델을 다시 호출한다.

### ④ 모델이 최종 답을 만들거나, 또 다른 도구를 요청한다

```
while (응답에 tool_use 가 있는 동안) {
    각 tool_use 를 실행
    결과를 대화에 추가
    모델을 다시 호출
}
```

**이 while 루프가 "에이전트"의 실체다.** 프레임워크들이 감싸주는 것도 결국 이 루프다.

예시 질문이라면 루프가 이렇게 돈다.

```
1회차  모델: tool_use search_documents("연차 이월 규정", "hr")
       우리: 제15조, 제16조 본문을 tool_result 로 붙임
2회차  모델: "제15조에 따르면 미사용 연차는 다음 해 3월까지 ..."  ← tool_use 없음 → 종료
```

검색 결과가 부족하면 2회차에 모델이 다른 검색어로 한 번 더 검색을 요청할 수도 있다. 몇 바퀴 돌지는 모델이 정한다. 그래서 에이전트는 실행 시간과 비용을 미리 알기 어렵다.

## 3. 루프를 직접 짜면 만나는 문제들

| 문제 | 대응 |
| --- | --- |
| **무한 루프** | 최대 반복 횟수 (보통 10\~25). 초과 시 중단하고 사용자에게 알림 |
| **비용 폭주** | 반복마다 전체 대화가 다시 들어간다 → 토큰이 누적 증가. 예산 상한 |
| **같은 도구 반복 호출** | 결과 캐싱, 중복 감지 |
| **도구 실패** | 에러를 tool_result 로 돌려주면 모델이 재시도하거나 다른 방법을 찾는다. **예외로 죽이지 마라** |
| **컨텍스트 초과** | 오래된 턴 요약·압축, 도구 결과 절삭 |
| **병렬 도구 호출** | 모델이 한 번에 여러 도구를 요청할 수 있다. 독립적이면 동시 실행 |
| **취소** | CancellationToken 을 도구 실행까지 전파 |
| **부작용** | 삭제·전송 도구는 사람 승인을 거친다 |

표의 항목 몇 개는 풀어 둘 필요가 있다.

비용 폭주는 1장에서 본 stateless 성질 때문이다. 질문 1,000 토큰에 도구 결과가 매번 3,000 토큰씩 붙는다고 하자. 1회차 입력은 1,000 이지만 2회차는 4,000, 3회차는 7,000 이 된다. 다섯 바퀴만 돌아도 입력 토큰 합계가 첫 호출의 25배를 넘는다. 그래서 반복 횟수 상한과 함께 "이번 실행에서 쓸 수 있는 토큰 총량" 상한을 둔다.

컨텍스트 초과도 같은 뿌리다. 도구 결과를 통째로 넣지 말고 필요한 부분만 넣는다. 검색 도구라면 상위 몇 건만, 그것도 관련도 점수가 기준을 넘는 것만 돌려준다. 컨텍스트 윈도우를 꽉 채운다고 답이 좋아지지 않는다. 관련 없는 글이 섞이면 모델이 엉뚱한 근거를 집는다(`03-rag/01-pipeline.md` 의 컨텍스트 조립).

병렬 도구 호출은 모델이 한 응답에 `tool_use` 를 여러 개 담아 보내는 경우다. "서울과 부산 날씨 알려줘" 라면 날씨 도구 요청이 두 개 온다. 서로 의존하지 않으므로 순서대로 기다리지 말고 동시에 실행한다. 프론트의 `Promise.all` 이 C# 에서는 `Task.WhenAll` 이다.

취소의 CancellationToken 은 .NET 에서 "이 작업 그만해도 된다"는 신호를 전달하는 객체다. 프론트의 `AbortController.signal` 과 같은 역할이다. 사용자가 중지를 누르면 HTTP 요청의 토큰이 취소 상태가 된다. 이 토큰을 LLM 호출과 각 도구 실행까지 인자로 넘겨줘야 실제로 멈춘다. 중간에 하나라도 안 넘기면 그 구간은 끝까지 돌면서 비용을 쓴다. 자세한 이야기는 `02-csharp-dotnet/02-aspnet-core.md` 와 `05-realtime-ui/02-streaming-ui.md` 의 취소 절에 있다.

**"도구 실패를 예외로 던지지 말고 결과로 돌려준다"** 가 처음에 잘 안 떠오르는 부분이다.

```
tool_result: "오류: 부서 'hr2' 는 존재하지 않습니다. 가능한 값: hr, finance, legal"
```

이렇게 주면 모델이 스스로 고쳐서 다시 부른다. 예외로 죽이면 사용자에게 "에러 발생"만 남는다.

에러 메시지는 사람이 아니라 모델이 읽는다고 생각하고 쓴다. "무엇이 틀렸는지"와 "어떻게 고치면 되는지"가 같이 들어 있어야 모델이 다음 호출을 바로잡는다. 스택 트레이스나 내부 경로를 넣으면 고치는 데 도움이 안 되고 내부 정보만 새어 나간다. 다만 DB 연결 끊김처럼 모델이 고칠 수 없는 실패는 루프를 멈추고 사용자에게 알리는 편이 낫다. 모델이 같은 호출을 계속 반복하며 반복 횟수만 소진하기 때문이다.

## 4. 에이전트 패턴들

### ReAct (Reason + Act)
생각 → 행동 → 관찰 → 다시 생각. 가장 기본. 위의 루프가 그대로 ReAct 다.

"생각"은 모델이 다음에 무엇을 할지 판단하는 단계, "행동"은 도구 호출 요청, "관찰"은 도구 결과를 읽는 단계다. 2장의 예시에서 모델이 검색 결과를 보고 "이 정도면 답할 수 있다"고 판단한 순간이 다시 생각하는 단계에 해당한다.

### Planner-Executor
먼저 전체 계획을 세우고, 단계별로 실행. 복잡한 다단계 작업에 유리.
- ✅ 사용자에게 계획을 미리 보여줄 수 있다 (승인받기 좋음)
- ❌ 중간에 상황이 바뀌면 계획이 어긋난다 → 재계획 로직 필요

예를 들어 "지난 분기 부서별 지출을 정리해 보고서로 만들어줘" 라면 계획 단계에서 "① 재무 데이터 조회 → ② 부서별 합계 → ③ 보고서 작성" 을 먼저 만든다. 이 목록을 화면에 체크리스트로 보여 주고 사용자가 승인하면 실행에 들어간다. ①에서 데이터가 없다는 결과가 나오면 남은 계획을 다시 세워야 한다.

### 멀티 에이전트
역할별로 나눠 각자 전문화. 오케스트레이터가 조율.

여기서 오케스트레이션(orchestration)은 "누가 언제 일하고 누구의 결과를 누구에게 넘길지"를 정하는 일이다. 오케스트라 지휘자가 악기를 직접 연주하지 않고 들어올 순서만 정하는 것과 같다. 오케스트레이터는 그 역할을 맡은 코드나 에이전트다. 순서를 코드로 고정할 수도 있고 오케스트레이터 자신이 LLM 이라 매번 다음 담당을 고를 수도 있다.

```
Orchestrator
 ├── Researcher  (문서 검색 전담)
 ├── Analyst     (계산·분석)
 └── Writer      (보고서 작성)
```

**왜 나누나:** 하나의 프롬프트에 모든 역할을 담으면 지시가 서로 간섭한다.
도구가 20개면 모델이 뭘 써야 할지 헷갈린다. 역할별로 도구와 지시를 좁히면 각자 정확해진다.

도구 설명 20개는 그 자체로 컨텍스트 윈도우를 차지한다. 게다가 비슷한 도구가 여럿이면 description 만으로 구분하기 어렵다. Researcher 에게는 검색 도구 두세 개만, Writer 에게는 문서 생성 도구만 주면 각자 고를 후보가 줄어든다.

> **이건 이미 해본 것이다.** Claude Code 에서 서브에이전트로 역할을 분리한 이유가 정확히 같다.
> "한 프롬프트에 다 맡기면 왜 실패하는지"를 겪어봤다면, 멀티 에이전트 설계의 문제의식은 이미 갖고 있는 것이다.
> (다만 "그러니까 나는 에이전트 프레임워크를 안다"로 확대하지는 말 것 — 별개다)

**대가:** 에이전트 간 통신 비용, 컨텍스트 전달 손실, 디버깅 난이도 폭증.
**단일 에이전트로 되면 단일로 해라.** 멀티는 필요할 때만.

컨텍스트 전달 손실은 이런 뜻이다. Researcher 가 문서 열 건을 읽고 요약 세 줄만 Writer 에게 넘기면 Writer 는 나머지 일곱 건의 내용을 모른다. 요약을 길게 넘기면 토큰이 늘고 짧게 넘기면 정보가 빠진다. 에이전트가 하나 늘 때마다 이런 경계가 하나씩 생긴다.

### Human-in-the-loop
부작용 있는 도구 앞에서 멈추고 사람 승인을 받는다. 엔터프라이즈에서는 선택이 아니라 필수.

부작용(side effect)은 실행하면 바깥 세상이 바뀌는 동작이다. 조회는 몇 번을 해도 상태가 그대로지만 메일 발송, 결재 승인, 데이터 삭제는 되돌리기 어렵다. 구현으로 보면 루프가 해당 `tool_use` 를 만났을 때 실행하지 않고 "승인 대기" 상태로 멈춘 뒤 화면에 확인 카드를 띄우는 것이다. 사용자가 승인하면 그때 실행해 결과를 붙이고 루프를 이어 간다. 거절하면 "사용자가 거절함" 을 tool_result 로 돌려준다. 화면 쪽 설계는 `05-realtime-ui/02-streaming-ui.md` 6장에 있다.

## 5. 워크플로우 vs 에이전트

CXP 에 **Workflow** 와 **Agent** 가 따로 있는 이유.

| | 워크플로우 | 에이전트 |
| --- | --- | --- |
| 경로 | 개발자가 정한 고정 순서 | 모델이 매번 결정 |
| 예측 가능성 | 높다 | 낮다 |
| 디버깅 | 쉽다 | 어렵다 |
| 비용 | 예측 가능 | 변동 |
| 적합 | 단계가 뻔한 반복 업무 | 경로를 미리 알 수 없는 문제 |

**실무 원칙: 고정할 수 있는 건 고정해라.**
"문서 검색 → 요약 → 메일 발송" 처럼 순서가 정해진 일에 에이전트를 쓰면
비싸고 느리고 가끔 이상한 짓을 한다. 워크플로우로 짜고, **판단이 필요한 노드에만 LLM 을 둔다.**

같은 예를 워크플로우로 짜면 이렇다. 검색은 일반 함수로 호출하고 요약 노드에서만 LLM 을 한 번 부른다. 메일 발송도 일반 함수다. 모델이 "메일을 보낼지 말지" 고민할 여지가 없으니 발송을 빼먹거나 두 번 보내는 일이 없다. 반면 "고객 문의를 읽고 필요한 부서 시스템을 알아서 조회해 답하라" 는 경로를 미리 그릴 수 없으니 에이전트가 맞다.

랭코드가 두 제품을 나눠 놓은 건 이 트레이드오프를 제품 차원에서 인정한 것이다.

## 6. 에이전트를 운영한다는 것

`01-backend-basics/05-long-running-jobs.md` 가 전부 여기에 적용된다.

- 실행은 **오래 걸린다** → 잡 등록 + 폴링/SSE
- **비결정적** → 같은 입력에 다른 결과. 재시도가 답이 아니다
- **취소 가능해야 한다** → CancellationToken 전파
- **at-least-once** → 도구 실행이 두 번 될 수 있다. **부작용 있는 도구는 멱등하게**
- **추적** → 어떤 도구를 어떤 인자로 불렀고 뭘 받았는지 전부 기록. 이게 없으면 디버깅 불가

비결정적(non-deterministic)이라는 말은 같은 질문을 두 번 넣어도 모델이 다른 경로를 고를 수 있다는 뜻이다. 한 번은 검색 한 번에 답하고 다음엔 세 번 검색한다. 그래서 "실패하면 다시 돌리면 된다"가 통하지 않는다. 다시 돌린 결과는 앞의 실행과 다른 실행이다.

at-least-once 는 "최소 한 번은 실행되지만 두 번 실행될 수도 있다"는 보장이다. 서버가 도구를 실행한 직후 죽으면 재시작한 쪽은 실행 여부를 모르고 다시 실행한다. 멱등(idempotent)한 도구는 두 번 실행해도 결과가 한 번 실행한 것과 같다. "견적서 상태를 승인으로 바꾼다" 는 멱등하지만 "메일을 보낸다" 는 아니다. 메일 같은 도구는 Idempotency-Key 로 중복을 걸러야 한다(`01-backend-basics/05-long-running-jobs.md` 4장).

### 추적(trace) 에 남겨야 할 것

```
run_id, 단계 번호, 모델, 프롬프트 버전
각 turn: 입력 토큰 / 출력 토큰 / 지연
각 tool_use: 이름, 인자, 결과(절삭), 소요 시간, 성공 여부
최종: 총 비용, 총 소요, 종료 사유(완료/최대반복/취소/에러)
```

여기서 turn 은 모델을 한 번 호출하고 응답을 받는 한 바퀴다. trace(추적)는 요청 하나가 거친 단계를 시간 순서대로 이어 놓은 기록이다. 일반 API 의 트레이스와 같은 개념이고 도구 호출이 단계로 들어간다는 점만 다르다(`07-db-infra/04-observability.md` 5장).

종료 사유는 꼭 따로 남긴다. "최대 반복으로 끝났다" 는 모델이 답을 찾지 못하고 맴돌았다는 뜻이고 "완료" 와는 전혀 다른 상황이다. 화면에는 둘 다 그럴듯한 답이 보일 수 있어서 기록이 없으면 구분할 방법이 없다. 도구 결과는 길이가 길 수 있으니 앞부분만 잘라(절삭) 남기고 개인정보는 가린다.

**프론트엔드가 이걸 보여주는 화면을 만들면 팀 전체가 쓴다.**
"에이전트가 왜 이렇게 답했지?"에 답할 수 있는 유일한 방법이 타임라인 뷰다.

타임라인 뷰는 실행 하나를 세로 목록으로 보여 준다. 각 행에 turn 번호, 호출한 도구 이름과 인자, 결과 일부, 걸린 시간, 토큰 수를 놓고 펼치면 전문이 보이게 한다. 브라우저 개발자 도구의 Network 탭과 비슷한 화면이라고 생각하면 된다.

## 7. 평가

에이전트는 RAG 보다 평가가 어렵다. **경로가 매번 다르기 때문.**

| 층 | 무엇을 보나 |
| --- | --- |
| **최종 결과** | 과제를 완수했나 (성공률) |
| **경로** | 불필요한 도구 호출은 없었나, 몇 번 만에 끝났나 |
| **도구 선택** | 맞는 도구를 골랐나 (도구별 정밀도/재현율) |
| **비용·지연** | 회귀가 없나 |
| **안전** | 승인 없이 부작용 도구를 부른 적 없나 |

경로가 달라도 **결과가 맞으면 성공**으로 보는 게 기본이지만,
"10번 돌아서 맞춘 것"과 "2번에 맞춘 것"은 비용이 5배 다르다. 둘 다 본다.

도구 선택의 정밀도와 재현율은 이렇게 읽는다. 정밀도는 "검색 도구를 부른 경우 중 정말 검색이 필요했던 비율", 재현율은 "검색이 필요했던 경우 중 실제로 검색 도구를 부른 비율"이다. 정밀도가 낮으면 쓸데없이 부르고 재현율이 낮으면 불러야 할 때 안 부른다. 둘 중 어느 쪽이 낮은지에 따라 description 을 고치는 방향이 달라진다.

층을 나눠 보는 이유는 RAG 평가에서 검색 품질과 생성 품질을 따로 재는 것과 같다. 최종 답이 틀렸을 때 도구를 잘못 골라서인지, 도구는 맞게 골랐는데 결과를 잘못 읽어서인지를 가려야 고칠 곳이 보인다.

실무에서는 **시나리오 기반 회귀 테스트**를 만든다: 대표 과제 20\~50개를 정해두고
프롬프트/도구/모델이 바뀔 때마다 돌려서 성공률과 평균 스텝 수를 비교한다.
→ `03-rag/03-retrieval-quality.md` 의 CI 평가와 같은 구조.

회귀(regression)는 고친 뒤에 전에 되던 것이 안 되게 되는 현상이다. 도구 설명 한 줄을 바꿨는데 다른 시나리오의 성공률이 떨어지는 일이 흔하다. 모델이 비결정적이니 시나리오마다 여러 번 돌려 평균을 본다.
