# 스트리밍 UI 렌더링

**이미 잘하는 영역이다.** 입원 차트에서 표 전체가 재렌더되던 걸 Profiler 로 찾아 행 단위로 줄인 경험이
여기에 그대로 적용된다. 채팅 화면 특유의 함정만 추가로 짚는다.

전제는 `01-sse-vs-websocket.md` 에서 이어진다. 서버는 SSE 로 토큰 이벤트를 하나씩 보내고 클라이언트는 이벤트를 받을 때마다 `onToken(text)` 같은 콜백을 부른다. 이 문서는 그 콜백 뒤에서 화면을 어떻게 그리느냐를 다룬다.

---

## 1. 문제의 구조

LLM 은 초당 수십 토큰을 뱉는다. 토큰마다 `setState` 하면 **초당 수십 번 리렌더**다.

토큰은 모델이 글을 만드는 단위로, 대략 단어 조각이나 글자 몇 개 정도다(`04-agent/01-what-is-an-agent.md` 1장). 서버가 토큰 몇 개씩 묶어 보내더라도 이벤트는 초당 수십 개 도착한다.

React 18 의 자동 배칭(batching)을 떠올리면 "어차피 모아서 렌더하지 않나?" 싶을 수 있다. 배칭은 같은 이벤트 처리 안에서 연달아 부른 `setState` 를 한 번의 렌더로 합쳐 줄 뿐이다. 네트워크 이벤트는 각각 따로 도착하므로 이벤트 하나가 렌더 하나가 된다.

```tsx
// ❌ 모든 토큰마다 전체 대화 목록이 리렌더된다
const [messages, setMessages] = useState<Message[]>([]);

onToken((t) => setMessages(prev => {
  const last = prev[prev.length - 1];
  return [...prev.slice(0, -1), { ...last, content: last.content + t }];
}));
```

`messages` 배열이 통째로 새로 만들어지므로 **이전 메시지 100개도 전부 리렌더** 대상이 된다.
게다가 마크다운 파서가 매 토큰마다 전체 텍스트를 다시 파싱한다.

숫자로 보면 이렇다. 메시지 100개짜리 대화에서 답변 하나가 토큰 500개로 온다면 컴포넌트 렌더가 100 × 500 = 50,000 번 일어난다. 이전 메시지 내용은 하나도 안 바뀌었는데도 그렇다. 한 프레임(약 16ms) 안에 끝내야 할 일이 밀리기 시작하면 입력창 타이핑까지 버벅인다.

## 2. 해법 — 세 겹으로

### ① 스트리밍 중인 메시지를 분리한다

```tsx
// 확정된 메시지 목록 — 스트리밍 중에는 절대 안 바뀐다
const [messages, setMessages] = useState<Message[]>([]);
// 지금 오고 있는 것만 별도 상태
const [streaming, setStreaming] = useState<string>("");
// 콜백 안에서 최신 값을 읽기 위한 ref (아래 설명)
const streamingRef = useRef("");

onToken((t) => {
  streamingRef.current += t;
  setStreaming(streamingRef.current);
});

// 끝나면 한 번만 합친다
onDone(() => {
  const content = streamingRef.current;
  setMessages(prev => [...prev, { id: runId, role: "assistant", content }]);
  streamingRef.current = "";
  setStreaming("");
});
```

**이것만으로 리렌더 범위가 "마지막 버블 하나"로 줄어든다.** 가장 효과가 크고 가장 쉽다.

화면은 `messages.map(...)` 으로 확정 목록을 그리고 그 아래에 `streaming` 을 그리는 버블 하나를 따로 둔다. `messages` 의 참조가 그대로라 목록 쪽은 다시 그릴 이유가 없다.

`streamingRef` 를 같이 두는 이유는 오래된 클로저(stale closure) 때문이다. `onDone` 콜백을 스트림 시작 시 한 번 등록하면 그 함수는 등록 시점의 `streaming` 값(빈 문자열)을 기억한다. 콜백 안에서 `streaming` 상태를 읽으면 끝까지 빈 문자열이 나와 빈 메시지가 저장된다. ref 는 렌더와 상관없이 항상 같은 객체라 언제 읽어도 최신 값이 들어 있다.

### ② 토큰을 ref 에 모으고 간헐적으로 커밋

```tsx
const bufferRef = useRef("");
const rafRef = useRef(0);
const [text, setText] = useState("");

const onToken = (t: string) => {
  bufferRef.current += t;                  // 렌더 유발 없음
  if (rafRef.current) return;              // 이미 다음 프레임에 예약돼 있다
  rafRef.current = requestAnimationFrame(() => {
    rafRef.current = 0;
    setText(bufferRef.current);            // 프레임당 최대 1회
  });
};

useEffect(() => () => cancelAnimationFrame(rafRef.current), []);
```

초당 60회 이상으로는 어차피 사람이 인지하지 못한다. `requestAnimationFrame` 이나
50\~100ms throttle 로 커밋 빈도를 고정한다.

`requestAnimationFrame`(rAF)은 "다음 화면을 그리기 직전에 이 함수를 한 번 불러 달라"는 브라우저 API 다. 화면은 보통 초당 60번(약 16ms마다) 갱신된다. 위 코드는 토큰이 아무리 많이 와도 한 프레임 사이에 온 토큰을 ref 에 이어 붙여 두었다가 프레임 직전에 `setText` 를 한 번만 부른다. 이 방식을 rAF 배칭이라고 부른다. 토큰이 안 오면 예약도 하지 않으므로 할 일 없는 프레임에 함수가 돌지 않는다. 여기서 커밋은 React 가 렌더 결과를 실제 DOM 에 반영하는 단계를 말한다.

비슷한 도구 셋을 구분해 두자.

- throttle 은 "최대 N ms 에 한 번만" 실행한다. 100ms throttle 이면 토큰이 계속 와도 0.1초마다 한 번 갱신된다. rAF 배칭은 간격을 브라우저 화면 갱신 주기에 맞춘 throttle 이라고 보면 된다.
- debounce 는 "입력이 N ms 동안 멈추면 그때 한 번" 실행한다. 검색창 자동완성에 쓰는 그것이다. 스트리밍에 쓰면 토큰이 쉬지 않고 오는 동안 한 번도 갱신되지 않고 답이 다 끝난 뒤에야 글자가 나타난다. 스트리밍에는 맞지 않는다.

탭이 백그라운드로 가면 브라우저는 rAF 호출을 멈춘다. 토큰은 ref 에 계속 쌓이다가 탭으로 돌아오는 순간 한꺼번에 반영된다. 스트림이 백그라운드에서 끝나도 `onDone` 에서는 ref 의 값을 직접 읽어 저장하므로 내용이 빠지지 않는다.

> 입원 차트에서 한 것과 같은 발상이다. **"데이터 갱신 빈도"와 "렌더 빈도"를 분리한다.**

### ③ 확정 메시지를 memo 로 잠근다

```tsx
const MessageBubble = memo(function MessageBubble({ message }: { message: Message }) {
  return <Markdown>{message.content}</Markdown>;
}, (a, b) => a.message.id === b.message.id && a.message.content === b.message.content);
```

리스트 key 는 반드시 안정적인 id 로. 인덱스를 쓰면 스트리밍 중 재정렬에서 깨진다.

`memo` 의 두 번째 인자는 "이전 props 와 다음 props 가 같으면 true" 를 돌려주는 비교 함수다. true 면 React 가 이 컴포넌트의 렌더를 건너뛴다. 부모가 다시 렌더되더라도 id 와 내용이 같은 확정 메시지는 그대로 둔다. ①로 `messages` 참조를 지켰다면 대부분 필요 없다. 그래도 입력창 상태나 사이드바 상태처럼 부모를 다시 렌더시키는 다른 원인이 있을 때 방어선 역할을 한다.

인덱스 key 가 깨지는 경우는 이렇다. 메시지를 지우거나 위로 과거 대화를 더 불러오면 같은 인덱스가 다른 메시지를 가리키게 된다. React 는 key 가 같으면 같은 컴포넌트로 보고 내부 상태(펼침 여부, 복사 버튼 상태 등)를 그대로 넘겨 버린다.

## 3. 마크다운 — 채팅 UI 최대의 성능 함정

```tsx
<Markdown>{streamingText}</Markdown>    // ❌ 토큰마다 전체 재파싱 + 전체 DOM 교체
```

문제가 두 겹이다.
1. 파싱 비용이 텍스트 길이에 비례해 누적된다 (O(n²))
2. **미완성 마크다운이 깨진 채로 렌더된다** — 닫히지 않은 코드블록, ` ** ` 하나만 온 상태

1번의 O(n²) 은 이렇게 나온다. 답변이 토큰 1,000개라면 첫 토큰에서 1개 분량, 두 번째에서 2개 분량, ... 마지막에 1,000개 분량을 파싱한다. 합하면 약 50만 개 분량이다. 끝난 뒤 한 번만 파싱했다면 1,000개 분량이면 됐다. 답이 길어질수록 뒤로 갈수록 느려지는 체감이 여기서 온다.

2번은 이런 모습이다. 모델이 코드블록을 여는 ```` ```ts ```` 까지만 보낸 순간, 파서는 그 아래 전부를 코드로 본다. 다음 토큰에서 블록이 닫히면 화면 전체가 일반 문단으로 돌아간다. 사용자 눈에는 화면이 번쩍이며 레이아웃이 뒤집히는 것으로 보인다.

### 대응

| 방법 | 설명 |
| --- | --- |
| **블록 단위 분할 + memo** | 완성된 블록(문단·코드블록)은 더 이상 안 바뀌므로 memo. 마지막 블록만 다시 렌더 |
| **스트리밍 중엔 plain text** | 끝나면 한 번 마크다운으로 교체. 가장 단순하고 확실하다 |
| **미완성 보정** | 닫히지 않은 코드 펜스를 임시로 닫아서 파서에 넘긴다 |
| **코드 하이라이팅 지연** | Shiki/Prism 은 무겁다. 스트리밍 중엔 끄고 완료 후 적용 |

**실무에서는 "마지막 블록만 raw, 나머지는 memo 된 마크다운"** 조합이 가장 많이 쓰인다.

```tsx
// 완성된 블록들 (변하지 않음) + 진행 중인 마지막 블록
const blocks = useMemo(() => splitIntoBlocks(text), [text]);
return (
  <>
    {blocks.slice(0, -1).map(b => <MemoBlock key={b.id} block={b} />)}
    <pre className="whitespace-pre-wrap">{blocks.at(-1)?.raw}</pre>
  </>
);
```

`splitIntoBlocks` 는 텍스트를 빈 줄 기준으로 문단과 코드블록 단위로 자른다. 코드 펜스 안의 빈 줄에서는 자르지 않아야 한다. 새 토큰은 항상 마지막 블록에만 붙으므로 앞의 블록은 한 번 완성되면 내용이 바뀌지 않는다. 블록 id 를 순번(0, 1, 2...)으로 주면 key 가 안정적이고 `MemoBlock` 은 내용이 같으면 렌더를 건너뛴다. 결과적으로 토큰마다 파싱하는 양이 "전체 답변"에서 "마지막 문단 하나"로 줄어든다.

다른 선택지로 React 18 의 `useDeferredValue` 가 있다. 마크다운 쪽에는 지연된 값을 넘겨 React 가 급한 렌더(입력창 타이핑 등)를 먼저 처리하고 마크다운은 여유 있을 때 그리게 한다. 파싱 총량을 줄여 주지는 않으니 블록 분할과 함께 쓰는 보조 수단으로 보면 된다.

## 4. 자동 스크롤 — 생각보다 까다롭다

```tsx
// ❌ 사용자가 위로 올려 읽고 있는데 계속 끌어내린다
useEffect(() => { endRef.current?.scrollIntoView(); }, [text]);
```

**규칙: 사용자가 바닥 근처에 있을 때만 따라간다.**

```tsx
const [stick, setStick] = useState(true);

const onScroll = (e: React.UIEvent<HTMLDivElement>) => {
  const el = e.currentTarget;
  const atBottom = el.scrollHeight - el.scrollTop - el.clientHeight < 80;
  setStick(atBottom);
};

useEffect(() => {
  if (stick) endRef.current?.scrollIntoView({ behavior: "auto" });
}, [text, stick]);
```

`atBottom` 계산식을 풀면 이렇다. `scrollHeight` 는 내용 전체 높이, `scrollTop` 은 위로 스크롤된 거리, `clientHeight` 는 눈에 보이는 창의 높이다. 전체 높이에서 이미 지나간 거리와 보이는 높이를 빼면 "아래에 남은 거리"가 나온다. 이 값이 80px 보다 작으면 바닥 근처로 본다. 0 으로 비교하지 않는 이유는 소수점 픽셀과 새로 추가된 줄 때문에 정확히 0 이 되는 순간이 드물어서다.

`endRef` 는 메시지 목록 맨 끝에 둔 빈 `div` 다. 그 요소를 화면 안으로 끌어오면 바닥으로 스크롤된다.

추가로:
- **"맨 아래로" 버튼**을 `stick === false` 일 때 띄운다
- `behavior: "smooth"` 는 스트리밍 중엔 쓰지 마라. 애니메이션이 밀려 끊겨 보인다
- **CSS 로 해결하는 법:** 컨테이너에 `overflow-anchor: auto` + `display: flex; flex-direction: column-reverse`
  조합을 쓰면 브라우저가 알아서 바닥에 고정한다. 다만 스크롤 방향 로직이 뒤집혀 다루기 까다롭다

smooth 가 끊겨 보이는 이유는 스크롤 애니메이션이 300ms 정도 걸리는 동안 새 토큰이 와서 목표 지점이 계속 바뀌기 때문이다. 애니메이션이 끝나기 전에 다음 애니메이션이 시작되기를 반복해 화면이 덜컹거린다.

## 5. 취소

```tsx
const abortRef = useRef<AbortController | null>(null);

const send = async (msg: string) => {
  abortRef.current = new AbortController();
  await streamChat(msg, { signal: abortRef.current.signal, onToken });
};

const stop = () => {
  abortRef.current?.abort();            // ① 클라이언트 연결 끊기
  fetch(`/api/chat/runs/${runId}`, { method: "DELETE" });   // ② 서버에도 알림
};
```

**①만 하면 서버는 계속 돌면서 토큰 비용을 태운다.** 둘 다 필요하다.
서버 쪽에서는 `CancellationToken` 이 LLM 호출까지 전파돼 있어야 실제로 멈춘다.

①과 ②가 따로 필요한 이유는 `01-sse-vs-websocket.md` 4장의 구조 때문이다. 실행은 백그라운드 잡으로 돌고 SSE 연결은 결과를 읽기만 한다. ①은 "나 이제 안 읽을래"이고 ②는 "그 작업 자체를 멈춰 줘"다. 연결을 끊는 것만으로 서버가 작업을 멈추게 하면 잠깐의 네트워크 끊김에도 실행이 날아가 이어받기가 불가능해진다. 그래서 의도적인 중지는 별도 요청으로 알린다. ②를 받은 서버는 그 실행의 CancellationToken 을 취소한다. 이 토큰은 LLM 호출과 도구 실행까지 전달돼 있어야 한다(`04-agent/01-what-is-an-agent.md` 3장).

취소했을 때 **이미 받은 부분 응답은 남긴다.** 지워버리면 사용자가 읽던 내용이 사라진다.

부분 응답을 남길 때는 "중지됨" 표시를 붙여 완성된 답과 구분한다. 서버에도 부분 응답과 종료 사유(취소)를 같이 저장해 두면 새로고침 후에도 같은 모습으로 복구된다.

## 6. 채팅 + 업무 화면 연계 — 공고에 적힌 그 업무

> "AI Agent 등의 채팅 중심 화면 요소와 업무 중심 화면 요소간 연계"

### 무엇이 어려운가

에이전트가 업무 데이터를 **바꾸면**, 옆에 열려 있는 업무 화면이 낡은 데이터를 보여주게 된다.

```
[좌] 채팅: "이 견적서 승인해줘"  → 에이전트가 상태를 변경
[우] 견적서 목록: 아직 '대기중'으로 표시
```

업무 화면은 TanStack Query 같은 캐시에 견적서 목록을 들고 있다. 이 캐시는 "내가 직접 수정 요청을 보냈을 때"만 갱신하도록 짜여 있는 경우가 많다. 에이전트는 화면을 거치지 않고 서버에서 바로 데이터를 바꾸니 업무 화면은 바뀐 줄을 모른다.

### 대응

| 방법 | 설명 |
| --- | --- |
| **이벤트 기반 무효화** | 에이전트 완료 시 `{ type: "entity_changed", entity: "quote", id }` 이벤트를 SSE 로 → `queryClient.invalidateQueries(['quote', id])` |
| **낙관적 반영** | 에이전트가 "무엇을 할 것인지"를 먼저 알려주면 UI 를 미리 갱신. 실패 시 롤백 |
| **단일 진실 원천** | 채팅이 만든 변경도 결국 같은 API 를 타게 한다. 채팅 전용 경로를 만들면 두 상태가 갈라진다 |
| **승인 UI** | 부작용 있는 행동은 채팅 안에 인라인 카드로 띄우고 사용자가 확인 |

이벤트 기반 무효화는 이렇게 이어진다. 에이전트가 견적서 상태를 바꾸는 도구를 실행하면 서버는 채팅 스트림에 `entity_changed` 이벤트를 하나 끼워 보낸다. 클라이언트는 이 이벤트를 받아 해당 쿼리를 무효화(invalidate)한다. 무효화는 "이 캐시는 이제 낡았다"고 표시하는 것이다. 그 쿼리를 쓰는 화면이 열려 있으면 TanStack Query 가 자동으로 다시 가져온다. 서버가 새 데이터를 통째로 밀어주는 게 아니라 "다시 가져와"라는 신호만 보내므로 이벤트가 작고 단순하다.

낙관적 반영(optimistic update)은 서버 응답을 기다리지 않고 성공할 거라 가정하고 화면부터 바꾸는 방식이다. 좋아요 버튼을 누르면 숫자가 바로 오르는 그것이다. 에이전트가 "견적서 Q-123 을 승인하겠습니다"라는 도구 요청을 낸 시점에 목록의 상태를 '승인 처리 중'으로 미리 바꿔 두고 실패하면 되돌린다.

**세 번째가 설계의 핵심이다.** 에이전트가 DB 를 직접 만지는 경로를 따로 두면,
업무 화면의 검증·감사 로그·권한 체크를 전부 우회하게 된다.
**에이전트도 우리 API 의 클라이언트여야 한다.**

단일 진실 원천(single source of truth)은 같은 데이터를 바꾸는 길이 하나뿐이어야 한다는 원칙이다. 견적서 승인이라면 화면의 승인 버튼과 에이전트의 승인 도구가 둘 다 같은 `POST /quotes/{id}/approve` 를 부른다. 그러면 금액 한도 검증, 감사 로그, 권한 체크가 한곳에서 똑같이 적용되고 변경 이벤트를 내보내는 지점도 하나로 모인다.

> TanStack Query 를 쓰고 있다면 `invalidateQueries` 로 대부분 해결된다.
> **어려운 건 기술이 아니라 "무엇이 바뀌었는지 서버가 알려주게 만드는 것"** 이다.

## 7. 그 밖에 챙길 것

| 항목 | |
| --- | --- |
| **접근성** | 스트리밍 텍스트에 `aria-live="polite"` — 단, 토큰마다 읽으면 소음이 된다. 완료 시에만 알리는 게 낫다 |
| **긴 대화** | 메시지 수백 개면 가상 스크롤(react-virtual). 단, 높이가 가변이라 까다롭다 |
| **에러 중간 발생** | 스트림 도중 끊기면 부분 응답 + "재시도" 버튼. 통째로 날리지 않는다 |
| **새로고침 복구** | `runId` 를 URL 이나 localStorage 에. 진행 중 작업을 잃지 않게 |
| **동시 대화** | 여러 탭에서 같은 대화를 열면? BroadcastChannel 또는 서버 상태를 진실로 |
| **비용 표시** | 내부 도구라면 토큰 사용량을 보여주는 것도 유용하다 |

표의 용어 몇 개를 풀어 둔다. `aria-live` 는 스크린 리더에게 "이 영역 내용이 바뀌면 읽어 달라"고 알리는 속성이다. `polite` 는 지금 읽던 걸 끝낸 뒤 읽으라는 뜻이다. 스트리밍 텍스트 자체에 걸면 글자가 바뀔 때마다 읽으려 들어서 듣는 사람에게는 소음이 된다. 그래서 별도의 숨긴 영역에 "답변이 완료되었습니다" 같은 문장을 완료 시점에 한 번 넣는 방식을 쓴다.

가상 스크롤(virtualization)은 화면에 보이는 메시지만 실제 DOM 으로 만들고 나머지는 높이만 계산해 빈 공간으로 두는 기법이다. 메시지마다 길이가 다르고 스트리밍 중에는 마지막 메시지 높이가 계속 변하니 높이를 측정해 다시 계산하는 처리가 필요하다.

BroadcastChannel 은 같은 출처(origin)의 탭끼리 메시지를 주고받는 브라우저 API 다. 한 탭에서 답변이 끝나면 다른 탭에 "대화 갱신됨"을 알리는 데 쓴다. 다만 탭 사이의 상태를 맞추는 것보다 서버의 대화 상태를 진실로 두고 각 탭이 그걸 다시 읽게 하는 편이 단순하다.

## 8. 측정

추측하지 말고 React DevTools Profiler 로 확인한다.

```
1. Profiler 녹화 시작
2. 스트리밍 응답 하나 받기
3. 커밋 횟수와 각 커밋의 소요 시간 확인
```

- 커밋이 수백 번 → ② throttle 이 안 걸린 것
- 커밋당 시간이 길다 → 렌더 범위가 넓은 것 (① 분리, ③ memo)
- 특정 컴포넌트만 오래 → 대개 마크다운/하이라이터

Profiler 설정에서 "Record why each component rendered" 를 켜 두면 각 컴포넌트가 왜 다시 렌더됐는지(props 변경, 부모 렌더, 상태 변경)까지 보인다. 확정 메시지 버블이 "parent rendered" 로 계속 찍힌다면 ③의 memo 가 빠졌거나 비교 함수가 늘 false 를 돌려주는 것이다.

**이미 해본 방법 그대로다.** 대상이 입원 차트에서 채팅 버블로 바뀐 것뿐이다.
